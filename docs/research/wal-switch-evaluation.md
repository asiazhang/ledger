## 0. 结论摘要

**结论：(b) 维持现状——不切 WAL，ADR-0117 决策 6 的触发门维持原文，不随「UI 优先」原则改写。**

三条决定性理由：

1. **边际收益趋近于零，且已按 UI 优先原则先行评估完毕。** 双连接模型（ADR-0117）已把真正的迟滞层——应用层写者闸门——结构性移出读路径；WAL 能再消除的只剩文件锁层「提交瞬间 EXCLUSIVE 窗口」的有界等待（≤5s）与 busy 失败类，而 #1720 的三档观测（2026-08-28 → 09-16 全部历史日志：busy 超时 / `database is locked` / 锁持时 >1s 探针）**全部零命中**。
2. **代价落在数据安全核上。** WAL 把「单文件 = 全部状态」的既定语义扩成三件套（`ledger.db` + `-wal` + `-shm`），本仓库有 **7 处文件级操作**要重裁——其中恢复、忘记口令重置、启动失败重置、加密转换/归一化是**单向不可再试**的操作。官方恢复机制对「旧边车残留 + 新主库」**没有与主库配对的校验**【一手】，引入今天不存在的「旧帧回放损坏」故障类。
3. **WAL 自带一个新的、保证会发生迟滞源，与 UI 优先原则方向相反。** autocheckpoint（默认 1000 页 PASSIVE）内联在 COMMIT 路径执行，偶发拖慢单次提交【一手】；现状被质疑的那个等待窗则是**有界且从未发生**的。用「保证偶发的慢」换「从未发生过的等待」，在 UI 优先标尺下是负收益。

触发门问题的明确回答：**不改写。** 判据①②仍可检验且未命中；#1720 已把③（迟滞类）归入 ADR-0117 的观测判据——观测面已按 UI 优先前移到「不等失败、盯迟滞」；而「竞争面存在即引入」式改写会被第 5.3 节的反向迟滞面直接反驳，改写后判据反而更不诚实。

## 1. 背景：触发门原文与本次评估的驱动

ADR-0117 决策 6 的升级触发条件（原文两档）：

> ①真实出现长于 `busy_timeout` 的写事务或提交窗口，读命令在等待窗内实际失败且用户可感知；②出现「写事务打开期间要求无界读可用」的真实需求。触发即修订本 ADR 单独裁决 WAL；未触发不引入。

- **两档均未命中**：#1720 已以 3.5 周全量日志证据定案（三档零命中），`unlock_notify` 等待优化 `wontfix`，「双侧 5s busy_timeout 不动」「1s 锁持探针阈值不动」为顺带定案的不动项【[#1720 定案评论](https://github.com/asiazhang/ledger/issues/1720#issuecomment-5788455103)】。
- **本票的驱动不是痛点而是原则**：AGENTS.md「用户使用时基本感受不到迟滞感，用户界面使用感受优先」——「等用户实际感知失败才评估」太晚，竞争面存在本身就是迟滞风险，故**评估先行**；但**评估 ≠ 引入**，WAL 是否引入仍由维护者裁决。

因此本报告回答两个问题：**(1)** WAL 对既有文件级语义的重裁代价有多大；**(2)** 触发门两档在 WAL 世界里还剩多少收益。最后二选一落结论。

## 2. 现状事实基线（代码核对）【代码】

1. **无持久化 WAL 设置点**：全仓唯一的 `journal_mode` 设置在 ledger-perf 生成期连接（`MEMORY`，连接级不持久化）；生产库恒为 rollback journal（delete）模式，单文件形态、无边车文件。
2. **双连接形态**：`open_db_in` 成对打开写连接 + `SQLITE_OPEN_READ_ONLY` 只读连接（写连接先行，建连收尾单点注入密钥 → `busy_timeout` → 外键 → 耗时 hook）；`CONCURRENT_BUSY_TIMEOUT` = 5s 单点收口，两侧同源。
3. **文件级操作清单**（全部核对过实现）：
   | 操作 | 机制 | 落点 |
   |---|---|---|
   | 备份 | 写连接上 `VACUUM INTO` → zip | 备份引擎 |
   | 恢复 | 提取临时同目录 → integrity + `user_version` 校验 → `fs::copy` 当前库为 RestoreSafetyBackup → `replace_file`（rename）替换 → 重启/原位重引导 | 备份引擎 |
   | 加密转换 / 归一化（ADR-0127） | 导出新库 → 试开校验 → rename 旧库 `.bak` + rename 新库顶位（失败尽力回滚） | 引导层转换链 |
   | 忘记口令重置 | 探测密文 → rename `ledger.db` → `ledger.db.bak` → 原位新建明文空库 | 引导层 |
   | 启动失败重置 | rename `ledger.db` → `ledger.db.bak` → 新建空库（建连 + 迁移 + integrity） | 建连层 |
   | 数据搬迁 | 源库 `VACUUM INTO` 目标临时名 → integrity → rename 启用；**旧位置的库永久保留**；密文库推迟解锁后补做 | 引导层 |
   | 手工拷库 | 用户自行拷贝 `ledger.db`（单文件即全部状态，应用开/关无差别） | 用户动作 |
4. **退出路径**：`RunEvent::Exit` 只挂退出兜底备份，**无显式连接收口/关库动作**——进程结束依赖 OS 回收。rollback 模式下无影响；WAL 下这是边车残留概率的关键输入（见 4.7）。
5. **边车防御先例**：ledger-perf 快照复制已有 `-wal` 残留防御（拷主库时连带拷 `-wal`、清理时三件套齐删）——工具链已把「边车是持久状态的一部分」当作防御面，生产路径尚无对应物。
6. **术语注意**：仓内已有业务概念「同步检查点」（sync-engine Checkpoint、`V022__sync_checkpoint`），与 SQLite `wal_checkpoint` 是不同概念，报告与未来实施须防撞名（见 4.7）。

## 3. WAL 技术事实（评估地基）

以下 13 条为重裁与收益判断的事实依据（细节与来源由本次调研产出，此处收录决定性条目）：

1. **WAL 是持久化 journal mode**：写入库文件头，跨连接、跨重启生效；任一连接设置即对同文件全部连接生效；切回需显式 `PRAGMA journal_mode=DELETE`。——【一手】wal.html §3.3/§8/§10
2. **边车生命周期**：连接打开期间 `-wal` 存在；**最后一个连接干净关闭**时先最终 checkpoint 再删 `-wal`/`-shm`；残留场景：崩溃/未干净退出、`PERSIST_WAL`、最后断开的是只读客户端。——【一手】wal.html §4/§6/§9
3. **恢复与分离后果**：首个连接自动 recovery（逐帧校验 checksum），崩溃后无须人工干预；但**主库与 `-wal` 分离**时官方原话是「先前已提交的事务可能丢失，或库文件可能损坏」；**recovery 只校验 WAL 自身帧校验和，salt 取自 WAL 头，没有任何与主库配对的校验**——旧边车 + 新主库 = 旧帧会被回放。——【一手】walformat.html §3、howtocorrupt.html §1.2/§1.3
4. **拷库要求**：`-wal` 是数据库持久状态的一部分，复制/移动必须连带；运行中拷「三件套」无原子性保证；官方推荐一致性手段是 backup API 或 `VACUUM INTO`；安全移除 `-wal` 的唯一方式是「打开再关闭数据库」。——【一手】wal.html §4、howtocorrupt.html §1.2、backup.html、lang_vacuum.html#vacuuminto
5. **并发与剩余 busy**：读写互不阻塞，提交只追加 WAL、不取主文件 EXCLUSIVE（EXCLUSIVE 仅 checkpoint 完成、WAL reset、模式切换、recovery 时短暂使用）；剩余 SQLITE_BUSY 场景：EXCLUSIVE locking mode、最后连接清理边车瞬间、崩溃后首连接 recovery 期间（`SQLITE_BUSY_RECOVERY`）、写写争用（本应用单进程单写者 ≈ 无）。——【一手】wal.html §1/§2.2/§9、walformat.html §2.3.1
6. **checkpoint**：默认 autocheckpoint 1000 页且**全部 PASSIVE**（不阻塞、不走 busy handler），WAL 达阈与最后连接关闭时各触发；FULL/RESTART/TRUNCATE 才阻塞（阻塞并发写者）；官方时机建议：不想 COMMIT 偶发变慢可关自动 checkpoint 挪独立线程/进程。——【一手】pragma.html（wal_autocheckpoint / wal_checkpoint）、wal.html §2.1/§3
7. **VACUUM INTO**：官方明确其输出是一致快照、事务性，WAL 源下**包含未 checkpoint 的已提交事务**；**输出文件的 journal mode 官方文档未声明**，论坛复现（3.46.1）为源 WAL → 输出 **delete**（发帖者视为文档缺口上报）。——【一手】lang_vacuum.html#vacuuminto；【社区】forum/forumpost/8f98e0d81b
8. **backup API**：完成时目标库是「开始拷贝那一刻」的一致最新快照，中途写入不破坏一致性；`VACUUM INTO` 被列为同等活库备份技术。——【一手】backup.html
9. **SQLCipher 与 WAL**：支持 WAL；**`-wal` 页数据用库密钥加密**（官方 design 给出 hexdump 验证），`-journal` 同样加密；**`-shm` 不在官方加密文件清单**（按 walformat：wal-index = 帧号/页号/校验和/salt/锁字节，无行数据，但暴露结构元信息）；`PRAGMA key` 必须在首次操作前；加密/解密导出走 `sqlcipher_export`，源库 `-wal` 已提交内容可见且不复制进目标；社区报告源库带旧边车时导出报 `disk image malformed`（删边车即恢复，二手）；4.14.0 修过 WAL-reset bug 并建议 WAL 场景升级。——【一手】zetetic.net/sqlcipher/design、sqlcipher-api；【社区】discuss.zetetic.net
10. **文件替换的官方指引**：覆盖库文件时**必须同时删除其热 journal（含 `-wal` 后缀）**；移动/复制必须连 `-wal` 走；两者都列为明确损坏成因。——【一手】howtocorrupt.html §1.2/§1.3、wal.html §4
11. **崩溃安全**：checkpoint 先 sync WAL 再回填、回填后 sync 主库再 reset，完成后主库具备原子性；WAL+FULL = 断电持久 ACID，WAL+NORMAL 始终一致但不保证断电持久（应用崩溃总是安全）；官方称 WAL 对 sync 失败「far more forgiving」。——【一手】pragma.html（synchronous）、wal.html §2.3
12. **官方劣势清单（反方依据）**：读为主应用可能慢 1–2%；**多出准持久的 `-wal`/`-shm`（官方明言这会降低其作为「应用文件格式」的吸引力）**；多出 checkpoint 需开发者留意；进 WAL 后不能改 `page_size`；只读打开条件变苛刻；autocheckpoint 触发时偶发 COMMIT 明显变慢。官方**未**有「单写者+单读者场景不值得切」的直接论断。——【一手】wal.html §1/§6
13. **只读连接 + WAL**：只读打开须满足其一——①边车已存在且可读；②目录可写、允许创建边车；③`immutable=1`；边车缺失且无权创建则打不开（`SQLITE_READONLY_RECOVERY` / `SQLITE_READONLY_CANTINIT` / `SQLITE_CANTOPEN`）；官方推荐先让可写连接完成初始化。——【一手】wal.html §5、rescode.html

## 4. 文件级语义重裁点逐项

### 4.1 备份与恢复（ADR-0007：`VACUUM INTO` 在线快照 + 文件替换式还原）

**现状语义**：备份 = 写连接上 `VACUUM INTO` 产出单文件一致快照后 zip 包装，不停写、无需关应用；恢复 = 提取到临时同目录 → `integrity_check` + `user_version` 校验（拒绝发生在替换之前）→ `fs::copy` 把当前库整文件拷为 RestoreSafetyBackup → `replace_file` rename 替换原库 → 恢复后自动重启/原位重引导；恢复期间持写连接锁。单文件形态下，安全备份的 `fs::copy` 与替换 rename 都天然自含。

**WAL 下语义变化**：
- `VACUUM INTO` 快照一致性**不变且更强**：读路径经 WAL 能见全部已提交（含未 checkpoint）事务【一手】；输出 journal mode 官方未声明、论坛复现为 delete——若成立，**备份产物仍是单文件 rollback 库**（zip 形态、恢复校验、跨模式语义都可能零改动），但这是文档缺口，属实施前必须实测的验证项【社区】。
- **RestoreSafetyBackup 的 `fs::copy` 只拷主文件**：WAL 中未 checkpoint 的已提交事务不在副本里——数据安全兜底件在「应用运行中恢复」这个恰恰最需要它的时刻静默失真（官方原话：分离可丢已提交事务或损坏）【一手】。
- **`replace_file` 只替换主文件**：旧 `ledger.db-wal/-shm` 残留在新库旁边，下次打开即触发 §3 条目 3 的旧帧回放——官方 howtocorrupt 明列的损坏成因【一手】。
- journal mode 随文件头走：若恢复产物是 delete 模式（同上待实测），替换后的活库会**静默回退 rollback 模式**，除非建连收尾每开必设 `PRAGMA journal_mode=WAL`（幂等）——WAL 的引入必须带一个「每次建连重申 journal mode」的收口单点，这是今天不存在的机制。

**影响**：
- **用户可见**：恢复损坏 → 启动失败恢复屏 / 数据丢失；恢复语义（本应用的最终自救通道）从「已验证原子」退化为「依赖边车清理是否做对」。
- **数据安全**：安全备份失真 + 残留回放损坏，两条都落在恢复链上——引入今天不存在的故障类。
- **复杂度**：恢复链 3 处改动（安全备份前先归并、替换连带删边车、journal mode 重设收口）+ 一项实测验证（`VACUUM INTO` 输出模式）。

### 4.2 模式随文件走（ADR-0075 决策 7）与整库转换 / 归一化链

**现状语义**：加密状态 = 库文件头 16 字节（文件即真相，不进引导状态）；备份产物天然密文（`VACUUM INTO` 继承密钥），备份/恢复/搬迁三条路径零改动；转换（开启/关闭/改口令）与 ADR-0127 归一化共用一条链：导出新库 → 试开校验 → rename 旧库 `.bak` 保留副本 → rename 新库原子顶位，中途失败原库原样、不存在半加密状态。

**WAL 下语义变化**：
- SQLCipher 加密 `-wal`（页数据同密钥）【一手】，`-shm` 不在官方加密清单（无行数据，含结构元信息）【一手】——**「文件即真相」从单文件扩为三件套**：主文件头判别逻辑本身不变，但「拷走 / 替换 / 改名单个文件」不再等价于「操作了这个库」。
- **转换 swap 的边车配对**：活库带边车时 rename 主文件 → 新库顶位后与**旧库的边车**配对 → §3 条目 3 的旧帧回放打进新密文库（或反向）→ 损坏。swap 前必须先「打开再关闭」归并或连带处置边车【一手】，这一步今天不存在。
- **`.bak` 副本失真**：rename 只带走主文件，副本丢 WAL 内容——「转换前形态保留」「忘记口令后想起口令仍可救回」的副本语义都静默缩水。
- SQLCipher 导出链对源库边车的依赖有社区 malformed 报告（二手），转换链须实测覆盖「带残留边车的源库」输入【社区】。

**影响**：
- **用户可见**：转换三流（开启/关闭/改口令）的「失败原库原样、无半加密状态」原子性承诺要重新验证。
- **数据安全**：核心中的核心——`.bak` 是不可再试单向操作的唯一回滚件，副本失真 + swap 残留是双重数据安全降级。
- **复杂度**：转换链、归一化链（ADR-0127）、探测点、副本语义全部要过一遍并补测试矩阵（干净态 / 残留态两维 × 三流）。

### 4.3 数据搬迁（DataLocation）

**现状语义**：三分支——目标已有库直接接管；目标空而源有库则源库 `VACUUM INTO` 到目标临时名 → integrity → rename 启用；两者皆无新建。源库**永久保留在旧位置**；密文库搬迁推迟到解锁后补做；全程 SQL 级复制，不搬文件本体，失败清理临时产物。

**WAL 下语义变化**：
- `VACUUM INTO` 语义同 4.1：一致性不变、含未 checkpoint 事务；目标产物（若 delete 事实成立）是干净单文件。
- 旧位置永久保留的源库在 WAL 世界里可能带边车：干净关闭会归并删除，**崩溃残留则旧位置三件套并存**——用户日后去旧位置「手工拷回」时命中 4.6 的丢数据语义（跨项关联，不是本项独立缺陷）。
- 源库以 WAL 形态被打开后 journal mode 已写进文件头：旧位置保留的库从此也是 WAL 库，边车语义跟随到「用户以为早已无用的旧文件」上。

**影响**：
- **用户可见**：搬迁本身三分支语义零改动；风险后置到旧位置残留文件的后续人工处置。
- **数据安全**：低——搬迁机制本身经 `VACUUM INTO` 免疫边车；风险在保留的旧库副本。
- **复杂度**：本项是重裁点中最轻的——搬迁实现可不动，只需把「旧位置残留边车」纳入 4.6 的口径与文档。

### 4.4 忘记口令副本（issue #573 / ADR-0075 决策 2/5）

**现状语义**：解锁屏逃生门——探测确认密文库 → rename `ledger.db` → `ledger.db.bak` 保留为**密文副本**（无密钥不可读，日后想起口令可救回）→ 原位新建明文空库（建连 + 迁移 + integrity）→ 新库建失败尽力把副本改回原位；副本**永不删除**、重置**不需要也无法验证口令**。

**WAL 下语义变化**：
- 残留态命中（上次未干净退出留下 `-wal`/`-shm`）：rename 主文件后，残留边车与**原位新建的明文空库**配对 → recovery 把旧密文库的 WAL 帧（SQLCipher 场景为密文帧）回放到全新的明文库 → 新库损坏，「重置后直接进入应用」承诺被打破【一手】。
- `.bak` 副本缺 `-wal`：副本丢最近已提交事务——逃生门的「数据仍可救回」语义静默缩水。

**影响**：
- **用户可见**：重置后新库进启动失败恢复屏（本该最干净的路径变成故障现场）。
- **数据安全**：逃生门本身变故障点——该路径的设计目标恰是「永不删除、永远可救」，两项变化都朝反方向。
- **复杂度**：低——重置前加「边车归并/清理」一步（对无边车的 rollback 现状是空操作），但必须进测试矩阵（残留态重置）。

### 4.5 启动失败重置（启动失败恢复屏「重置为空库」）

**现状语义**：rename `ledger.db` → `ledger.db.bak` 保留（`.ok()` 容忍不存在，**绝不删除任何文件**）→ 原位新建空库（建连 + 迁移 + integrity）→ 原位换连直接进入应用；启动失败相位连接尚未建立（除占位内存库）。

**WAL 下语义变化**：与 4.4 同构——(a) 残留边车与新空库配对 → 回放损坏；(b) `.bak`（本为「打不开的库留给人救」）缺 WAL 内容。差别仅在触发相位：启动失败常与崩溃相邻，**恰是残留态概率最高的时刻**——风险与场景正相关。

**影响**：
- **用户可见**：重置成功却起不来 / 重置出的空库带脏内容。
- **数据安全**：`.bak` 是最后兜底件，失真即兜底失效。
- **复杂度**：低，与 4.4 共用同一处置（重置前归并边车）。

### 4.6 手工拷库有效性（含外部工具）

**现状语义**：单文件 `ledger.db` = 全部状态；用户随手拷贝自救、网盘/同步工具盯目录、外部 `sqlite3` CLI 直接读库，**应用开/关无差别成立**——ADR-0007「备份 = 文件级快照」与 ADR-0075「文件即真相」的用户侧地基；ADR-0127 的外部工具清单（危险/安全）也建立在单文件上。

**WAL 下语义变化**：
- **只拷主库**：官方原话——已提交事务可能丢失或库损坏【一手】。三种时机里只有「最后连接干净关闭后」成立，而本应用退出路径无显式关库动作（§2 第 4 条），崩溃/强退后**边车残留是常态而非常态**。
- **拷三件套**：运行中无原子性保证，主库与 `-wal` 可能不是同一时点【一手】。
- 外部工具面变化：CLI 对 WAL 库读写会创建/消费边车；ADR-0127 的安全/危险清单要增补边车维度（如：对带边车的活库做文件级操作）。

**影响**：
- **用户可见**：**用户最常做的自救动作（拷贝 ledger.db）变成丢数据动作**——这是全部重裁点里唯一直接命中普通用户日常动作的一项，支持口径、帮助文档、同步工具提示都要重写。
- **数据安全**：用户侧丢数据风险从 0 到有。
- **复杂度**：文档 + 可选的启动期残留检测提示；机制本身（干净关闭归并）见 4.7。

### 4.7 checkpoint 归并策略（含退出时归并保证、边车残留污染面）

**现状语义**：**不存在**——rollback 模式无 checkpoint 概念，库文件的归并（journal 恢复进主库）由 SQLite 按热 journal 自动处理且不留常驻文件。仓内已有的「同步检查点」（sync-engine Checkpoint / `V022`）是业务概念，与 SQLite checkpoint 无关。

**WAL 下语义变化（全部是新决策面）**：
- **归并时机**：默认 autocheckpoint 1000 页、全 PASSIVE、**内联在 COMMIT 路径**执行【一手】——大库上偶发单次提交明显变慢；官方给的减压手段（关自动、挪独立线程）= 新线程 + 新策略面。
- **退出时归并保证**：只有「最后连接干净关闭」才触发最终 checkpoint + 删边车【一手】；本应用 `RunEvent::Exit` 只挂兜底备份、无显式关库（§2 第 4 条），进程结束方式（正常退出时 Drop 是否执行、崩溃/强退）决定残留概率——**要「退出时归并」成为保证，必须新增显式收口（退出钩子里 checkpoint(TRUNCATE) / 关连接），这是新机制**。
- **边车残留污染面**：残留窗口 = 4.1（替换配对）、4.2（swap 配对）、4.4/4.5（重置配对）、4.6（拷库丢失）的**共同放大器**——残留越常态，上面每一项的暴露面越大；`SQLITE_FCNTL_PERSIST_WAL`、只读客户端最后断开等官方列出的残留场景进一步扩大窗口。
- **只读连接的打开条件**（ADR-0117 读连接直接受辖）：只读打开 WAL 库要求边车就绪或目录可写【一手】——既有「写连接先行、读连接随后」的成对次序必须升级为硬约束（写连接负责初始化边车），任何「只读连接先于/独立于写连接打开」的路径都会踩 `SQLITE_READONLY_RECOVERY`/`CANTOPEN`。
- **synchronous 语义联动**：WAL+FULL 才保持断电持久 ACID；WAL+NORMAL 换来性能但牺牲断电持久【一手】——默认值取向是一个新的、用户可感知数据丢失窗口的决策（现状 delete+FULL 无此分叉）。

**影响**：
- **用户可见**：checkpoint 内联造成的偶发提交变慢是**保证会发生**的迟滞（与现状「从未发生过的等待」对照，见 5.3）。
- **数据安全**：残留常态化的放大效应；`synchronous` 取向若为提速选 NORMAL，等于用断电丢提交换性能——必须显式裁决。
- **复杂度**：新增策略面最多的一项——checkpoint 模式与时机、退出归并钩子、残留检测、只读次序硬约束、术语防撞名。

## 5. WAL 后收益重估

### 5.1 #1720 等待优化（`unlock_notify`）在 WAL 下的剩余收益

**现状收益**：救「等锁等到失败」的场景——通知式等待替代 busy 重试轮询。#1720 定案：三档证据（busy 超时 / `database is locked` / 锁持 >1s 探针）3.5 周全零，`wontfix` 关闭，重开成本 = 各 Cargo.toml 加一项 feature。

**WAL 下剩余收益 ≈ 0**：WAL 把 busy 场景收窄到「最后连接清理边车瞬间」「崩溃后首连接 recovery 期间」「写写争用」（单进程单写者 ≈ 无）、EXCLUSIVE locking mode（本应用不用）【一手】——即等待优化的目标场景在 WAL 世界里**比现在更少**。WAL 不但不复活该优化，反而进一步坐实它没有可救的对象。

**结论（明确）**：无论切不切 WAL，#1720 的 `wontfix` 维持，重开判据维持 #1720 定案原文；本票不重开 #1720。

### 5.2 ADR-0117 读路径独立只读连接（双连接模型）在 WAL 下的剩余收益

**关键分层**：双连接治的是**应用层互斥闸门**——写闭包持锁期间读命令无界排队（ADR-0117 背景的结构性问题）；WAL 治的是**文件锁层**——写事务取 EXCLUSIVE 时读连接的有界等待。两层正交：**单连接 + WAL 下，读仍排在应用层写闭包后面**，WAL 对闸门问题零帮助。

**结论（明确）**：双连接模型的收益在 WAL 下**全额保留，不被 WAL 替代、不因 WAL 缩水**——它是结构修复，不是等待优化。WAL 相对**现状**（双连接已落地）的边际收益只剩：

- 消除 ADR-0117 代价 4「提交瞬间 EXCLUSIVE 窗口的有界等待（≤5s busy_timeout）」——**有界、3.5 周零命中**；
- 消除 busy 失败类的**整个类别**（含恢复期间 `SQLITE_BUSY_RECOVERY`、清理边车瞬间 busy——注意这两个新场景本身是 WAL 引入的，净消除量并不等于账面全部）；
- 毫秒级的读写互不阻塞体验增益（现状读已在闸门外，增益仅剩提交窗口内那几毫秒）。

**量化表述**：以「用户可感知迟滞」计，WAL 的边际收益 = 一个**从未观测到**的失败类 + 一个**有界且从未触发**的等待窗 + 毫秒级窗口等待；论证重心若走 (a)，全部筹码都在「未来可能出现」上——这正是触发门要守的「防提前升级」。

### 5.3 反向项：WAL 自带的新迟滞面（UI 优先原则下的对账）

- autocheckpoint 内联 COMMIT 路径，**偶发拖慢单次提交**，官方劣势清单明列【一手】——这是**保证会发生**的事件，只是频率低；
- 现状被质疑的等待（提交瞬间 EXCLUSIVE 窗口）是**有界且从未发生**的（三档零命中）；
- 「UI 使用感受优先」要求对**两类都**提前评估：评估结论是 WAL 把「从未发生过的等待」换成「保证偶发的慢」+ 一条新故障类（旧帧回放）+ 用户日常拷库语义破坏——**净方向为负**。

## 6. 结论：(b) 明确维持现状

### 6.1 触发门是否随「UI 优先」原则改写：**不改写**

- **判据①②维持原文**：仍可检验、仍未命中；且它们是「**引入**」的判据，不是「**评估**」的判据——UI 优先原则要求的前移是「评估先行」，本报告即履行，原则不要求把引入门槛降到「竞争面存在」。
- **观测面已按 UI 优先前移**：#1720 定案已把③（锁持 >1s 迟滞类）归入 ADR-0117 的观测判据——「不等失败、盯迟滞」的前移已经用观测实现，不需要用提前引入 WAL 实现。
- **改写反而更不诚实**：若把①改成「存在竞争面即触发」，判据立即命中、指向引入——但 5.3 证明 WAL 自带一个新的迟滞面，新判据会要求引入一个**自带反例**的方案；判据必须保持「出现 WAL 能净改善的可检验证据」这一形态。
- **②的真实需求（写事务打开期间无界读可用）在本应用不存在**：读已走独立连接、写事务期间读照常服务（ADR-0117 决策 1 已交付该语义的 rollback 版本）。

### 6.2 维持现状的理由（汇总）

1. **边际收益 ≈ 0**：三档证据零命中 + 等待有界（5.1/5.2）；真正的迟滞层（应用层闸门）已由双连接结构性解决，WAL 对它零帮助。
2. **代价落在数据安全核**：7 处重裁点中恢复、忘记口令、启动失败重置、转换/归一化是单向不可再试操作，全部要求新增「边车归并/清理」步骤才恢复既有原子性（§4）。
3. **引入今天不存在的故障类**：旧边车 + 新主库 = 旧帧回放损坏，官方 recovery 无主库配对校验【一手】；且残留态在本应用退出路径下是常态（无显式关库收口）。
4. **WAL 自带新迟滞源与新策略面**：checkpoint 内联 COMMIT、退出归并钩子、`synchronous` 取向、只读打开次序硬约束、术语防撞名（§4.7）——每一项都是持续维护面。
5. **单文件形态是既定产品价值**：文件即真相、手工拷库自救、备份/恢复的心智模型、ADR-0127 外部工具清单，都建立在单文件上；官方自己也明言边车「降低其作为应用文件格式的吸引力」【一手】。
6. **符合触发门的立意**：触发门存在的目的就是防提前升级；在两档未命中、边际收益为零的时刻引入，等于门白立。

### 6.3 若触发门未来命中：开工清单（影响面盘点，非修订草案）

触发门命中并经维护者裁决后，修订草案才起笔；本节先期备齐影响面（票面把「ADR-0007 / ADR-0075 影响面清单」列为 (a) 分支的交付项，此处作为 (b) 结论下「若未来反转结论须付代价」的对照材料提前盘点，属超前材料而非 (b) 所必需）：

- **ADR-0007 影响面**：RestoreSafetyBackup 由裸 `fs::copy` 改为「先归并再拷 / 连带三件套」；`replace_file` 替换连带删同名 `-wal`/`-shm`；journal mode 每开重申收口；`VACUUM INTO` 输出模式实测（决定备份 zip 与恢复校验是否要动）；备份一致性语义（决策本体）不变。
- **ADR-0075 决策 7 影响面**：「模式随文件走」扩义为「加密状态看主文件头、持久状态随三件套走」；转换 swap 前边车归并；`.bak` 副本语义补 WAL 内容（先归并再 rename）；`-shm` 明文元信息的威胁模型定性；`sqlcipher_export` 带残留边车源库的实测。
- **ADR-0127 影响面**：归一化复用转换链故同权承担 swap 边车处置；外部工具清单增补边车维度。
- **ADR-0117 连带**（如修订决策 6，只动触发条件与 WAL 边界表述，决策 1–5 与双连接模型不动，除非论证确需并逐条列出）：只读连接先行次序升级为硬约束；代价 4（提交窗口等待）随 WAL 消失须改写。
- **新机制面**：建连收尾 `journal_mode=WAL` 幂等重申、退出归并钩子、checkpoint 策略与 `synchronous` 取向、残留检测/提示、术语防撞名。
