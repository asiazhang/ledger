# ADR-0117: 读路径独立只读连接（路线 B）——读走独立连接 + busy_timeout，长写事务不再挡读

- 状态：已接受（spec #1274 决策 8「路线 B 另案记账」所立；本 ADR 只立方向与协议，实施另票）
- 日期：2026-09-13
- 作者：Ledger 项目
- 关联：**修订 ADR-0069 决策 1**（单连接形态 → 写连接 + 固定只读连接两连接；其否决 tokio-rusqlite 预留的「出现连接池等真实多连接需求可重议」口子由本 ADR 行使，0069 状态行已加修订指针）；**推翻 issue #147 方案 b 否决中的「第二只读连接」部分**（WAL 部分的否决维持，见「WAL 边界」）；ADR-0104（读入口仪式收敛，不推翻不修订正文——`read_entry` 签名与仪式语义原样，实施票更替其消费的连接句柄）；ADR-0075（加密基座：决策 3/5 是本决策口令获取协议的直接依托，决策 6/7 转换与备份语义在读连接下不变）；ADR-0080（原位重引导，换连的执行机制）；ADR-0114（跨账本只读聚合，「各自只读连接」的场景先例）；ADR-0009（连接级耗时 hook 与单连接形态的历史出处）；机制术语「写连接 / 读连接」以本 ADR 为唯一解释处，不进业务词汇表（ADR-0104 决策 8 先例：跨域基础设施机制不属任何自然域；spec #1274 决策 11 同此判定）

## 背景

现状是**单连接形态**（ADR-0009 所记、ADR-0069 形状乙保留）：一条 SQLite 连接包在共享互斥锁里（基础设施 crate db 区 `DbState`），读与写锁同一把——壳层读入口 `read_entry`（infra crate shell_support 区，ADR-0104）与统一写入口 `db::write` / `write_entry` 拿的是同一个句柄。这条连接同时兼任「SQLite 单写者互斥」与「读访问闸门」：写闭包持锁多久，所有读命令就等多久，且这个等待**无界**——它等的是应用层互斥锁，不是 SQLite 文件锁，没有超时语义。

既有性能防线（ADR-0067 余额缓存、ADR-0068 阈值门禁）防的是「读查询本身慢」，防不了「读被写者闸门挡住」这个结构问题；ADR-0069 决策 4「慢闭包不得进锁」只靠注释与评审兜底，spec #1274 核实的现场（标的信息同步整段持锁数分钟、读命令全部排队）正是这类退化。批量导入、多端同步重放、定时追补等写入面同样存在长事务的结构性可能——数据量增长后任何一条变长，挡的都是全部读。

两道既有裁决挡在路上，须显式处理：

- **issue #147**（标的全量同步假死，已退役）：当年修复选了方案 a（收窄锁粒度），显式否决方案 b「WAL + 第二条只读连接」，注明「只有当收窄后仍有可感知卡顿时才另行考虑」。
- **ADR-0069**：否决 tokio-rusqlite，同时保留口子——「除非上游支持项目现行 rusqlite 版本，或项目出现连接池等真实多连接需求，不再重议」。

spec #1274 以路线 A（锁跨度结构化收窄 + 守门）修复当下缺陷，并把路线 B（读彻底不经过写者闸门）另案记账——即本 ADR。两案关系：路线 A 收窄**写侧**的持锁跨度，解决「写路径纪律退化挡读」；路线 B 把**读侧**移出闸门，解决「任何长写事务挡读」——后者是前者的结构性兜底，也是本 ADR 的全部内容。

## 决策

### 1. 读路径改走独立只读连接（路线 B）

读命令不再锁写连接：另建一条**读连接**，指向同一库文件、以只读方式打开、挂 `busy_timeout`；写路径保持既有单连接与写者闸门原样（该连接此后称**写连接**，即词汇表与既有文档的「主连接」）。

连接形态由「一条互斥锁内的读写共用连接」变为**两条固定连接**：写连接维持单写者互斥（`db::write` / `write_entry` 语义不变）；读连接只服务 `read_entry`。rollback journal 模式（现状，本决策不引入 WAL）下两连接的并发由 SQLite 文件锁仲裁：

- 写事务进行中（RESERVED 锁）读连接照常读——**长写事务不再挡读**；
- 挡读收窄为写事务取 EXCLUSIVE 锁的窗口——正常事务在提交瞬间，特大事务中途落盘（cache spill）时短暂提前；读连接在 `busy_timeout` 内等待——等待有界，窗口异常增长时读命令失败可见（码化错误），不再无界挂起。

### 2. 密文库每条连接的主口令获取：换连点同源成对，不新增口令来源

每条连接独立完成密钥注入（建连收口单点的 `PRAGMA key`，ADR-0075 决策 3：SQLCipher 按默认 KDF 参数由主口令派生密钥）。读连接的口令来源**收口为换连点在场且已验证的口令**，与写连接同源成对：

- **手输解锁**：解锁命令面传入的主口令，写连接与读连接先后以同一口令打开；
- **自动解锁**：钥匙串缓存读取（infra crate boot 区 passphrase_cache，发布构建先过 LocalAuthentication 生物门）得到的口令——读取发生在解锁屏、用户在场，读连接随写连接同刻消费同一口令，**不在读连接建连时独立触发钥匙串读取**（避免生物门在非解锁窗口弹交互，自动轮询不读钥匙串的既有纪律不因此破例）；
- **明文库**：无口令，读连接与写连接同形打开。

**会话信封（sync-engine crate trigger 区 SessionEnvelope）职责不变**：它是同步轮次的封包形态记忆（ADR-0098），不是口令缓存，不承担读连接的口令来源；读连接口令的会话内可用性由换连点直接持有。改口令 / 关闭加密后经原位重引导落解锁屏重新解锁，读连接随写连接以新口令（或明文）成对重建——口令轮换对两连接对称，无中间态。

### 3. 四条路径的换入/换出协议：读连接一并纳入，成对、单点、fail-closed

**通用协议**：读连接与写连接同用「共享句柄 + 互斥体内槽替换」形态（`DbState` 既有 Arc 语义，ADR-0080：换入后壳层、HTTP 壳、调度线程已持有的克隆同步可见）；换入/换出**收口在既有换连单点**（引导序列的连接换入步骤与解锁/重置的 `resume_business_surface` 编排），扩展为成对换连；门翻转次序 fail-closed 不变——进入锁定/失败先立门再换出（换连窗口内业务 IPC 已被拦截），回到就绪先换入真实连接再开门；锁定/失败期间两连接同为占位内存库形态，门禁拦截下不被触达。

| 路径 | 换出（旧读连接） | 换入（新读连接） | 失败语义 |
|---|---|---|---|
| **加密解锁**（启动探测落解锁屏 → 手输/自动解锁成功） | 解锁前无真实读连接（占位形态），无需动作 | 口令验证通过（`unlock_db_file` 打开成功）后，与写连接以同一口令**成对原位换入**，随后门翻转、业务恢复 | 口令错误两连接都不换入，保持占位、锁定门保持立起——fail-closed，无限重试（ADR-0075 决策 5 修订口径） |
| **恢复**（Restore，backup crate engine `restore_db_from` 文件替换） | 替换库文件成功后**立即换出（占位化）**：旧读连接指向被替换前的旧文件（rename 后仍指旧 inode），继续读会给出陈旧数据——换出不得等到重启 | 前端触发原位重引导（ADR-0080），引导序列按新库文件成对换入；恢复期间读被占位挡住的窗口 = 既有「恢复持写连接锁」窗口的自然延伸 | 恢复失败原库原样保留，旧读连接不换出（回滚无痕）；重引导读连接建连失败 = 引导失败，落失败恢复屏 |
| **数据搬迁**（DataLocation，「写意图 + 下次启动生效」，引导内核执行搬迁；密文库解锁后补做） | 运行窗口内搬迁不动活动库，两连接**原地不动**；补做搬迁成功后同样由原位重引导接管 | 重引导时按目标位置成对换入；搬迁进行时处于引导窗口，无旧读连接存活 | 补做搬迁失败不阻断解锁，应用继续以当前位置运行（既有语义），读连接随现状换入；重引导失败落失败恢复屏 |
| **加密转换**（开启/关闭/改口令，整库转换 + 原子替换，ADR-0075 决策 6） | 转换执行期间读连接**照常可用**（读旧库，转换连接以 `busy_timeout` 5s 容让并发，既有语义）；替换成功后立即换出（与恢复同款 inode 语义） | 原位重引导成对换入；改口令场景旧读连接凭旧口令打开旧 inode，不受新口令影响——换出在替换后立即执行，不跨窗口 | 转换失败原库原样保留（不存在半加密状态），读连接不换出；重引导失败落解锁屏/失败恢复屏 |

同族路径（忘记口令重置、启动失败重置、账本切换）全部经既有换连单点或原位重引导，读连接按同一通用协议成对跟随，不逐路径另立协议。**读连接缺失期间读命令报码化错误，不静默回落写连接**——回落会让读路径重新经过写者闸门并绕开只读约束，本决策的守护目标随即失效。

### 4. 连接生命周期单点收口

- **建连**：建连收尾单点（密钥注入 → 外键 → 耗时 hook）扩出只读形态：只读 flags、`busy_timeout` 取值与既有转换连接的 5s 同源收口，不在调用点散布；
- **换入/换出**：收口第 3 条所述既有单点，禁止任何路径手搓第二条连接绕开收口（实施票以源扫描/结构守门钉住，对齐 ADR-0104 决策 6 的守门纪律）；
- **失效/关闭**：随托管形态——占位化即换出，不新增独立生命周期路径；备份/恢复、加密转换、搬迁路径内已有的临时第二连接（生命周期操作，spec #1274 Out of Scope 既有判定）不属本决策管辖，形态不变。

### 5. 备份不受影响的依据

备份产物由 backup crate engine 的 `VACUUM INTO` 从**写连接**生成（SQL 级一致快照），不是拷贝活动库文件——它看到的是执行时点的已提交状态，读连接的存在不改变其前提与一致性语义；自动备份调度线程既有形态（5s 超时获取写连接）不变。恢复安全备份（RestoreSafetyBackup）是文件级拷贝，发生于恢复持写连接锁的静止窗口内，读连接只读不改文件内容，不受影响。`VACUUM INTO` 继承源库加密与密钥、备份跨设备可移植性（ADR-0075 决策 3/7）在读连接下同样不变。

### 6. WAL 边界：本决策不含 WAL、不含读连接池

- **不做** WAL，**不做**读连接池。只读连接已把「长写事务挡读」消掉；剩下的提交瞬间等待由 `busy_timeout` 有界化。
- **WAL 是同一路线的加强版**：读走快照、写提交不再要求主文件排他——连「读到提交都不让路」的最后一丝等待也消失（spec #1274 决策 8 语）。代价是库文件形态改变（`-wal`/`-shm` 边车文件）：搬迁、恢复、忘记口令副本、启动失败重置等文件级操作的语义、手工拷库的有效性、checkpoint 归并策略都要重新裁决，ADR-0075 决策 7「模式随文件走」的简单性受损。
- **升级触发条件**（可检验，防提前升级）：①真实出现长于 `busy_timeout` 的写事务或提交窗口，读命令在等待窗内实际失败且用户可感知；②出现「写事务打开期间要求无界读可用」的真实需求。触发即修订本 ADR 单独裁决 WAL；未触发不引入。读连接池不设触发条件——单写多读的桌面场景下「固定一条读连接」已覆盖全部已知读频度，池化属为不存在的问题引入参数面。

## 与既有裁决的关系（哪条修订、哪条推翻）

- **issue #147：部分推翻。** 其方案 b「WAL + 第二条只读连接」的整体否决中，「第二条只读连接」部分由本 ADR 显式推翻——当时否决的语境是全量同步假死的当下修复，收窄锁粒度（方案 a）正确且已交付；但方案 b 被一并否决后，预留的另行考虑条件（「收窄后仍有可感知卡顿」）在结构性问题（读侧无闸门豁免）面前过窄。本 ADR 记录：长写事务挡读不是「卡顿程度」问题，是「读要不要经过写者闸门」的结构问题，触发场景由可感知卡顿改为写入面的结构性存在（spec #1274）。#147 的 WAL 否决部分**维持**（见「WAL 边界」升级触发条件）；其收窄锁粒度交付与全部行为语义不变，路线 A（spec #1274）是其纪律的守门化延续。
- **ADR-0069：修订决策 1，行使否决口子，其余原样。** 决策 1「单连接 + 互斥锁形态原样保留」中的「单连接」由本 ADR 修订为「写连接 + 固定只读连接」两连接固定形态；「不做连接池、不做专用线程」**维持**（本决策不是连接池）。其否决 tokio-rusqlite 时预留的「出现连接池等真实多连接需求可重议」口子由本 ADR 行使：真实多连接需求（读路径独立）已认定，重议结论是**自建固定只读连接**——该否决的其余理由（上游版本配对僵局、胶水无能力增益）不变，故驱动仍不引入。决策 2–5（`run_db` 阻塞线程池、span 归因、慢闭包纪律、接缝契约零改动）全部原样。
- **ADR-0104：不推翻、不修订。** 读入口的仪式收敛（锁仪式单点、失败映射、span 归因、线程池投放）语义原样；`read_entry` 签名收「连接句柄」，句柄类型不变（共享互斥锁内的 `Connection`），变的只是**传入的句柄指向读连接**——实施票完成更替后，组合拓扑（`run_db` ∘ lock）与两壳调用面零变化，既有豁免清单（backup 命令等）语义照旧。
- **ADR-0075：兼容，协议依托。** 决策 3（钥匙串只缓存口令、密钥由口令派生）与决策 5（解锁推迟打开库、fail-closed 门禁）是第 2、3 条协议的直接依托；决策 6（整库转换原子替换）与决策 7（备份随文件走）在读连接下语义不变。
- **ADR-0080：兼容。** 原位重引导是恢复、搬迁、转换三条路径换连的执行机制，读连接并入其引导序列的连接换入步骤，fail-closed 次序不变。
- **ADR-0114：同方向先例。** 跨账本投资汇总「各自只读连接」聚合（已接受、实施未落地）是只读连接的场景先例；本 ADR 把只读连接从聚合场景的特殊形态升为读路径的统一形态，其「密文本必须已解锁才计入」边界与本 ADR 的口令协议同构（未解锁 = 无口令可用 = 不建真实读连接）。

## 否决（防重复提案）

- **读写锁（`RwLock` 替代互斥锁）**：否决。①`rusqlite::Connection` 只实现 `Send` 没有 `Sync`（spec #1274 Further Notes 核实），`RwLock<T>: Sync` 要求 `T: Send + Sync`，单连接并发读在类型层就不成立；②退一步改多连接 + 读写锁，读多时写饥饿——写路径要过的闸门反而更堵；③它没有把读移出闸门，「读等写」仍无界，症状由持锁时长决定、与锁的类型无关。本质：问题在「读写共用同一条连接」，不在应用层锁的形状。
- **连接池 + WAL（一步到位）**：否决。①一次性引入 WAL 的全部文件形态代价（见「WAL 边界」）而当前无 WAL 级并发需求；②池化参数（池大小、复用策略、写连接独占性）在单写多读的桌面场景无收益，徒增故障面与排查成本；③两件事捆在一起会互相污染裁决——WAL 有可检验的触发条件，池化没有。WAL 保留为升级路径；连接池无限期不设。
- **第三方异步驱动（tokio-rusqlite）**：否决，ADR-0069 在案。上游支持滞后于项目现行 rusqlite 版本，为异步换降级方向颠倒；其本体是「专用线程 + 通道」胶水，无能力增益；且异步驱动解决「调用线程占用」，与「读写文件级分离」正交，替代不了本决策——本 ADR 落点在形状乙之上叠加，不重开该案。

## 代价

1. **每账本连接数翻倍**（内存 + 文件句柄）：桌面单账本规模可忽略；多账本场景本就按每本连接计（ADR-0114）。
2. **换连面翻倍**：加密解锁、恢复、搬迁、加密转换四条路径（外加重置/切换账本同族路径）都要成对换入换出，漏一半即「读连接指旧库」的陈旧读——靠第 4 条单点收口与实施票的接线负向守门（删除读连接换入调用 → 测试变红，ADR-0087 断言强度）兜底。
3. **只读约束运行期暴露**：读路径若混入隐藏写（隐式 PRAGMA 写、写盘临时表等）会在只读连接上报只读错误——「读路径无写」从纪律变成运行时约束，实施票需甄别存量读路径后收口。
4. **提交瞬间等待有界但非零**：rollback journal 模式下读在写事务 EXCLUSIVE 窗口（正常在提交瞬间，特大事务中途落盘时短暂提前）于 `busy_timeout` 内等待；窗口异常增长时读命令失败可见（码化错误），不无界挂起。
5. **口令在场连接数 +1**：读连接在进程内持有主口令（与写连接同权同源），钥匙串缓存与会话信封职责不扩，但「口令在场的连接」从一条变两条。

## 后果

- 长写事务（批量导入、多端重放、定时追补、标的信息同步等）不再挡读：读可用性从「等写者闸门、无界」变为「SQLite 文件锁仲裁 + 提交瞬间有界等待」。
- 本 ADR 只立方向与协议；实施另票，范围至少含：`read_entry` 连接句柄更替、建连单点只读形态、四条路径成对换连接线、守门与「删除即变红」负向判据、存量读路径只读甄别。
- 写路径、备份、同步、导入等全部既有入口的对外行为与契约零变化；数据库连接与锁不属任何业务域词汇表（spec #1274 决策 11），机制术语「写连接 / 读连接」以本 ADR 为唯一解释处。
