# ADR 0100: 启动期 schema 漂移守卫——init_db 尾部内存参照库方向性 diff，漂移报 boot.schema-drift

- 状态：已接受（grilling 定稿，2026-09-10）
- 日期：2026-09-10
- 作者：Ledger 项目
- 关联：#971（问题实证与评估，本决策来源）；#272（发布约定：未发布迁移允许就地修改——守卫防护的工作流）；#601/#602（启动失败恢复通道——守卫失败的承接面）；#963（接线型 ticket 负向判据惯例）；ADR-0087（测试三层权威——守卫测试断言强度）；ADR-0050（错误码化只增不改）；ADR-0018/ADR-0089（数据位置与多账本——db-reset.sh 补口的事实依据）；ADR-0027（V005 搜索索引移除——遗留对象容忍的依据）；ADR-0068/ADR-0009（性能门槛与观测线——守卫成本归属）

## 背景

`rusqlite_migration` 的迁移裁决只比较 `PRAGMA user_version`：`goto()` 在 `target == current` 时直接返回 Ok，不校验 schema 内容。本仓发布约定（#272）允许对**未发布迁移就地修改**，这对已跑过该迁移的库是静默失效的：文件改了、版本号没变、重跑不触发。#971 实测踩中：开发库 `user_version = 22`（与迁移序列长度一致，应用判定「已最新」）但 `sync_parked_ops` 缺 V021 声明的 `park_params` 列，应用正常启动，直到挂起队列读写才报 `no such column`。同类事故已有先例（2026-09-08 `merchant_id` 缺失）。

既有防线全部落空：迁移测试明示「历史库升级路径不测」；启动失败恢复屏（#601/#602）只接「库打不开」（`to_latest` 报错 → 失败门），本场景 `to_latest` 正常返回，恢复屏不触发。

## 决策

1. **守卫接缝 = `init_db` 尾部单点**：`to_latest` 返回 Ok 后执行 schema 一致性校验，漂移即返回码化错误。全部生产建连路径（明文启动、解锁换连、重置、备份恢复、加密转换、checkpoint 重建）统一收口 `init_db`，守卫一处接线零遗漏；密文库解锁路径的漂移在解锁屏按码呈现，逃生门（忘记口令/从备份恢复）既有可达，无需新通道。

2. **检测机制 = 内存参照库方向性 diff**：守卫时从零迁移一个内存参照库（直接调 `migrations().to_latest()`，不经 `init_db`，避免递归守卫），与真实库对比：
   - 对象清单（`sqlite_master` 的表/视图/索引）：**参照有而实际缺 = 漂移；实际多出 = 容忍**。方向性是硬约束——跑过 V005 的老库合法残留搜索索引对象、`sqlite_sequence` 等参照库没有的对象，非方向性比对必然误报（ADR-0027 语义：新库不再产生、存量不清理）。
   - 列集：各表 `PRAGMA table_info` 列集，同方向性。
   参照库由迁移链自动构建，零手工清单维护，迁移链演化时参照自动跟随，可捕获任意漂移而非仅清单内列。

3. **失败语义 = 新独立码 `boot.schema-drift`**：错误构造器 + 错误模板同步（ADR-0050 只增不改），文案「数据库结构异常，可从备份恢复或重置」。不复用 `boot.db-unreadable` 单码：漂移库**打得开且数据完好**，恢复通道中「从备份恢复」应作为用户首选动作呈现，与「库不可读」（重置优先）的处置顺序有真实差异，前端按码区分文案（#994）。

4. **已知边角（v1 接受）**：漂移库的备份产物可能同样漂移（漂移发生后自动备份跑过），恢复该备份后守卫在原位重引导时自然再判，仍漂移则回恢复屏（重置通道始终可达）。v1 不在恢复路径前置校验备份文件——对 zip 内库文件建只读连接校验 schema 并处理加密备份口令交互，复杂度不成比例。

5. **脚本补口（#993）**：`db-reset.sh` 解析 `data_location.json`（与 `data_location::configured_intent` 同语义）覆盖自定义数据位置，消除「就地修改迁移后受影响库不知在哪」的人工记忆依赖。

## 备选与否决

- **复用测试签名清单做启动校验**：`migrations.rs` 的签名表/列清单提为常量供启动消费。实现最薄，但清单需人工双维护，且只覆盖清单内对象——#971 的 `park_params` 恰是 V021 后补列、不在清单内，该机制对本次事故无效。签名清单留在测试层做测试自己的断言，两处不合并。
- **构建期指纹哈希**：构建时对参照库 `sqlite_master` 哈希存常量，启动时比对。哈希对「多出对象」无法方向性容忍，老库合法残留直接误报；要解决须回到对象清单，绕回方案 2。
- **仅启动路径 / 仅 debug 构建守卫**：恢复路径恰是「库可能被外来文件替换」的入口（备份恢复、加密转换产物），不守卫留洞；debug-only 使 dev/prod 行为分叉。守卫成本 ms 级，全额覆盖。
- **恢复路径前置校验备份文件**：体验更好但恢复路径显著增重（见决策 4），v1 不做；守卫在恢复后再判已保证不静默带病。

## 影响

- 守卫上线后，「就地修改未发布迁移 → 存量库静默带病」的事故类（#957、#971）在启动期确定性拦截，失败经既有恢复通道（重置/从备份恢复）承接，不再延迟到业务写路径。
- 每次建连增加一次内存参照库构建（22 个 DDL + 种子，ms 级）：属启动路径合法慢操作，ADR-0068 判据明文不含启动迁移，不设门槛；受 ADR-0009 100ms SQL 观测线约束即可。
- 词汇落数据文件域：`CONTEXT-backup-datafiles.md` 新增 Schema 漂移守卫词条，「启动失败恢复」词条判定来源扩写。
- 发布边界：不修改迁移、数据模型与既有错误码，新增码符合「只增不改」；无 schema/契约破坏。
- 落地：#992（守卫本体 + 测试）、#994（前端文案，blocked by #992）、#993（脚本补口，独立）。
