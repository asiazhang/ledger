# ADR-0027: 统一模糊搜索语义与 Rust 全量扫描实现

- 状态：已接受（修订 ADR-0004：FTS5 索引及其一致性机制整体移除）
- 日期：2026-09-17
- 作者：Ledger 项目
- 关联：issue #195（规格）、issue #196（全局搜索落地）、issue #198/#199（拼音可搜下拉）、issue #200（文档收口）

## 背景

ADR-0004 以 FTS5 虚拟表实现交易模糊搜索（整词 + 右锚前缀 + 拼音首字母整串），配合「触发器入队 → 后台定时刷新 → 启动对账」的一致性机制。两处体验与维护问题推动重新设计：

1. **语义缺口**：用户输入 `wy` 搜不到备注含「万科物业」的交易——现有实现只支持整词与右锚前缀，不支持跳字的子序列匹配；而跳字子序列恰恰是用户对「模糊搜索」的直觉预期。
2. **缓存一致性负担**：倒排索引与主表天然异构，触发器、重建队列、后台线程、启动对账、stale 标志整套机制只为「让索引追上主表」，仍存在分钟级不可搜窗口，是一类持续产生 bug 的来源。

## 统一模糊搜索语义规格（前后端共同契约）

> 输入按空白切词，词条之间 AND；每个词条对每个字段判定——
> **命中 = 原文连续子串（大小写不敏感）∨ 词条是该字段拼音首字母串的子序列（大小写不敏感）**
>
> 首字母串生成规则：中文字取拼音首字母、ASCII 字母/数字小写原样保留、标点与空格跳过（「ABC银行」→ `abcyh`）；多音字按前字规则修正（「银行」→ `yh`）。

混合输入（如「招zsyh」）无需特判：含汉字的词条对纯 ASCII 首字母串的子序列匹配必然失败，自然落到原文子串路径。该规格同时约束全局搜索（Rust 实现）与拼音可搜下拉（前端实现，issue #198/#199），语义只存在于这一份规格中。

## 决策

1. **全局搜索弃用 FTS5，改为 Rust 全量扫描**。搜索时 SQL 取候选（非删除交易的备注 + 转出账户名，金额/日期过滤仍在 SQL 层走既有 B-tree 索引），Rust 内存中按统一语义契约逐条过滤，按交易日期降序排序后分页。
2. **子序列匹配与首字母生成收口为纯函数**（`commands::search::text`），带边界单测；前端以 pinyin-pro 各自实现同一规格，接受生僻多音字的字库级分歧，不为字面一致耦合数据形状。
3. **连带移除整套索引机制**：`search_transactions` 虚拟表、`search_reindex_queue`、三个入队触发器、后台定时刷新线程、启动对账、搜索结果 `stale` 标志（`TransactionSearchResult.stale` 字段随模型一并删除，前端「索引更新中」提示移除）。
4. **SQL 变更不走「追加 drop 迁移」**：明确不考虑旧库兼容，原 V005__search_index.sql 迁移文件自迁移序列整体移除（后续迁移文件名不变，序列号不回填；`user_version` 按序列位置计数）。旧库三种情形的处理（均不属迁移，避免 user_version 语义纠缠）：
   - **user_version 大于当前序列长度**：打开时被 rusqlite_migration 拒绝（DatabaseTooFarAhead），需重置或手动校正 user_version；
   - **能打开的旧库/旧备份（user_version ≤ 序列长度）**：残留 FTS 对象不做启动幂等清理、也不做单独 drop 迁移——issue #197 将 FTS5 机制完整移除、维持「不考虑旧库兼容」立场；app_settings 建表迁移可能被位置语义跳过，读侧 `settings::get` 缺表返回默认值、写侧 `settings::set` 就地建表自愈（均有单测），升级路径以 `db::tests` 测试为准。
5. **搜索命令对外 API 形状不变**（参数、分页语义），仅排序语义由 bm25 相关度改为交易日期降序（对外可见的行为变更，属规格预期）；写入路径立即可搜，无任何时效性容忍。唯一例外：返回结构中的 `stale` 字段属 #195「连带移除」明列项（索引机制消失后无滞后可言），其删除优先于「返回结构保持现状」的一般性表述，前端「索引更新中」提示同步移除。

## 理由

**为什么 FTS5 做不到子序列**：倒排索引只能回答「哪个文档包含完整词条 T」与「以 T 开头的词条」（右锚前缀靠 B-tree 有序区间）；子序列命中的键集合（`wkwy`、`wxy`、`awya`…）不可枚举、无字典序区间性质，且 MATCH 语法没有「有序 + 间隔不限」的位置算子（短语要求紧邻、NEAR 无序且限窗）。逐字符分词 + AND 会引入海量无序误报。子序列语义与倒排索引根本不兼容——编辑器模糊查找器（fzf 等）均采用线性扫描即为此理。

**为什么全量扫描可接受**：个人账本量级下实测 10 万条约 90ms/次、MB 级内存，远低于感知阈值；换来的是零一致性机制、零不可搜窗口、代码面大幅缩小。`LIKE '%w%y%'` 与自定义 SQLite 函数虽语义可行，但性能与全量扫描同量级（前置通配使索引失效）、不提供匹配位置信息、无法与前端共享实现，故不采用。

**排序改日期降序**：与交易列表心智一致（最先看到最近的匹配）；bm25 相关度排序随 FTS5 一并消失。

## 后果

1. 备注与账户名无索引，搜索为 O(全库) 扫描——若未来数据规模或匹配复杂度超出预期，需重新评估（当前不预留索引层逃生舱）。
2. 可搜索范围维持历史收窄语义不变：备注 + 转出账户名；分类名、转入账户名不搜。
   > 后续扩展（issue #193 / ADR-0028）：商户名（Merchant）纳入可搜索范围，匹配语义与本规格一致；商户名与账户名同款即时读取，软删商户历史交易仍可搜、改名即刻生效。
3. 下拉拼音可搜（issue #198/#199）复用本规格，实现载体为前端纯函数 + 薄封装选择器，范围边界（实体下拉 vs 枚举/币种下拉）见界面交互域「拼音可搜下拉」。

## 修订记录

- **2026-08-31（原 ADR-0043 并入，该文件已删除）：候选处理流式化，内存 O(1)。** `query_all` 一次性物化全部候选改为 `query_map` 游标逐行读取、逐行按统一语义契约过滤、命中即计数 `total`、仅物化当前页条目。语义、对外 API、排序（日期降序）、分页与 `total` 精确性全部不变。实测（10 万笔、release）：物化与流式耗时无差异（约 110–130ms，瓶颈在拼音计算与 SQLite 取行），内存峰值 64.8MB → 15.9MB（50 万笔 309.5MB → 63.5MB），流式内存不随数据量增长。全遍历本质不变：子序列语义与倒排索引不兼容，仍不预留索引层逃生舱。
- **2026-09-04（V018，issue #492 / 父 #489 B3）：搜索取行两段式——正式启用索引层逃生舱。** 50 万笔账本下备注拼音搜索实测 2932ms（perf-bench #1），超出感知阈值，后果 #1「不预留索引层逃生舱」的实现条款被实测推翻并正式启用（**子序列语义与倒排索引不兼容的结论不变，FTS5 仍排除**）。实现形态：① 备注拼音首字母冗余列 `note_pinyin`（小写，V018），Writer 接缝同写维护、存量行搜索时惰性回填（列缺失时现算兑底，语义不受回填进度影响）；② 两段式取行——第一段沿搜索覆盖索引 `idx_transactions_note_search`（列表序 + 最小匹配列，partial WHERE is_deleted=0）index-only 流式匹配，仅当前页 id 回表取展示列；③ 账户/分类/商户侧口径改由小参考表字典在 Rust 层判定（50 万候选流上 JOIN 即取行主要成本，实测 25ms → 1170ms），字典每次搜索新建，改名即刻生效语义不变。匹配语义、对外 API、排序、分页与 `total` 精确性零变更。实测裁决（spec Q14-a）：50 万笔 release bench p95 154ms（2932ms → 154ms，达标 ≤200ms），进程内候选缓存无需追加；若未来回归超标，候选缓存（id+拼音串，写后脏标记、惰性重建）为后续可逆手段。
- **2026-09-04（issue #493 / 父 #489 B4）：门禁首跑实测 CI 口径超标，以分项阈值处置；候选缓存手段仍保留预留。** 性能门禁（ADR-0068）首跑（run 33867886806）实测：本搜索在 perf-bench CI（ubuntu-latest、50 万笔 seed 42、iterations 20）下 p95 = 313ms，超默认判据 200ms——上一条修订记录的「实测裁决 p95 154ms 达标」系本地 release 口径，CI 单核性能约为其一半，门禁首跑拦截的正是这一口径差异。处置经权衡后**不启用**上文预留的进程内候选缓存：真实用户设备（本地 release 154ms）本就达标，超标仅是 CI 验收环境画像，为验收环境支付数十 MB 常驻堆内存的代价不成比例；改为门禁分项阈值（ADR-0068：本基准项 400ms，与 CI 实测余量约 1.28×，同其它项对默认线的余量同量级）。候选缓存手段仍保留预留：若未来低端设备实测超分项线，再评估进程内数组或本地文件 + mmap 形态（页缓存可回收）。
