# ADR-0027: 统一模糊搜索语义与交易搜索实现

- 状态：已接受（取代已删除的 ADR-0004；并入已删除的 ADR-0043；正文已按现行态收敛）
- 日期：2026-09-17（现行态收敛：2026-09-29）
- 作者：Ledger 项目
- 关联：#195（规格）、#193（商户纳入，ADR-0028）、#196–#200（首版与拼音可搜下拉）、#492/#515（覆盖索引与 SQL 下推）、#1718/#1725/#1728（语义分家与迁移纪律定稿）、#1885（购买项纳入，ADR-0138）

## 背景

ADR-0004 以 FTS5 虚拟表实现交易搜索，配套触发器、重建队列、后台刷新、启动对账与 `stale` 标志，暴露两类结构性问题：

1. **语义缺口**：用户输入 `wy` 搜不到「万科物业」——倒排索引只支持整词与右锚前缀，不支持跳字子序列匹配。
2. **一致性负担**：倒排索引与主表异构，整套同步机制只为追平主表，仍留有分钟级不可搜窗口，是持续产生缺陷的来源。

推翻 FTS5 后，两项实证又修正了后续演进：① 50 万笔账本下 Rust 内存全扫 CPU 耗时超阈值，需转入覆盖索引 SQL 下推；② 几十万行交易流水上拼音子序列区分度崩塌，搜索语义需按候选集量级分家。

## 统一模糊搜索语义规格（前后端共同契约）

> 输入按空白切词，词条之间 AND，字段之间 OR；每词条对每个字段判定——
> **命中 = 原文连续子串（大小写不敏感）∨ 词条是该字段拼音首字母串的子序列（大小写不敏感）**
>
> 首字母串生成规则：中文字取拼音首字母、ASCII 字母/数字小写原样保留、标点与空格跳过（「ABC银行」→ `abcyh`）；多音字按前字规则修正（「银行」→ `yh`）。

- **混合输入无需特判**：含汉字的词条对纯 ASCII 首字母串的子序列匹配必然失败，自然落回原文连续子串分支。
- **实现归属**：后端纯函数收口于 `ledger-transaction` 的 `shared::search_text`，前端以 `pinyin-pro` 独立实现同规格，接受生僻多音字的字库级分歧，不为字面一致耦合数据形状。
- **按候选集量级分家（#1728 语义契约定稿）**：
  - **小集合字典**（前端拼音可搜下拉、商户/保司管理过滤、后端标的搜索 ADR-0037）：保留完整双分支（原文子串 ∨ 拼音首字母子序列）。
  - **大集合流水**（交易搜索 `TransactionSearch`）：收窄为**纯原文连续子串**。几十万行候选集上，拼音子序列（如 `zs` 命中一切首字母含 `z…s` 序的条目）噪音随数据量线性放大、区分度崩塌。

## 决策

1. **交易搜索命中面与行为契约**
   - 可搜范围：**备注 + 转出账户名 + 商户名（ADR-0028）+ 购买项名称（ADR-0138）**；分类名、转入账户名不搜。
   - 软删交易及软删账户/分类被排除；软删商户的历史交易仍可搜；账户名与商户名即时读取、改名即刻生效。
   - 结果按**交易日期降序**服务端分页（ADR-0008）；写入立即可搜，无任何时效性容忍（原 FTS5 整套索引机制与 `stale` 标志移除）。

2. **交易搜索实现形态：覆盖索引 SQL 下推两段式**
   - **第一段（筛选与计数）**：以 `INDEXED BY` 钉定搜索覆盖索引 `idx_transactions_note_search`（列表序键 + 最小匹配列，partial `WHERE is_deleted = 0`）做 index-only 全扫，直接按列表序产出且无临时 B-tree。
     - 备注原文在 SQL `WHERE` 以 `LIKE` 匹配（`%`/`_`/`\` 经 `ESCAPE '\'` 按字面转义）；
     - 账户名与商户名由每次搜索新建的小字典在 Rust 侧预判命中 id 集合后下推 `IN`；
     - 购买项名称逐词条对 `transaction_purchases` 预查询命中 id 集合并下推 `IN`（共享 2 万参数预算，超预算词条退让 `EXISTS` 半连接；子表远小于交易主表且前置通配 `LIKE` 无 B-tree 可定位，不建名称索引）；
     - 软删过滤一并下推 `WHERE`。
   - **第二段（回表）**：仅对当前页命中 id 回表取展示列。预查询、行集、总数与回表同收单一读事务，保证读快照一致。
   - 无关键字、仅金额/日期筛选的路径保持最小列流式扫描。

3. **Unicode 非 ASCII 大小写边界（显式接受）**
   - SQLite `LIKE` 仅对 ASCII 做大小写折叠，备注含非 ASCII 大小写变体时不跨大小写命中；账户/商户名字典预判在 Rust 侧保持全 Unicode 折叠。不为此引入自定义 SQLite 折叠函数。

4. **迁移移除与收缩纪律（原决策 4 及 #1725 修订注记）**
   - **未发布迁移**：原 FTS5 迁移 V005 移除时未随任何版本发布，故自迁移序列整体移除且不回填编号；存量旧库残留的 FTS 对象不做清理，由启动期 schema 漂移守卫方向性容忍（ADR-0100）。
   - **已发布迁移**：已进发布 tag 的迁移不得整文件移除（否则破坏存量库 `user_version` 位置语义、跳过后续迁移）。已发布 schema 的收缩必须走**追加收敛迁移**——首例为 V031 拆除 V018 引入的 `note_pinyin` 列及回填索引、重建 `idx_transactions_note_search`。

## 否决与已退役方案（演进证据）

- **FTS5 倒排索引（原 ADR-0004，已整体移除）**：倒排索引无法枚举跳字子序列键集合，与模糊语义根本不兼容；且同步队列与对账机制持续制造一致性缺陷。
- **Rust 内存全量扫描（首版 & 原 ADR-0043 流式化，已退役）**：流式游标将 50 万笔内存峰值从 309.5MB 压至 63.5MB（O(1)），但跨边界取行加 Rust 逐行过滤在 50 万笔下仍需 2932ms（引入覆盖索引 + 字典预判后降为本地 154ms / CI 313ms）。改为覆盖索引 SQL 下推后，50 万笔 seed 42 实测压至本地 ~56–63ms、CI ~70–82ms（商品名搜索 #1885 本地 p95 138ms），满足默认 200ms 门槛并撤销了 ADR-0068 的 400ms 分项例外。
- **备注拼音冗余列 `note_pinyin`（V018 引入、V031 退役）**：曾为支撑交易搜索的拼音子序列下推而设，配套 Writer 同写、惰性回填与设置页一键修复；语义分家后大流水不再支持拼音搜索，整条派生列与修复链经 V031 彻底拆除。
- **进程内候选缓存（#493 评估后否决）**：以数十 MB 常驻堆内存换取扫描加速；SQL 下推已使真实设备与 CI 双双达标，支付常驻内存代价不成比例，不引入进程内缓存或 mmap 逃生舱。

## 后果

1. 交易搜索的文本匹配本质仍是覆盖索引上的 O(全库) 线性扫描（备注与购买项名称均无 B-tree 定位），在 50 万笔个人账本量级下已由性能门禁持续验证达标（ADR-0068）；未来数据量级显著跃升并触发门禁回归时再重评优化手段。
2. 下拉拼音可搜与交易搜索同源一份语义规格、按候选集量级分治；下拉消费方的范围边界（实体下拉 vs 枚举/币种下拉）见界面交互域「拼音可搜下拉」。
3. 交易搜索备注路径不兜底非 ASCII Unicode 大小写折叠；该边界在领域词汇表显式记录。
