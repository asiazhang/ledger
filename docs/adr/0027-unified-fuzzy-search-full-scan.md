# ADR-0027: 统一模糊搜索语义与搜索实现形态

- 状态：已接受（取代已删除的 ADR-0004；已合并原 ADR-0043 并收束历次修订为现行态）
- 日期：2026-09-17（现行态收束：2026-11-20）
- 作者：Ledger 项目
- 关联：issue #195/#196（初版规格与落地）、#492/#515（覆盖索引与 SQL 下推）、#1725/#1728（语义分家与 V031 拼音退役）、#1885（购买项命中面）；关联 ADR-0008、ADR-0028、ADR-0037、ADR-0068、ADR-0100、ADR-0138、ADR-0148

## 背景

ADR-0004 曾以 FTS5 虚拟表配合「触发器入队 → 后台刷新 → 启动对账」实现交易搜索，带来两个根本问题：

1. **语义缺口**：倒排索引只支持整词与右锚前缀，不支持跳字子序列（如 `wy` 搜「万科物业」）与任意位置连续子串。
2. **一致性负担**：倒排索引与主表天然异构，整套同步机制只为追平主表，仍存在不可搜窗口且持续产生活跃缺陷。

## 统一模糊搜索语义（全库唯一规格）

> 输入按空白切词，词条之间 AND；每词条对每个字段判定——
> **命中 = 原文连续子串（大小写不敏感）∨ 词条是该字段拼音首字母串的子序列（大小写不敏感）**
>
> 首字母串生成规则：中文字取拼音首字母、ASCII 字母/数字小写原样保留、标点与空格跳过（「ABC银行」→ `abcyh`）；多音字按前字规则修正（「银行」→ `yh`）。混合输入（如「招zsyh」）无需特判——含汉字词条对纯 ASCII 首字母串的子序列匹配必然失败，自然落回原文子串路径。

**语义分家（判据 = 候选集量级）**：

- **原文连续子串分支**：全仓共享（交易搜索与各类下拉/字典检索）。
- **拼音首字母子序列分支**：收窄归**小候选集检索**独享（下拉选择器、标的搜索 ADR-0037 等）。在几十万行交易流水上，跳字子序列（如 `zs`）区分度崩塌、噪音随数据量线性放大，因此交易搜索（TransactionSearch）只按原文命中。

## 决策（现行）

1. **交易搜索弃用 FTS5，采用覆盖索引 SQL 下推 + 两段式取行**：
   - 连带移除整套 FTS5 虚拟表、重建队列、入队触发器、后台刷新线程与启动对账；写入立即可搜，无滞后窗口。
   - **第一段（匹配与分页）**：单条下推查询以 `INDEXED BY` 钉定搜索覆盖索引 `idx_transactions_note_search` index-only 全扫（列表序供序，EXPLAIN 测试钉定无临时 B-tree），将备注原文 `LIKE`（通配符经 `ESCAPE` 按字面匹配）、账户/商户字典命中 id 集合 `IN` 下推、购买项子表预查询命中 id 集合 `IN` 下推（空集合零每行开销，全语句共享下推预算、超预算退让 `EXISTS` 半连接）、软删口径及金额/日期过滤一并收进 WHERE。
   - **第二段（展示回表）**：仅对当前页命中 id 回表取展示列；结果按交易日期降序分页（与交易列表心智及 ADR-0008 分页契约一致，弃用 bm25 相关度）。
2. **可搜索范围与字典时效**：
   - 命中面 = 交易备注 ∨ 转出账户名 ∨ 商户名（ADR-0028）∨ 购买项名称（ADR-0138 决策 14）；分类名、转入账户名不搜。
   - 账户/商户字典每次搜索新建：改名即刻生效，软删商户的历史交易仍可搜；购买项名称实时预查询并与行集/总数共处同一读事务快照。
3. **语义纯函数单一收口**：切词、子序列匹配与拼音首字母生成收口于 `ledger-transaction` 的 `shared::search_text`。随着 Web 参照前端退役（ADR-0148），NSH 原生壳直接消费同一 Rust 实现，不再存在前后端双实现或字库分歧。
4. **旧库与迁移边界**：
   - 原未发布迁移 `V005__search_index.sql` 已自迁移序列整体移除；旧库残留的 FTS 对象不做启动清理、不补 drop 迁移，由启动期 schema 漂移守卫按方向性 diff 容忍（ADR-0100）。
   - **边界收窄**：上述「移除迁移」纪律**只限未发布迁移**；**已发布迁移**的 schema 收缩必须走追加收敛迁移（迁移文件只增不改，如 V031 退役 `note_pinyin` 列与回填索引、重建覆盖索引），避免存量库 `user_version` 位置错位。

## 理由、否决方案与已知边界

- **排除 FTS5 / 倒排索引**：子序列命中的键集合不可枚举、无字典序区间性质；前置通配连续子串（`%keyword%`）同样无法利用倒排或 B-tree 定位。线性扫描（收窄至覆盖索引 C 层 index-only 全扫）是该语义下的最优形态，同时彻底消灭索引一致性负担。
- **不建购买项名称索引**：前置通配无 B-tree 可定位，且购买项子表行集远小于交易主表，全扫即枚举级成本。
- **不启用进程内候选缓存**：#492/#493 曾评估将候选集常驻堆内存，但真实用户设备本就达标、为 CI 单核画像支付数十 MB 常驻堆不成比例（ADR-0068）；SQL 下推落地后彻底无必要，仅保留为未来极端退化时的可逆手段（届时亦可评估本地文件 + mmap）。
- **量化证据（50 万笔、购买项 ≈10 万行，本地 release p95）**：备注搜索 58.9ms（下推基线 56ms）、商品名搜索 138.0ms，相对早期全扫（2932ms）与 Rust 覆盖索引扫描（154ms）均有充足余量。CI 门禁口径与超标处置归 ADR-0068。
- **已知边界**：SQLite `LIKE` 大小写折叠仅对 ASCII 生效，备注与购买项名称含非 ASCII 字母时的大小写差异显式不兜底（账户/商户名字典在 Rust 侧全 Unicode 折叠，不受影响）。
