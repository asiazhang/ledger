# ADR-0058: 字段错误态——格式错误即时红显、不拦截、提交禁用

- 状态：已接受
- 日期：2026-09-02
- 作者：Ledger 项目
- 关联：词汇表：界面状态与交互域「字段错误态」、TransactionModalState（首批落地载体）；ADR-0045（交易弹窗编排）；ADR-0049（i18n，错误文案后补时经既有文案资源）

## 背景

弹窗表单对非法输入现行三重失语：金额等数字字段经 `NInputNumber` 精度约束，输入 `4.30发` 期间值不更新、失焦时非法文本被**静默清空**，无任何反馈；全仓校验均为提交时手写 if + warning toast，无红框、无提交禁用；也没有可复用的错误视觉 token（仅支出语义红 `#d03050` 硬编码与组件库内置错误色）。用户在编辑交易弹窗输入非法金额时得不到任何即时提示，直到点保存才见「请输入金额」。本 ADR 记录统一的输入格式错误反馈规范及其牵连裁决（不拦截、判定单点、错误红选型、范围边界）。

## 决策

1. **立统一交互规范「字段错误态」（全应用口径，词条化收口语义）**：只覆盖格式类错误——解析失败、超出表示精度、必填为空；纯业务规则不成立（如金额纯零）不在其列，走既有提交时校验通道。反馈形态为红框＋提交禁用，两件同发；字段错误文案按需后补（经既有 i18n 资源），不是本态的必要组成。
2. **即时判定**：输入中即判定即红；初始为空不红（不惩罚尚未输入），空值红在失焦或保存尝试时出现。
3. **不拦截、不静默丢弃**：允许自由键入与粘贴，非法性只由红态表达，不做字符过滤或吞键；非法输入原样保留显示，红态持续到用户修正。实现上允许调整输入组件用法（如改 `NInput` + 共享解析、或调整 `NInputNumber` 参数），以「非法文本可见且持续红显」为准绳，不绑死组件选型。
4. **判定口径单点**：新建轻量共享模块收口全部格式判定（金额格式、必填等）与错误态装配，各表单消费；改口径只碰一处。不引入 Naive UI 的 NForm rules 体系，也不迁移存量表单。
5. **错误红用组件库内置错误色**（输入组件 `status="error"` 一类机制），不定制新 token、不复用支出语义红——交互反馈红与业务语义色（收入绿/支出红/退款蓝）是两类红，不混同。
6. **范围边界**：本期只做自由输入字段（金额、数量、价格、名称类文本）；下拉类字段无输入面、日期选择由组件自身钳制键入，均不在本态范围，必填下拉未选维持既有提交 toast，统一红显留推广期裁决。
7. **落地顺序**：首批交易弹窗族（记一笔/退款/编辑/加入物品，TransactionModalState 四意图），验证后逐步推广到全部含自由输入的弹窗表单。

### 否决案

- **输入字符过滤**（金额框直接吞掉非数字字符，永不存在非法内容）：拦截让「为什么打不进去」成为新的困惑；粘贴混排文本时拦截行为更难预期；且与「非法输入可见」的诚实反馈直觉相悖。
- **NForm rules 全面迁移**：全仓表单均无 rules 体系，迁移成本与本期收益不匹配；判定单点已满足统一口径诉求，表单装配方式保持现状。
- **复用支出语义红**：支出红表达金额的业务含义（不随主题），错误红表达交互反馈态；混用会让红色在交易语境下语义过载。

## 理由

- 即时红显把错误发现从「提交时」提前到「输入时」，与用户实际诉求（输入中即见反馈）对齐；静默清空是最差形态——用户的输入被无声丢弃，连错在哪都无从得知。
- 判定单点是「全应用统一规范」的必然要求：没有单点，16 处弹窗的口径必然漂移；单点收口后推广即消费，不增新口径。
- 内置错误色零新 token、主题体系内暗/亮自动协调，且已有消费先例（仪表盘 NProgress）。

## 代价与边界

- 非法文本保留意味着表单状态需容纳「显示文本 ≠ 已解析值」的中间态，数字字段可能需要调整现有 `NInputNumber` 用法，是本期主要实现成本。
- 「必填」红显与「格式」红显共用本态，但两者的触发时机不同（输入中 vs 失焦/提交尝试），消费方需按字段性质声明，共享模块只收口径不代判时机。
- 下拉/日期未纳入本期，两类控件的红显口径留推广期统一；在此之前弹窗内红态覆盖是不完备的（预期内）。
