# ADR 0144: 账本身份引入「内容锚指纹」——备份归属按指纹 × 设备分域，云端按设备分前缀

- 状态：已接受（决策入档；实现随实施票落地）
- 日期：2026-10-31
- 作者：Ledger 项目
- 关联：ADR-0089（多账本与备份分域——本决策修订其「身份即目录」在**备份归属**维度的适用）、ADR-0016（受管备份命名与保留上限）、ADR-0139（双库成对产物与备份元数据）、ADR-0091（DeviceId、LWW 裁决）、ADR-0018（库外引导指针，已由 0089 泛化为账本注册表）；词汇表：参考数据与设置域「账本指纹（Book Fingerprint）」、多端同步域「DeviceId」、备份与数据文件域 Backup / ManagedBackup / BackupRetentionLimit / BackupPruning（随本 ADR 修订）
- 来源：grill-with-docs 四轮裁决（2026-10-31）

## 背景

跨平台共用一份备份目录时出现「数据不一致」：Linux 端列表只见 5 份备份，macOS 端的产物一份都看不到。实测现场：同一备份目录内 34 个受管 zip——29 个带 macOS 端账本标识、4 个无标识的历史命名、1 个带本机账本标识；本机列表恰为 4 + 1 = 5，与作用域过滤逐条吻合。

根因不在列表逻辑，在**账本身份的来源**：默认账本的 id 由本地默认数据目录路径稳定派生（折叠默认账本的既有语义），于是同一个逻辑账本在两台机器上各有一条路径 ⇒ 两个不同的 id。列表与滚动清理按 id 严格匹配（`in_scope`），两端便互不可见；数据本身是同一本（同 schema 版本、同交易集合、备份元数据同来源应用版本）。

连带两个未被设计的后果：保留上限按 id 分别计算 ⇒ 另一端的历史产物在本端永不参与滚动清理（现场 29 份无人管）；容灾镜像为单命名空间 ⇒ 两端互相镜像删除对方的产物，只靠单次删除上限兜底。

性质判定：不是实现 bug——代码与既有词汇表一致（账本「身份即目录」、备份「只见当前活动账本的产物」）。撞车的是模型未覆盖的场景：**同一逻辑账本存在多条本地路径**。多账本（ADR-0089）要的是「不同逻辑账本互不干扰」，本决策要的是「同一逻辑账本的多端产物合流」，两者不能共用一个身份。

## 决策

### 1. 账本指纹：内容锚 + 首用固化

账本的跨端身份改为**账本指纹**：内容锚取库内最早一笔交易的 UUIDv7（跨端恢复/同步后必然相同），首次算出即固化进 AppSettings（新增一个配置键变体，零 schema 迁移），此后恒读固化值；空库（尚无交易）退化为端内生成 UUIDv7。

否决「端内生成 + 靠多端同步收敛」：需新增账本级设置的语义命令变体，牵动协议枚举、LWW 裁决域与重放注册表绑定，而未开同步的两端依旧分裂——为一条几乎不变的身份值付这份成本不成立。否决「只靠恢复继承」：不解决两端各自新鲜启动的分裂。

### 2. 注册表 id 降级为「本地账本句柄」

引导层的「身份即目录」继续成立（同一目录不得登记为两本），但注册表 id **只在本机有效**，不得用作产物归属标签，也不再是「同一逻辑账本」的判据。一份逻辑账本可对应多端多个句柄。

### 3. 可见性：按指纹分域，外来产物按内容锚归并

受管备份的列出与清理由「句柄相等」改为「指纹相等」。存量产物（文件名带的是别的端的句柄、或无标识）遇指纹不匹配时，以内容锚判定归属：命中本账本则计入，判定结果按「文件名 + 大小 + 修改时间」缓存到**独立本地缓存文件**（可从产物重建，故不进库、不进注册表）。密文产物读不出内容锚，改由备份元数据的明文字段判定（见决策 5）；元数据无设备/指纹、内容锚又不可得者归**「未知来源」桶**。

未知来源桶的产物**永不参与自动清理**，只能手动清理。否决「归本机」：那会让 A 端的滚动清理删掉 B 端历史——正是本决策要消灭的故障模式。

### 4. 保留上限按（指纹 × 设备）分别计数

上限的第二维是**设备**（多端同步域 DeviceId，安装实例级，重装即新设备）。各端只删自己名下的产物，互不挤占配额；重装后旧设备前缀下的产物不被新安装清理，属合法语义。

### 5. 备份元数据携带指纹与设备，文件名不加设备段

zip 内备份元数据增 `fingerprint` 与 `device_id` 两个**明文**字段（只含标识，不含密钥）；旧版本反序列化对未知字段宽容，双向兼容。文件名仍只带一个标识段（今后写入指纹），不加设备段——前后端各持一份命名常量的一致性成本已是有意接受的取舍（ADR-0016），不再加一个要同步的段。

### 6. 容灾镜像按设备分前缀

云端备份路径增一层设备前缀，本地备份目录同步分一层，镜像的 1:1 映射语义不变；旧的扁平路径长期保留只读，列目录与恢复同时兼容两处。否决「保持扁平 + 只删本设备上传的对象」：对象到设备的映射比目录前缀脆。否决「一次性搬运云端对象」：不可逆，收益只是目录整齐。

### 7. 兼容红线：不动 schema、不动注册表格式版本

指纹只占一个 AppSettings 键，不新增表、不升 schema；别名缓存是独立本地文件，不碰账本注册表。于是新版本对旧版本**完全隐形**：旧版本读新库同 schema、读新注册表同格式版本、读新备份元数据只忽略多余字段。跨端版本错位的窗口因此零风险。

注册表格式版本一旦 bump，版本不匹配即被判为损坏并回退默认账本——这会让「先升一台」的窗口变成数据可见性事故，是本次刻意避开的单向门。

## 理由

- **内容锚是唯一能让两端独立算出同一答案的来源**：不依赖同步通道是否开启、不依赖注册表是否同步、不依赖产物元数据是否齐全；旧库也能反算，存量归并因此可自动化。
- **首用固化把锚漂移窗口压到「首用之前」**：与 DeviceId 的「首用生成并持久化」同款语义，删改最早交易的极端场景在固化后不再影响身份。
- **未知来源保守不删是破坏性动作的正当默认**：清理错删不可撤销；宁可让一批旧产物无人清理（用户可手动清），也不让某端替另一端做决定。
- **不动注册表版本是这次决策里最硬的一条**：它是唯一「一改就把另两端变成瞎子」的点，而账本身份其实并不需要住进引导配置。

## 代价

- 首用固化前锚会随「最早一笔交易被删」漂移；固化后不受影响。
- 旧密文产物无法自动归并，须人工登记别名（新密文产物因元数据带指纹而不受影响——加密是可选增强，不该反向阉割跨端可见性）。
- 列表首次遇到外来产物需解包内主库取内容锚（现有列表已为每个文件开一次包，属既有成本的一部分），靠别名缓存摊平，首次略慢。
- 备份目录与云端路径各多一层设备子目录，旧扁平路径长期并存（列目录与恢复要兼容两处）。
- 设备维度以安装实例为粒度：重装即新设备，配额不跨安装累计，旧前缀产物永久留在未知/旧设备桶里不自动清理。

## 替代方案

- **读侧宽容匹配**（猜哪些标识属于同一本）：换个平台路径又对不上，无法收敛。
- **注册表 id 随云端同步 / 手工统一两端的注册表**：破坏「设备本地偏好不随库走」的既有边界，多账本场景直接失效。
- **账本指纹走同步协议下发**：见决策 1，成本与收益不匹配，且未开同步即分裂。
- **列表不过滤、全量展示**：把真正不同的两本账混为一谈，废掉 ADR-0089 的分域语义。
- **云端保持单命名空间**：见决策 6。
