# ADR-0093: 前端自定义样式引入 vanilla-extract 原子样式方案

- 状态：已接受
- 日期：2026-09-09
- 作者：Ledger 项目
- 关联：词汇表界面状态与交互域「样式方案」「Design Tokens」词条；参考数据与设置域 Appearance（设备偏好）、语义色接缝

## 背景

前端样式现状是「SFC scoped style + 组件库主题体系」，不存在独立 CSS 框架：77 个视图组件中 25 个自带 scoped 样式块，外加一份小体量全局样式表。样式随视图数增长各自漂移，没有类型护栏，视觉常量（圆角、背景分层、灰阶）散落在主题覆盖文件与各组件之间。诉求是三件事：原子化（样式体积随代码增长趋平）、类型安全（token 引用错在编译期报错）、零运行时（不向浏览器注入样式引擎）。

最初意向是 StyleX。调研结论：StyleX 官方定位 framework-agnostic 但为 React 调优，v0.18 才恢复 `stylex.attrs` 以支持 Vue 这类以 `class` 挂载样式的框架；Vue 下的既有用法要求放弃 SFC `<style>` 块、把样式对象定义在脚本模块顶层，社区先例稀薄，官方文档亦明示 Vue 「may need some custom configuration」。可以引入，但属于逆着生态主航道行船。

## 决策

1. **载具**：自定义标记的样式方案采用 vanilla-extract（构建期 TypeScript 样式，官方 Vite 插件）+ Sprinkles（官方原子化层）。样式以组件旁路样式文件形态与组件共置。
2. **边界**：组件库（Naive UI）及其主题体系（配置提供者、主题覆盖、语义色接缝）一字不动；新方案只接管组件库之外的自定义布局与元素。「组件库内部样式 + 外部原子方案」两套机制共存是显式接受的形态——组件库组件的内部样式不可被外部方案接管，机制层统一只有更换组件库一条路，量级远超本决策。
3. **一致性收口在 token 层**：新增中性 Design Tokens 单一来源（圆角阶梯、背景分层、边框、文字灰阶），组件库主题覆盖改为从其派生，新方案主题同样从其派生；两处视觉口径同源，一致性由派生保证而非人工同步。交易语义色维持既有领域接缝不动，新方案直接消费。
4. **亮暗切换**：新方案以主题合同 + 亮/暗两个主题类表达，绑定应用根元素、由 Appearance 设备偏好驱动，与组件库的主题切换并行不互扰。
5. **迁移纪律**：存量 scoped 样式与全局样式表冻结，新代码一律走新方案，存量随触碰渐进迁移（boy-scout）；守门检查挂入 `check.sh`——存量文件白名单，禁止新增 `<style>` 块。

## 理由

- **为什么不是 StyleX**：满足三属性但 Vue 是二等公民——集成依赖非官方惯例、社区实践薄、升级路径不受官方保障；为了载具名号接受生态风险不值。
- **为什么不是 Panda CSS**：同为 Vue 官方支持的候选（`css()` 可内联 SFC、语义 token 自带亮暗切换），体感最接近 StyleX；但多一个 codegen 产物目录与构建步骤，管线重量对本仓库的样式体量不成比例。备选记录在案，若未来吃 recipe/模式体系再议翻案。
- **为什么 vanilla-extract**：三属性齐备，官方 Vite 插件即插即用（无 codegen 产物），框架无关是官方主航道而非附加承诺；旁路样式文件形态与仓库「单一来源、显式接缝」的既有口味一致。
- **为什么迁移只管增量**：存量 25 个 scoped 样式块无现实缺陷，全量迁移是纯风险无对价；没有守门的「渐进迁移」实践中永不完成，故白名单守门与迁移纪律同票落地。

## 代价

1. 两套样式机制并存，贡献者需判别「这块样式归谁管」——边界由守门检查机械维持，判别成本低但存在。
2. 每个样式化组件旁多一个旁路样式文件，组件文件数近倍增——共置形态的固有成本，接受。
3. Sprinkles 若在运行时组合原子类会带入全量类样式，纪律为构建期组合；越线属实现 bug 而非设计缺口。
4. token 派生使组件库主题覆盖文件失去独立性——改中性 token 会波及组件库视觉，这正是「单一来源」的本意，但差异化管理能力（组件库一套色、自定义另一套）不再免费。
