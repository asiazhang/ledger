# ADR 0018: 数据库存储位置可配置——引导指针文件 + 启动期搬迁

用户可自定义 ledger 主数据库文件所在目录（DataLocation，见 CONTEXT.md），未配置时仍用默认应用数据目录；文件名固定 `ledger.db`、单一活动路径、不做多账本并存。该配置必须在**打开数据库之前**读取，因此无法按 ADR-0017 的归口落进任何一层：最终以默认应用数据目录下的一个小型指针文件承载，作为「独立配置文件已否决」规则的**唯一例外**；位置更改采用「写意图 + 下次启动自动搬迁（Relocation）」的两段式生效模型。

## 背景

需求动机是把库放进同步盘（iCloud / OneDrive 等）或大容量盘——只需单一活动位置，随时可整体搬家。设计难点在配置本身的落点：

| 可选落点 | 为何不适配 |
|---|---|
| `app_settings` KV 表（ADR-0017） | 存在于 `ledger.db` 内部，而本配置决定"打开哪个库"，鸡生蛋 |
| localStorage 推送（`backupDir` 先例） | Rust 在 setup 阶段就要建连，早于前端 ready 与 immediate watch，首启/冷启动存在时序缺口 |
| 独立通用配置文件 | ADR-0017 明确否决过，理由是游离于事务/迁移体系之外 |

上述分析表明这不是归口规则没想清楚，而是出现了一个规则未覆盖的新层次：**引导配置**——比"库内一切状态"更底层。同时，搬迁本身有现成机制：rusqlite 支持 `VACUUM INTO`，且 `commands/backup/core.rs` 已有"写入唯一临时名 + 校验"的使用先例。

## 决策

1. **引导指针文件**：默认应用数据目录下一个小型文件，仅记录当前意图的 DataLocation（约等于"库在哪"一个问题）。损坏、缺失均视同未配置 → 使用默认目录，即删掉它就能回到出厂行为，天然是逃生舱。
2. **两段式生效**：设置页点「更改」只在当时做校验（`create_dir_all` 自动建目录 → 试写验证可写 → 目标已有 `ledger.db` 时弹二选一："接管该库 / 取消换位"，不静默覆盖也不解析库内容）并把意图写入指针文件；真正搬迁发生在**下一次启动建连之前**，引导逻辑三个分支：目标位置已有库→直接用；目标为空而原位置有库→`VACUUM INTO` 整库搬迁后再用；两者皆无→新建空库。
3. **搬迁选启动期而非点击时**：点击时立即复制会在"复制完成 → 用户实际重启"之间留下增量丢失窗口（期间的记账落在旧库，重启即丢）；启动期一次完成则不存在双写窗口。代价是用户点击后看不到即时结果，通过明确的"下次启动生效"提示换取正确性。
4. **设备本地偏好边界**：永不随 Backup/Restore 携带或恢复（Restore 无法合法覆盖"库在哪"这一本机事实）；指针指向的路径非法或打不开时回退默认目录并在界面显著提示，原库文件永远保留、绝不自动删除。
5. **「恢复默认位置」入口**：作为同一张设置卡上的次级操作提供，复用第 2 条完全相同的机制与校验，零新增逻辑。

## 考虑过的替代方案

- **配置存 `app_settings`**：不可能，见背景表格。
- **沿用 backupDir 的 localStorage 推送模式，并把 DB 打开推迟到前端就绪之后**：为一个单项配置扭曲整个启动时序（所有命令、调度线程都要处理"连接尚未就绪"态），收益不成比例，否决。
- **点击「更改」时立即 `VACUUM INTO` 复制**：实现直观但产生增量丢失窗口（决策 #3），否决。
- **允许自命名完整文件路径（支持多账本）**：引出"如何识别某个文件是不是合法 ledger 库"的解析负担与一整类并发/误选问题，超出单一活动路径的需求，MVP 否决。

## 后果

- 归口规则升级为四层，ADR-0017 的表格由此补充一个例外行：**引导配置 → 库外指针文件**。除 DataLocation 外不得再往指针文件里塞东西——任何"也想放在建连前读"的新诱惑都应先重新论证是否真属于引导层。
- 数据库打开流程增加一处前置步骤（读指针 → 定位目录 → 必要时搬迁），该逻辑集中在建连入口附近，保证"将来调 DB 打开行为只有一个地方要看"。
- 设置页对搬家结果的反馈是延迟的（重启后），文案必须讲清"下次启动生效"；界面上还应展示当前完整路径，方便核对是否真的在预期位置。
