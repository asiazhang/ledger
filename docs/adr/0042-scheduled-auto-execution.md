# ADR 0042: 定时计划自动执行（到期追补）与设备级开关

- 状态：已接受（部分推翻 ADR-0024 的「期次手动执行」边界；ADR-0024 失败策略等其余 MVP 决策维持）
- 日期：2026-08-31
- 作者：Ledger 项目

## 背景

定时计划期次到期后什么也不会发生：没有任何自动落账，用户必须进「定时」页逐笔手动执行（ADR-0024 MVP 边界）。笔记本合盖睡几天是常态，醒来后积压期次全靠记忆补，忘了就一直躺在库里——订阅花费、预算、账户余额全部不含这些该记的账，账本悄悄失真。

自动备份（ADR-0016）已有一套成熟的「后台轮询 + 参数注入时间的纯函数判定」调度纪律，检查周期在 #306 已收紧到 10 分钟。自动执行自然归并到同一条调度线程上，但要回答四个新问题：① 开关存哪里（设备级还是账本级）；② 什么算「到期」、追补到什么程度；③ 失败了怎么办；④ 多设备同开会不会重复落账。

## 决策

1. **设备级「自动执行」开关，默认关**。属设备偏好：单一来源在前端 localStorage（应用设置 store），应用启动与变更时经领域命令形状的 IPC 推送命令更新后端**运行时镜像**（备份目录镜像推送先例，ADR-0016 决策 3）。**刻意不进 `app_settings` KV 表**（不随本决策改写 ADR-0017 的归口规则）：该表随 Backup/Restore 迁移，存进去就成了全账本单值——表达不了「这台执行、那台不执行」，还会把自动化意外迁移到新设备。镜像默认关：未推送即关，换新机器或恢复备份后默认关。
2. **追补语义**：到期 = 期次 `pending` 且计划日期 ≤ 今天（**含今天**：交易日期忠实回填期次计划日期，迟执行不丢正确日期；跨午夜后下一检查周期自然滚动到新到期期次）；计划须 `active`。`failed` / `processing` / `cancelled` 期次与 `paused` / `cancelled` 计划一律不碰。逐条经既有单期执行入口落账（事务自持 + CAS），单期失败不中断同批后续；追补尝试失败的单期 CAS 置为 `failed`，保持手动重试入口、不被下一轮自动反复重试（ADR-0024 失败策略维持）。入口返回执行汇总（到期/成功/失败计数与失败明细）并落日志。
3. **调度归并：单一 tick 双判定**。自动备份轮询线程泛化为每轮先做备份到期判定（纯函数，24 小时锚点 + 脏标记不变）、再做追补判定；线程只做周期调用，决策全在参数注入的入口函数（自动备份模块既有纪律）。追补入口是**唯一新增接缝**：参数注入（连接、开关状态、今天日期）→ 执行汇总，所有后端行为测试打这一个入口；期次执行本体与备份到期判定沿用既有接缝零改动。开关由线程从镜像读出后注入。
4. **置脏联动自动备份**：每笔自动落账成功即经统一写入口语义置脏（ADR-0032），自动备份到期判定联动可见——自动生成的账同样被备份保护。
5. **多设备竞态：接受并文档化，不做同步层互斥**。仅当两台设备**同时离线**且都开启自动执行才可能各自落账成重复；在线场景由期次 CAS 与同步状态收敛天然保护。防线 = 设备级默认关 + 设置说明明示「自动执行只应在一台机器开启」。

## 理由

1. **开关存 localStorage 而非 KV 表，是因为「设备级」是本决策的语义核心**。ADR-0016 决策 3 曾论证「调度器消费的开关必须后端可见」而把自动备份开关存库——但自动备份开关是账本级保护网（备份本就该随账本走）；自动执行开关恰恰相反，它的价值就在于**不**随账本迁移。两者属不同层次，不构成归口冲突。
2. **追补而非只补「今天到期」**：离线几天后积压期次一次性补齐、日期忠实回填，账本才能在醒来后立刻恢复真实。含今天边界让「当天到期当天落」，跨午夜滚动让长期挂着的应用无需重启。
3. **失败置 failed 而非留在 pending**：留在 pending 会被下一轮反复重试——正是 ADR-0024 失败策略要避免的「自动反复重试」；置 failed 后由用户看清原因、手动重试（既有单期执行命令天然接受 failed）。CAS 守卫保证并发下不覆盖其他设备已推进的期次。
4. **归并到既有线程而非另起线程**：调度线程已被 #306 收紧为 10 分钟一轮、毫秒级开销，追加一个「读镜像 + 一次日期比较」的判定成本可忽略；两个后台线程各自拿锁反而引入新的争抢面。

## 代价与边界

- 只在应用运行期间生效：应用不运行即无执行主体，这是行为定义不是缺陷；系统休眠唤醒后由 10 分钟轮询在下一轮补上。
- 两台设备同时离线且同开仍会重复落账：接受该竞态，以「默认关 + 说明文案」为防线，不建同步层互斥。
- 失败标记存在极窄降级窗口：单期执行失败后置 `failed` 若自身也失败（或进程在两步间退出），期次留在 `pending`，下一轮会再试一次——标记 CAS 带同状态守卫，下一轮自然补上标记并再次告警；持久性故障（如缺汇率）至多每轮多一次注定失败的尝试，不产生重复落账。
- 无提醒/角标：自动执行落地后「到期未执行」的主要场景消失，失败期次仍在计划详情可见。
- 手动执行流程不变：计划详情逐期执行保持现状，自动与手动共用同一单期执行入口。

## 替代方案

- **开关存 `app_settings`（随备份迁移）**：全账本单值表达不了设备级，恢复备份会把旧机器的自动化带到新机器——正是用户故事 15 要避免的，否决。
- **失败留 pending 下轮再试**：构成对永久性失败（如缺汇率）的无限自动重试，违背 ADR-0024，否决。
- **独立调度线程 / 更短追补周期**：两个线程争抢同一连接锁、收益仅是分钟级提前，否决。
- **同步层互斥 / 分布式锁**：离线优先架构下无协调者，复杂度远超「同开两台」的边缘场景，否决（ADR 承载 + 默认关足够）。

## 修订关系

- **部分推翻 ADR-0024**：「期次只能手动执行」的 MVP 边界演进为设备级受控自动执行；ADR-0024 的失败手动重试、严格日期不顺延、单期不可跳过等其余决策维持。
- **沿用 ADR-0016 修订注记的检查周期**（#306 收紧的 10 分钟）作为追补的检查周期；备份触发模型与频率锚点不变。
