# ADR-0062: 性能基准数据集——确定性生成而非入库

- 状态：已接受
- 日期：2026-09-03
- 作者：Ledger 项目
- 关联：spec #458（性能基准数据集与基准工具 ledger-perf）；实现票 #459（generate 子命令，本 ADR 随其落地）、#460（投资域与计划域画像扩展）、#461（bench 子命令）、#462（CI 观察workflow）；依赖 ADR-0056（bin 属包内自动发现目标，产品 lib 不新增模块）；词汇表无新增词条（工具为开发侧基础设施，不产生领域术语）

## 背景

Ledger 的 BDD 与集成测试全部跑在内存小库上，当真实账本增长到数十万笔 Transaction 时，交易列表与聚合查询是否仍然流畅没有任何系统性答案；慢查询日志（perf_trace，≥100ms 告警）只是被动防线。要建立性能基线，先要有一个**稳定可复现的大库**——它从哪来？

最直觉的做法是把一个大库文件提交进仓库，但这立刻撞上三面墙：仓库永久膨胀（50 万笔库以百 MB 计，且只增不减）、二进制内容不可 review（每次再生成都是一次不可读的巨型 diff）、以及生成逻辑与 schema 漂移后无人察觉。git-lfs 只解决膨胀的存储面，diff 不可读与基础设施成本照旧。带 DDL 拷贝的 JS 生成脚本则引入第二份 schema 事实来源——迁移演进后脚本照常产出「看起来能用」的旧库，漂移完全静默。

## 决策

### 1. 数据集不入仓库，由工具现场确定性生成

基准数据集（`ledger-perf generate`）在需要时现场生成：固定默认种子（`--seed` 覆盖）、默认 500,000 笔（`--transactions`）、锚定结束日期 2025-12-31（`--end-date`，刻意不锚定「今天」，避免数据随墙钟漂移）。同参数必出同构的生成数据（全表有序摘要一致）——性能问题可以被任何人精确复现，查询优化可以在同一数据集上前后对照验证。随机数用手写可种子化 PRNG、参数用手写解析，**零新增依赖**；生成逻辑全部封在 bin 模块内部，产品 lib 不新增模块、不扩散接缝。

### 2. 建库经应用自身的迁移应用路径，不复制 DDL

生成器打开文件库后调用与产品启动完全相同的迁移入口（打开 → 应用全部迁移 → user_version 正确），schema 与 user_version 永远和真实产品一致；迁移是 schema 唯一事实来源，不存在第二份 DDL。数据画像（核心交易域：账户/分类/商家长尾/多币种与汇率历史/转账/退款链/软删除，投资域与计划域随后扩展）只为性能形似，不承诺业务语义完备。

### 3. 默认输出到构建目标目录，与真实用户库物理隔离

默认输出路径在构建目标目录下（`src-tauri/target/ledger-perf/`）：天然被版本控制忽略、与真实用户库文件物理隔离——生成行为永远不会威胁真实数据；`--out` 可改，目标文件已存在先删后建，保证幂等重建。

### 4. 工具形态：包内自动发现 bin，与主程序同 package

`ledger-perf` 作为后端包内自动发现的 bin 目标存在（`src/bin/`），随包编译、随常规测试循环携带正确性单测（画像行数、外键完整、user_version、确定性摘要——断言经现有查询函数层与标准连接工厂完成）。正确性测试保证「schema 演进破坏生成器」时第一时间失败，这正是 DDL 拷贝方案缺失的防线。

## 备选否决

- **checked-in 二进制（大库文件提交进仓库）**：仓库永久膨胀且只增不减；二进制内容不可 review，每次再生成产生不可读的巨型 diff；生成逻辑与 schema 漂移后无人察觉。三者叠加使这条路的维护成本随时间单调上升。
- **git-lfs 托管大库**：膨胀与 diff 不可读同病，另加一套 LFS 基础设施（服务端配额、 contributor 安装门槛、CI 拉取配置）；且「库文件与迁移漂移」的根本问题原样存在。
- **带 DDL 拷贝的 JS 生成脚本**：脚本内复制一份 DDL/枚举/画像 SQL，与迁移必然漂移——迁移演进后脚本照常产出旧 schema 的库，基准数字悄悄失真；引入 Node 侧第二套生成栈还需在 JS 里再造一个 PRNG 与产物校验，成本高于收益。

## 后果

- **仓库零膨胀**：库文件永不进仓库（默认路径被版本控制忽略），diff 永远可 review。
- **可复现性成为规格**：同参数必出同库由确定性单测守护（同种子两次生成全表有序摘要一致）；「约数画像」以固定值落地（50 账户 / 40 生成分类 / 800 商户 / 转账 8% / 退款 2% / 软删 1%），分布断言容差按小样本测试规模校准。
- **生成/基准逻辑住 bin**：产品 lib 零改动；后续 bench 子命令（#461）经同一 bin 扩展，经「现有 pub 查询函数 + 标准连接工厂」消费生成的库，基准代码内不重写业务 SQL。
- **CI 观察不判定**：每周现场生成 + 跑基准（#462），耗时只记录不设阈值，阈值机制等基线分布稳定后再议。

## 修订记录

- **2026-09-06（issue #532）：bench-import 子命令——批量导入写基准。** ADR-0067 写路径「每行同事务整体重算余额缓存」的成本是否可感知（#519 grilling 裁决：由数裁决，不拍脑袋）在本子命令下量测：50 万笔既有数据集上批量导入固定行数 ×「同账户集中/多账户均匀」两分布，报告总耗时 min/avg/p95 与单行均摊 p95；行数档默认 50/100/200——按 AI 导入真实量级校准（按月导入，单月账单最多上百笔），不预设不存在的单批万级场景。每次迭代从 pristine 快照恢复（源库零改动，迭代间数据集规模固定）；导入走批量编排权威 `TransactionBatch::run` 与生产同一 SQL 路径，基准日期取数据集最大交易日期次日（去重身份不命中既有数据）；正确性底线 = 每次导入后断言余额缓存与实时计算逐账户一致，失败即量测作废；刷新段开销经既有耗时日志（SQL 语句级全覆盖）归因，不新增观测代码。无门禁判定、check.sh 不跑（输出人工判读）；perf-bench CI 每日以最大档 200 行 × 两分布观测、只记录进 Summary——写基准无交互可感线可依，阈值待 CI 基线分布稳定后修订 ADR-0068 另立判据（同本 ADR→0068 先观察后立阈的先例顺序）。本 ADR 既有决策（确定性生成、迁移路径建库、bin 形态、物理隔离）不变。
- **2026-09-04（issue #493 / 父 #489 B4）：观察期结束，阈值门禁另立决策落地（ADR-0068）。** 后果「CI 观察不判定」的预留口子正式兑现：perf-bench 升级为判定门禁——全部 10 项基准逐项 p95 ≤ 200ms @ CI（ubuntu-latest、50 万笔 seed 42 确定性库），超标即 job 失败；迭代 10→20（n=10 时最近秩 p95 恒等于 max，20 次才成真分位数）；判定下沉 `ledger-perf bench --max-p95-ms`，workflow 只传参。判据、统计口径与豁免原则（启动迁移/备份等合法慢路径不入判据；ADR-0009 的 100ms 观测告警线保留不动）以 ADR-0068 为准。本 ADR 其余决策（确定性生成、迁移路径建库、bin 形态、物理隔离）不变。
- **2026-09-04（issue #514 / 父 #512）：基准库画像对齐——generate 补填 note_pinyin 派生列 + 新增拼音子序列基准项。** 交易行裸 INSERT 此前未填 V018 派生列 note_pinyin，靠 bench 预热时搜索入口惰性回填才与真实库对齐；现在主臂与计划期次交易臂的 INSERT 均以与 Writer 接缝同规则的 `pinyin_initials` 同写补填，基准库与真实库搜索路径画像一致（同参数两次生成的确定性不变，全表摘要随新列内容自然变化）。bench 新增「备注搜索拼音子序列」基准项（默认关键字 kf），与中文子串基准并列（issue #461 的 10 项 → 11 项）；阈值判定见 ADR-0068 修订记录。
