# ADR-0127: 明文库形态不变式与快照路径 ATTACH 显式 KEY——外来形态归一化收口启动引导

- 状态：已接受（事故落档，spec #1452 / issue #1455；实现已随 #1453、#1454 落地）
- 日期：2026-09-18
- 作者：Ledger 项目
- 关联：ADR-0075（决策 4 启动探测文件头；决策 5 启动失败恢复屏；决策 6 整库转换机制——本裁决的归一化复用其「明文 → 明文」形态；决策 7 备份继承源库加密与密钥——不变式二的唯一例外条款）；ADR-0016（自动备份：`VACUUM INTO` 快照通道与失败重试语义）；ADR-0080（启动引导序列——归一化的挂载点）；ADR-0111（探测与归一化落 infra boot 区）；词汇表：备份与数据文件域 Backup（边界句）、启动失败恢复

## 背景

事故（#1452）：2026-09-13 起某个账本的自动备份连续静默停摆——应用一切正常（打开、记账、查询、恢复、加密形态转换全部可用），只有备份与多端同步检查点产出全灭；日志里同一错误出现 328 次，文本是 SQLite 原文 `unable to open database: <备份目录临时文件路径>`，不含任何原因；备份目录累积 162 个 0 字节临时文件。「失败保留脏标记、下周期重试」的既有语义在此退化为「每个周期必然以同一方式失败」——重试在结构上不可能成功。

根因不在损坏而在**形态**：外部工具（macOS 自带 `/usr/bin/sqlite3`，Apple SEE 构建）执行 `VACUUM` 时把明文库文件头偏移 20 的「每页保留字节」从 0 改写为 12。该字段只是 SQLite 每页预留的空闲字节数——文件合法、`integrity_check` 通过、读写版本字段正常，日常读写完全无感。但 SQLCipher 给 `ATTACH` 加的补丁在「主库请求的保留字节 > 0」时推断主库是加密库、让附加库继承同一密钥；明文库没有密钥，`sqlcipherCodecAttach` 返回 `SQLITE_MISUSE`，`VACUUM INTO` 内部那条**不带 KEY** 的 ATTACH 因此报出不含原因的 `unable to open database`。自动备份、手动备份、更新前备份与同步检查点产出（同为 `VACUUM INTO`）全部命中；加密库不受影响——无 KEY 的 ATTACH 继承真实密钥，是既有设计依赖的行为（ADR-0075 决策 7）。

立档动机是这条缺陷的**反直觉**：文件合法、日常读写正常、错误信息不含原因，三条叠加让故障看起来像「备份坏了」而不是「库文件形态被外部工具改了」。把两条不变式与被否决的绕行方案写下来，后来者才不必重新发现这条 SQLCipher 陷阱。

## 决策

1. **形态不变式一（应用自有明文库）**：应用自有的**明文**库必须满足文件头偏移 20「每页保留字节」= 0。偏差不是损坏——文件合法、能通过完整性检查——而是**外来形态**，处置口径是启动期整库归一化，不是报损坏、更不是静默带病运行。加密库不受本不变式约束：SQLCipher 写码器需要非零保留字节存放 IV/HMAC，保留字节 > 0 对密文库是常态而非偏差。
2. **归一化收口启动引导（建连之前），不在备份时做**：启动处置判定新增一态「明文库 + 外来保留字节」；命中时在建连之前复用既有整库转换链做「明文 → 明文」的形态归一（显式 `ATTACH … KEY ''` + SQL 级导出 + 显式对齐 `user_version` + 试开校验 + 原子替换 + 保留 `.bak` 副本），失败清理临时产物、原库原样，经启动失败门交既有失败恢复屏（码化错误）。收口启动引导的理由：此刻连接尚未建立，重写文件不需要换连编排，也不存在把连接锁从几十毫秒拉到百毫秒级的运行期代价；且「库文件形态」本就是引导层的处置对象（明文/密文探测、损坏残留判别同住此处）——备份路径的正确动作是门禁加指路（重启即被归一化修复），不是兼营文件修复。
3. **形态不变式二（快照/导出路径不得依赖隐式密钥继承）**：应用自己书写的 ATTACH 语句在一切快照/导出/转换路径上必须显式携带目标 KEY（明文目标用空钥匙）；隐式密钥继承不得成为新代码依赖的机制。`VACUUM INTO` 的内部 ATTACH 是唯一被容许的例外——它继承源库密钥（密文库备份语义，既有设计依赖，ADR-0075 决策 7），而对明文外来形态必然失败；因此快照发起前有源库形态门禁：命中外来形态明文库直接返回码化错误（文案指向重启修复），不发起注定失败的语句，失败路径不残留任何临时文件。加密库快照语义不变。
4. **归一化不新增第二套实现，同根因路径不另设机制**：归一化复用整库转换链（同一转换核心，不新增导出/替换/校验实现）；多端同步检查点产出与备份同为 `VACUUM INTO`，启动归一化后自然恢复，不为它引入第二套快照机制或第二处形态检查。
5. **检测复用唯一读头点**：既有文件头探测是仓库唯一的读头点，扩展为一次读取同时给出明文/密文三态与保留字节，不新增第二份头解析；`probe_file_kind` 三态视图保留，既有消费方零改动。

## 否决

- **`VACUUM INTO 'file:<路径>?key='`（URI 参数绕过推断）**：实测 1 行改动即可让 ATTACH 成功，但产物仍保留外来保留字节——污染随备份与恢复传递（用这份备份恢复出来的库再次踩同一坑），且把「库文件形态被改」这一根因永远掩盖在绕过之下。绕过不是修复。
- **在线备份 API（rusqlite backup feature 的页级拷贝）**：明文库实测可用（`integrity_check=ok`），但 SQLCipher 对加密库禁用页级拷贝——无法成为明文/密文共用的单一机制，且产物同样保留外来保留字节。备份域需要的是单一机制，不是按形态分叉的两条。
- **`PRAGMA reserve_bytes = 0` 就地归零**：本构建（bundled SQLCipher）不提供该 pragma（读取即报错），且该 pragma 对非空库无效——即便可用也需整库重写，与既有转换链相比没有更便宜的路径。
- **归一化置于备份时（而非启动引导）**：备份时归一化要在持有连接的状态下做文件级写换，连接锁被拉长一个量级；且「文件形态处置」与「快照产出」是两个职责，备份域不该拥有文件形态语义（理由见决策 2）。

## 外部工具清单（供 ledger-migrate 等外部工作流参照）

- **危险**：Apple `/usr/bin/sqlite3`（SEE 构建，`PRAGMA compile_options` 含 `CODEC=see-cccrypt`）的 `VACUUM`——实测把明文库保留字节从 `00` 写成 `0c`。对应用自有库文件执行该工具的 `VACUUM` 会触发上述全部后果。
- **安全**：`sqlite3 .backup`（实测忠实复制：`00→00`、`0c→0c`）；Python 标准库 `sqlite3` 模块的 `VACUUM`（实测保真）。

## 后果

- 常态成本：正常明文库的启动探测多读 5 个字节（保留字节与既有头字段在同一次读取中取回）；归一化只在命中外来形态时发生，正常库不动文件。
- 归一化的代价是文件被重写：文件级同步/去重工具（网盘、git-LFS 类）会全量重传一次；峰值磁盘约 2× 库大小（旧库 rename 为 `.bak`，不额外拷贝）。实测 14.7 MB / 3596 页 ≈ 72 ms（debug 构建）。
- 新增两条码化错误：启动引导的 `boot.db-normalize-failed`（归一化失败，原库原样进失败恢复屏）与备份域的 `backup.foreign-form`（快照前门禁命中，文案指向重启），文案经 i18n（zh 与后端消息逐字一致，ADR-0050）；备份失败路径的临时文件清理是结构性行为（所有退出路径统一收尾）。
- 词汇表：备份与数据文件分域补一条边界句（外来形态库的处置口径），不新增术语。
- 守门：删除启动归一化接线 → 壳启动集成测试变红（断言「文件被归一化 + 启动相位就绪」，对准用户可观察结果）；备份域以「外来形态夹具返回稳定错误码且无临时残留」钉住门禁。
