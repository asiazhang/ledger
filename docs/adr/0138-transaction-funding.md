# ADR 0138: 多出资方（出资项）——expense/income 交易的出资分解子表与契约互斥

- 状态：已接受（决策入档；实现随实施票落地）
- 日期：2026-09-28
- 作者：Ledger 项目
- 关联：ADR-0096（出资账户——buy/sell 结算归因，保持专属、不泛化）、ADR-0067（余额缓存整体重算）、ADR-0011（Amount Model 与币种一致性）、ADR-0033 / ADR-0105（写入协议与编排入口）、ADR-0091（多端同步 DomainCommand）；词汇表：核心交易域「出资项（Funding）」「来源订单号（Source Order No）」（新）、InvolvingAccount、受影响账户、Transaction Kind Mapping
- 来源：issue #1859（迁移侧 ledger-migrate 组合支付落账需求）triage + grill 三轮（Q1–Q12 全部获维护者确认）+ 抛弃式原型讨论（四出资情形与订单形态，分支 `prototype/1859-multi-funding-readside`）

## 背景

京东等平台存在组合支付：一笔订单由多个账户共同付款（真实回单：订单 ¥281.60 = 小金库 ¥28.53 + 余额 ¥253.07），且存在预售（定金与尾款跨账户）。迁移侧需把账本行拆到商品级（多品订单要能看到「买了什么、每件多少钱」），但商品行金额只对应部分出资，当前模型要求每笔交易的出资账户唯一——迁移侧以「跨界拆分行」（同一子单在账户边界拆两行、各挂一个账户）临时绕过，属临时形态（两年约 10 单）。

四种出资情形（讨论分类，界面不呈现）：一对一（现状）、一对多（一笔交易多账户出资）、多对一（多行商品同一账户）、多对多（多行商品多账户，其中跨界行需要分解）。本决策让后三种在一行内可表达、且余额与对账口径正确。

## 决策

1. **数据模型：新子表，不复用出资账户列**。出资分解落独立子表 `transaction_fundings`（交易引用、显式顺序位、账户引用、金额、扣款标签），子行生命周期绑定主行（主行软删即失效，子行无独立软删位）；显式顺序位保读回稳定；存量行零迁移（分解可选，缺省 = 单出资现状）。**否决**把 ADR-0096 的出资账户列泛化复用——那是 buy/sell 的结算归因角色，与本决策的逐条分解语义不同源。
2. **契约互斥**：写入时带非空出资分解 ⇒ 禁止携带 `account_id`（码化报错）；不带 ⇒ `account_id` 必填（现状）。**否决**「`account_id` 作缺省主出资」与「静默忽略」——前者制造双写歧义，后者静默丢数据。
3. **范围**：仅 `expense` / `income` 可带分解；`transfer`（两端已表达）、投资 kind（结算归因见出资账户）、`dividend` / `split` / `convert` 不做；定时计划生成的分期 / 订阅维持单出资（后续按需立单）。
4. **约束束**：每条出资账户准入与 `account_id` 同口径（存在、未软删、币种与交易一致、不折算），**不设账户类型闭集**（credit / debt 可出资，白条场景）；每条金额为正整数分，Σ 出资 == 交易金额；扣款标签自由文本、可选、上限 50 字；允许同一账户多条出资项（定金 + 尾款靠标签区分）。
5. **refund**：关联分解交易的退款缺省**按出资比例自动分解**（读时推导、不落库），比例换算的整数分尾差归顺序位最小的出资项；可显式携带出资分解覆盖——覆盖与 expense / income 对称落子表分解，读回同决策 6 规则；原支出为分解行时退款缺省**无单一账户可继承**（读回 `account_id` 为 `null`，账户口径走派生分解），币种 / 分类 / 商户继承不变；不做按出资项寻址的指定退款（索引寻址脆弱）。
6. **读回与修改**：读回非空分解 ⇔ 存在分解行；分解行的 `account_id` 读回 `null`（AI API / HTTP 契约类型域 `string → string | null`，属已发布契约放宽——CHANGELOG `Unreleased` 记 BREAKING 条目，前端 TS 同步）；`UpdateTransactionInput.account_id` 改 `Option` 全量语义（`None` ⇔ 必须携非空分解；不用空串哨兵）；单 ⇄ 多就地互转走既有修改协议，受影响账户取并集整体重算。
7. **口径**：每条出资按所属 kind 的符号计入该账户 `account_flow`（等价于一组不可见 posting）；受影响账户（写前 ∪ 写后）在既有事务内整体重算，余额缓存机制不变（ADR-0067）；报表按交易计数、不按出资计数；InvolvingAccount 三端口径自动覆盖出资端，账户过滤与 AI 读回对账零新增开发。
8. **读侧（本单只做读侧，录入侧不做、AI 导入与迁移走契约）**：列表分解行显示首条出资账户 + 「等 N 账户」（同账户多条退化「同账户 N 笔」）；详情展示出资项列表（账户 / 扣款标签 / 金额）；退款派生分解带「按比例自动分解」标注。
9. **订单可读性（原型衍生，独立票）**：订单归属以结构化**来源订单号**承载——交易行新增可空列（增量迁移、无存量迁移），AI / HTTP 契约增可选字段（来源元数据，schema 与契约不限 kind，比照商户列先例），导入教学随契约更新；组合支付订单的行尾渲染静态订单徽章（列有值才渲染），详情抽屉增加订单区（行数、合计、按账户聚合的出资构成），订单聚合经只读查询命令按列下推；**不做列表组头分组、不做点击过滤/下钻**——位置性分组在可分页 / 可排序 / 可筛选的列表上必然断裂（跨页断头、重排散开、污染分页计数），订单聚合按需可读即可。

## 理由

- **数据正确性优先**：组合支付下余额与对账口径当前只能靠迁移侧拆行近似，分解进模型是一等解法；迁移侧后续按幂等键重导受影响行即可，成本极低。
- **互斥是唯一无歧义形态**：「主出资 + 分解」让同一事实有两个权威来源；互斥 + 全量修改语义（`None` ⇔ 分解）让契约自证。
- **子表 vs 泛化出资账户列**：分解条数可变、带标签、需要顺序，列方案表达不了；且两概念语义不同源，混用会同时污染两个词条。
- **显式顺序位**：读回顺序是用户可见语义（对账单顺序），不依赖数据库返回顺序。
- **refund 按比例**：对齐「原路退回」直觉、缺省零存储零录入负担；显式覆盖落库与 expense / income 对称，留出精确回退的口子；尾差归顺序位最小出资项，与分期尾差同一哲学（可预测、不随机）。
- **读侧「等 N 账户」**：列表信息密度与可读性的平衡点（原型 A/B/C 三形态对比后收敛），全量分解在详情一层按需可读。
- **来源订单号结构化**：订单归属要跨行聚合，锚点必须可下推、不可被用户编辑破坏；备注文本三重不可靠（可编辑、不可下推、污染交易搜索命中），结构化列是唯一形态。

## 代价

- 契约类型域放宽（`account_id` 可空）是 BREAKING：HTTP / AI 契约消费方须适配，CHANGELOG `Unreleased` 记条目；TS 类型同步。
- 账户一致性守卫从一处变两处（单账户 + 逐条出资），约束违反面变宽（Σ 不等、非正金额、标签超限）。
- 「等 N 账户」损失列表层明细，核对分解需点开详情——接受，理由见决策 8。
- 订单可读性依赖来源订单号列有值：手动记账自然为空（无徽章、无订单区），属可选增强的自然边界；新增一列与一个只读查询命令的维护面。
## 替代方案

- **迁移侧维持跨界拆分行**：临时形态永久化，商品行与真实付款账户永远无法同时成立，行数膨胀——否决。
- **`account_id` 作缺省主出资**：单/多两形态下同字段双语义，写入校验与读回都需区分「没填」与「主出资」——否决。
- **复用 / 泛化 `funding_account_id`**：与 ADR-0096 buy/sell 结算归因语义冲突，且表达不了可变条数与标签——否决。
- **列表组头分组（订单聚合常驻列表）**：位置性约定，跨页断头、排序散开、污染分页计数——否决，改随行徽章 + 详情订单区（决策 9）。
- **refund 按出资项索引寻址**：索引随编辑漂移，脆弱——否决，缺省按比例 + 显式覆盖覆盖两需。
- **备注文本解析订单号**：归属挂在用户可编辑自由文本上，跨行聚合不可下推（全表 LIKE），且交易搜索按备注原文命中、单号污染搜索命中（ADR-0027 同型教训）——否决，改结构化来源订单号列。

## 影响

- 契约：`TransactionInput` / `UpdateTransactionInput` 增可选 `funding[]`（互斥）；`Transaction` 读回增分解数组、分解行 `account_id` 可空（BREAKING 条目）；交易增可选来源订单号字段（增量）；错误码新增互斥与约束违反各条件（zh/en 模板同步）。
- schema：新子表 + 顺序位列与索引；交易新增来源订单号可空列（增量迁移）；均无存量迁移。
- 同步：DomainCommand 载荷随写入命令走，Replay 形态同语义；存活校验扩到出资端账户引用（缺行挂起同现有 ParkedOp 口径）。
- 读闭包纪律：列表（页行集 ↔ 出资子行）、详情读回（主行 ↔ 子行）与订单汇总（同单行集 ↔ 出资聚合）等跨语句读闭包经 ensure_transaction 收同一读事务，配读快照探针测试（删除接线即红）。
- AI 导入教学：随契约同步更新（组合支付落账指引——可分解时携出资分解、来源订单号写入列，不再跨界拆行）。
- 词汇表同步（随本 ADR 入档）：核心交易域新增「出资项（Funding）」「来源订单号（Source Order No）」词条；CONTEXT-MAP 核心交易条目主题追加。
- 实施拆票（sub-issue 挂 #1859）：① 后端核心（契约 + 子表迁移 + 写入协议三路径 + 读回 + refund + 读闭包纪律 + 同步载荷 + AI 教学 + 域单测 / API 集成测试）；② 前端读侧（列表标记 + 详情出资项 + 契约接线 + i18n + Vitest）；③ 订单可读性全链（来源订单号列迁移与契约字段 + 订单汇总只读命令 + 行尾徽章 + 详情订单区，依赖①的读回）。
