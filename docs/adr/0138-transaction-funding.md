# ADR 0138: 多出资方（出资项）与订单购买项——出资分解子表、购买项子表与订单可读性

- 状态：已接受（决策入档；实现随实施票落地）
- 日期：2026-09-28
- 作者：Ledger 项目
- 关联：ADR-0096（出资账户——buy/sell 结算归因，保持专属、不泛化）、ADR-0067（余额缓存整体重算）、ADR-0011（Amount Model 与币种一致性）、ADR-0033 / ADR-0105（写入协议与编排入口）、ADR-0091（多端同步 DomainCommand）、ADR-0008（交易列表服务端分页——「共 N 条」仍按交易计）、ADR-0027（统一模糊搜索——命中面扩至购买项名称，实现须补性能证据）、ADR-0029 / ADR-0052（预算口径）；词汇表：核心交易域「出资项（Funding）」「来源订单号（Source Order No）」「购买项（Purchase Line）」（新）、InvolvingAccount、受影响账户、Transaction Kind Mapping
- 来源：issue #1859（迁移侧 ledger-migrate 组合支付落账需求）triage + grill 三轮（Q1–Q12 全部获维护者确认）+ 抛弃式原型讨论（四出资情形与订单形态，分支 `prototype/1859-multi-funding-readside`）；购买项一轮为维护者与 AI 的 grill 定稿（Q1–Q11 全部获维护者确认）+ 抛弃式原型裁决（交易列表「合并订单的每个购买项各占一行」；原型未提交，折入真实实现后整套移抛弃分支）

## 背景

京东等平台存在组合支付：一笔订单由多个账户共同付款（真实回单：订单 ¥281.60 = 小金库 ¥28.53 + 余额 ¥253.07），且存在预售（定金与尾款跨账户）。迁移侧需把账本行拆到商品级（多品订单要能看到「买了什么、每件多少钱」），但商品行金额只对应部分出资，当前模型要求每笔交易的出资账户唯一——迁移侧以「跨界拆分行」（同一子单在账户边界拆两行、各挂一个账户）临时绕过，属临时形态（两年约 10 单）。

四种出资情形（讨论分类，界面不呈现）：一对一（现状）、一对多（一笔交易多账户出资）、多对一（多行商品同一账户）、多对多（多行商品多账户，其中跨界行需要分解）。本决策让后三种在一行内可表达、且余额与对账口径正确。

另一条线索是**订单可读性**：电商回单（京东等）一单常买多件、叠加各类优惠，订单实付只有一个数，而用户要看的是「这一单买了什么、各是什么分类」。当前模型只有交易行，多商品订单只能把商品名挤进备注，列表上读不出商品与分类的对应关系。用户参考物是平台侧订单列表（订单块内商品各占一行、右侧一个订单总额）；原型阶段比较过的形态——把清单放进详情弹窗、把商品名写进备注列一段文本、树形 / 可展开子行、每个购买项做成独立交易行（各带金额）——都被否决，落点定在交易列表本身。

定稿的用户可见形态：**每个购买项各占一行；订单级字段纵向合并成一格；金额格显示订单实付；分类列逐行显示购买项自己的分类、不合并；备注列一列两用（有清单的行逐行显示商品名 + 件数，没有的行退回原备注渲染）**。

## 决策

1. **数据模型：新子表，不复用出资账户列**。出资分解落独立子表 `transaction_fundings`（交易引用、显式顺序位、账户引用、金额、扣款标签），子行生命周期绑定主行（主行软删即失效，子行无独立软删位）；显式顺序位保读回稳定；存量行零迁移（分解可选，缺省 = 单出资现状）。**否决**把 ADR-0096 的出资账户列泛化复用——那是 buy/sell 的结算归因角色，与本决策的逐条分解语义不同源。
2. **契约互斥**：写入时带非空出资分解 ⇒ 禁止携带 `account_id`（码化报错）；不带 ⇒ `account_id` 必填（现状）。**否决**「`account_id` 作缺省主出资」与「静默忽略」——前者制造双写歧义，后者静默丢数据。
3. **范围**：仅 `expense` / `income` 可带分解；`transfer`（两端已表达）、投资 kind（结算归因见出资账户）、`dividend` / `split` / `convert` 不做；定时计划生成的分期 / 订阅维持单出资（后续按需立单）。
4. **约束束**：每条出资账户准入与 `account_id` 同口径（存在、未软删、币种与交易一致、不折算），**不设账户类型闭集**（credit / debt 可出资，白条场景）；每条金额为正整数分，Σ 出资 == 交易金额；扣款标签自由文本、可选、上限 50 字；允许同一账户多条出资项（定金 + 尾款靠标签区分）。
5. **refund**：关联分解交易的退款缺省**按出资比例自动分解**（读时推导、不落库），比例换算的整数分尾差归顺序位最小的出资项；可显式携带出资分解覆盖——覆盖与 expense / income 对称落子表分解，读回同决策 6 规则；原支出为分解行时退款缺省**无单一账户可继承**（读回 `account_id` 为 `null`，账户口径走派生分解），币种 / 分类 / 商户继承不变；不做按出资项寻址的指定退款（索引寻址脆弱）。
6. **读回与修改**：读回非空分解 ⇔ 存在分解行；分解行的 `account_id` 读回 `null`（AI API / HTTP 契约类型域 `string → string | null`，属已发布契约放宽——CHANGELOG `Unreleased` 记 BREAKING 条目，前端 TS 同步）；`UpdateTransactionInput.account_id` 改 `Option` 全量语义（`None` ⇔ 必须携非空分解；不用空串哨兵）；单 ⇄ 多就地互转走既有修改协议，受影响账户取并集整体重算。
7. **口径**：每条出资按所属 kind 的符号计入该账户 `account_flow`（等价于一组不可见 posting）；受影响账户（写前 ∪ 写后）在既有事务内整体重算，余额缓存机制不变（ADR-0067）；报表按交易计数、不按出资计数；InvolvingAccount 三端口径自动覆盖出资端，账户过滤与 AI 读回对账零新增开发。
8. **出资项读侧（本单只做读侧，录入侧不做、AI 导入与迁移走契约）**：列表分解行显示首条出资账户 + 「等 N 账户」（同账户多条退化「同账户 N 笔」）；详情展示出资项列表（账户 / 扣款标签 / 金额）；退款派生分解带「按比例自动分解」标注。
9. **订单可读性：结构化来源订单号列 + 购买项子表**。订单归属以结构化**来源订单号**承载——交易行新增可空列（增量迁移、无存量迁移），AI / HTTP 契约增可选字段（来源元数据，schema 与契约不限 kind，比照商户列先例），导入教学随契约更新。订单明细以**购买项子表**承载（表名 `transaction_purchases`，与出资项 `transaction_fundings` 同构）：交易引用、显式顺序位、名称、件数、分类引用、可选价格（决策 10）；子行生命周期绑定主行（主行软删即失效，子行无独立软删位）；显式顺序位即对账单顺序（用户可见语义）；存量行零迁移（无购买项 = 现状，行为零变化）。范围：仅 `expense` 可带购买项；`refund` 不另挂清单（退货 / 部分退货的呈现随实施票，依赖本决策的模型形态）；`transfer`、投资 kind、`dividend` / `split` / `convert` 不做。**否决**表名 `transaction_items`——与物品域 `items` 撞名，两个概念不同源；**否决**把商品清单塞进备注文本或新增交易行标量列——条数可变、逐条带分类与件数，列方案表达不了，备注文本不可下推。
10. **购买项价格：可空，存而不显示，不进金额口径**。购买项可携带**商品价格（单价，可空）**——源单只给订单总额时为空，故价格是**可缺的原始凭据**而非必需字段；标价小计由「单价 × 件数」复算，不另存。价格**不在列表 / 卡片 / 详情展示**（沿用决策 13 的呈现形态：购买项行只显示名称 + 件数），也**不进任何金额与折算口径**——交易金额恒为订单实付，价格不参与余额 / 报表 / 预算，也不与实付做勾稽校验。**否决**把购买项价格显示在购买项行：优惠 / 满减下标价之和 ≠ 订单实付是常态，列表上并置两组数字必然引来「加不起来」的疑问（与决策 11 否决按购买项分摊同一根因）。**否决**不留价格：价格可缺但不该缺——它是导入侧拿得到的原始凭据，且让决策 12 的订单级分类选取规则在库内可复算。
11. **报表 / 预算口径：按交易行分类整单计入，不按购买项分类分摊**。分类聚合按交易行分类（金额 = 交易金额）计入，度量口径与分类聚合表达式零改动。**否决读时推导分摊额**（按标价比例分摊、Σ == 订单实付、尾差归最后一件、不落库）：购买项价格可缺（决策 10），分摊基数**只有部分订单有**——按购买项分摊会让报表口径因数据可得性分裂（价格齐全的单按商品归、缺价格的单按整单归），同一张报表里两套口径无法向用户解释；且报表与预算的分类聚合两处均为 SQL 下推 + 覆盖索引钉定查询计划，掺入比例计算必然打掉既定计划，与本项目对聚合性能的量化先例冲突。**否决**把分摊额落库。**代价**：报表一单归一类、列表逐项显示分类，两处口径不一致——由决策 12 使不一致可解释，并在词汇表「购买项」词条显式声明这是设计使然而非数据错误。
12. **订单级分类的选取**：导入按「源单金额最大的商品分类」定交易行分类（导入时源单可见金额；价格齐全时可经「单价 × 件数」在库内复算，价格缺失时按件数退让）；购买项分类只作列表明细。
13. **列表呈现**：每个购买项各占一行、同单各行相邻；订单级列（日期 / 类型 / 商户 / 来源 / 账户 / 金额 / 操作）纵向合并成一格、内容纵向居中；**分类列逐行显示该购买项自己的分类、不做合并**（不作「同单分类一致才合并」的一致性判定——合并格只能写一个值，层级分类下「生活 > 宠物」与「生活 > 日用品」没有任何一个真值能同时代表二者）；备注列一列两用（列名改「商品 / 备注」），有购买项的行逐行显示名称 + 件数、没有的行退回备注原文渲染；账户格在有购买项的行呈现出资构成（逐条账户 + 金额，多条出资才补合计行），无购买项的行沿用决策 8 的「首条 + 等 N 账户」；操作列只留订单级一个。**否决**以详情弹窗为落点、商品名并入备注文本、树形 / 可展开子行、购买项作独立交易行（各带金额）、列表组头分组——位置性分组在可分页 / 可排序 / 可筛选的列表上必然断裂（跨页断头、重排散开、污染分页计数）；本方案的相邻购买项行不新增组头、不改分页计数、重排不散（购买项行由主行派生，不是独立排序单元），故不受该否决约束。**不做**点击过滤 / 下钻。
14. **计数、筛选与搜索面**：分页、`total` 与「共 N 条」按**交易**计（ADR-0008 口径不变），一页视觉行数可多于页大小；筛选与排序作用于交易，命中即整单显示全部购买项行（不裁剪命中行——裁剪会让订单级合并跨度与金额重复错乱）；购买项名称进交易搜索命中面（ADR-0027 的统一模糊语义与「交易搜索按原文命中」口径不变，实现须按项目先例给出 50 万笔库的定量性能证据，必要时补覆盖索引）。一单的购买项行可被页边界切开——**接受**（分页按交易计、单数商品行少、不新增组头行）。
15. **移动档、详情与写入面**：移动档卡片内逐行列出购买项（卡头仍是订单级、金额只出现一次）；只读详情弹窗列购买项清单（与出资项列表同层对称）；触控轴没有悬停，详情是长商品名的全文出口（桌面端长名另经悬停显示全文）。**仅 AI 导入写入、界面只读**，不提供购买项编辑入口，纠错靠按幂等键重导覆盖该订单。**否决**界面编辑（新增表单 / 移动档 / 校验 / 写路径 / 同步冲突面，成本远大于展示价值）。

## 理由

- **数据正确性优先**：组合支付下余额与对账口径当前只能靠迁移侧拆行近似，分解进模型是一等解法；迁移侧后续按幂等键重导受影响行即可，成本极低。
- **互斥是唯一无歧义形态**：「主出资 + 分解」让同一事实有两个权威来源；互斥 + 全量修改语义（`None` ⇔ 分解）让契约自证。
- **子表 vs 泛化出资账户列**：分解条数可变、带标签、需要顺序，列方案表达不了；且两概念语义不同源，混用会同时污染两个词条。
- **显式顺序位**：读回顺序是用户可见语义（对账单顺序），不依赖数据库返回顺序。
- **refund 按比例**：对齐「原路退回」直觉、缺省零存储零录入负担；显式覆盖落库与 expense / income 对称，留出精确回退的口子；尾差归顺序位最小出资项，与分期尾差同一哲学（可预测、不随机）。
- **读侧「等 N 账户」**：列表信息密度与可读性的平衡点（原型 A/B/C 三形态对比后收敛），全量分解在详情一层按需可读。
- **来源订单号结构化**：订单归属要跨行聚合，锚点必须可下推、不可被用户编辑破坏；备注文本三重不可靠（可编辑、不可下推、污染交易搜索命中），结构化列是唯一形态。
- **列表是用户唯一会看的地方**：详情弹窗与备注文本两个落点都被用户否决；购买项行与订单级合并格让「这一单买了什么」在不点开任何东西的前提下可读。
- **逐列判定合并，分类列不合并**：订单级字段在订单内天然同值，合并无损；分类在订单内可以不同，合并必然丢信息，逐行显示是唯一无损形态。
- **记账与明细分层**：交易行仍是唯一的金额与统计单元（余额、报表、预算、InvolvingAccount 全不动），购买项只是它的人可读明细——口径不动是这次改动能落在读侧与呈现层的根本原因。
- **只读 + 导入写入**：购买项的主入口是读回单，导入侧一次解析即可覆盖，用户不需要在应用里做录入动作；编辑面真有需求时另立票。

## 代价

- 契约类型域放宽（`account_id` 可空）是 BREAKING：HTTP / AI 契约消费方须适配，CHANGELOG `Unreleased` 记条目；TS 类型同步。
- 账户一致性守卫从一处变两处（单账户 + 逐条出资），约束违反面变宽（Σ 不等、非正金额、标签超限）。
- 「等 N 账户」损失列表层明细，核对分解需点开详情——接受，理由见决策 8。
- 订单可读性依赖来源订单号列有值：手动记账自然为空（无订单归属标注），属可选增强的自然边界；新增一列与一张子表的维护面。
- **报表与列表口径双轨**：一单归一类（报表）vs 逐项分类（列表）——靠决策 12 的订单级分类选取规则与词汇表声明使其可解释。
- **一页视觉行数大于页大小**：「共 N 条」按交易计，一页可能铺出远超页大小的行。
- **跨页断头**：一单的购买项行可被页边界切开（决策 14）。
- **长商品名在列表上被截断**：桌面端靠悬停显示全文，触控轴靠详情弹窗，两处都要做（原型只有 2 行截断、无全文出口，按用户可见缺陷处理）。
- **搜索命中面扩到子表**：既有搜索覆盖索引的查询计划需重新评估并给出证据。
- **价格可缺 ⇒ 分摊基数覆盖率不完整**：部分订单只有总额、没有单价；本次已否决按购买项分摊（决策 11），该代价只在将来重启分摊时兑现——届时须先接受「部分订单无基数」或补录（重导 / 逐笔修改）。
- **订单级分类规则的复算依赖价格可得性**：价格齐全时可经「单价 × 件数」在库内复算校验，价格缺失时只能按件数退让（决策 12）。
- **schema 就地扩 V034**：本地已跑过 V034 的开发库不会自动获得新子表，开发期需重建库（未发布窗口内，不影响任何已发布版本的使用者）。

## 替代方案

- **迁移侧维持跨界拆分行**：临时形态永久化，商品行与真实付款账户永远无法同时成立，行数膨胀——否决。
- **`account_id` 作缺省主出资**：单/多两形态下同字段双语义，写入校验与读回都需区分「没填」与「主出资」——否决。
- **复用 / 泛化 `funding_account_id`**：与 ADR-0096 buy/sell 结算归因语义冲突，且表达不了可变条数与标签——否决。
- **列表组头分组（订单聚合常驻列表）**：位置性约定，跨页断头、排序散开、污染分页计数——否决，改列表内逐购买项行 + 详情购买项清单（决策 13 / 15）。
- **refund 按出资项索引寻址**：索引随编辑漂移，脆弱——否决，缺省按比例 + 显式覆盖覆盖两需。
- **备注文本解析订单号**：归属挂在用户可编辑自由文本上，跨行聚合不可下推（全表 LIKE），且交易搜索按备注原文命中、单号污染搜索命中（ADR-0027 同型教训）——否决，改结构化来源订单号列。
- **按购买项分摊金额（读时推导 / 落库）**：要改报表与预算口径点、无标价基数、打掉覆盖索引计划——否决（决策 11）。
- **商品名并入备注文本**：不可下推、不可聚合、污染交易搜索命中——否决（与「备注文本解析订单号」同型）。
- **树形 / 可展开子行**：多一层交互才看得到明细——用户否决。
- **购买项作独立交易行**：每个购买项各带金额会让余额与报表失真（优惠后分摊不成立），且与真实付款账户无法同时成立——否决（与「迁移侧维持跨界拆分行」同型）。
- **详情弹窗为购买项落点**：用户否决。
- **表名 `transaction_items`**：与物品域 `items` 撞名——否决。
- **界面可编辑购买项**：写路径与校验面成本远大于展示价值——否决（决策 15）。
- **把购买项价格显示在购买项行**：优惠 / 满减下标价之和 ≠ 订单实付是常态，列表并置两组数字必然引来「加不起来」的疑问——否决（决策 10），价格存而不显示。
- **按购买项行计数分页**：分页锚点下沉到展开层，排序与合并语义复杂化，且与报表「按交易」口径分家——否决（决策 14）。

## 影响

- 契约：`TransactionInput` / `UpdateTransactionInput` 增可选 `funding[]`（互斥）；`Transaction` 读回增分解数组、分解行 `account_id` 可空（BREAKING 条目）；交易增可选来源订单号字段（增量）；写入与读回（交易输入 / 修改输入 / 读回交易行 / 同步归一化载荷）各增购买项数组（含可空价格），一并进 AI / HTTP 契约（只增不改，非 BREAKING）；错误码新增互斥与约束违反各条件（zh/en 模板同步）。
- schema：V034 就地扩为「出资项 + 购买项」两张子表（未发布窗口内不新开版本号，文件名仍为出资项语义）；出资项子表带顺序位列与索引；购买项子表带顺序位与可选价格列（可空）；交易新增来源订单号可空列（增量迁移）；均无存量迁移。模型文档的 Migration 索引行与实体关系图随实施同步——此刻不改，schema 未落地时索引与图以 migration 为唯一事实来源。
- 同步：DomainCommand 载荷随写入命令走，Replay 形态同语义；购买项随交易命令载荷走（无新实体标签、无协议改动）；存活校验扩到出资端账户引用（缺行挂起同现有 ParkedOp 口径）。
- 读闭包纪律：列表（页行集 ↔ 出资子行 / 购买项子行）、详情读回（主行 ↔ 子行）与订单汇总（同单行集 ↔ 出资聚合）等跨语句读闭包经 ensure_transaction 收同一读事务，配读快照探针测试（删除接线即红）。
- 报表 / 预算：零改动（决策 11）。
- AI 导入教学：随契约同步更新（组合支付落账指引——可分解时携出资分解、来源订单号写入列，不再跨界拆行；购买项字段与订单级分类选取规则，**价格拿不到就留空、不猜不编造**，不再把商品名写进备注）。
- 前端：出资项读侧呈现（列表标记 + 详情出资项）；购买项的列合并与「一列两用」折入生产列构造器（原型规则转正）、移动档卡片与只读详情各增购买项清单、长名悬停全文；i18n 文案（列名、件数、空态）随键值新增。
- 词汇表同步（随本 ADR 入档）：核心交易域新增「出资项（Funding）」「来源订单号（Source Order No）」「购买项（Purchase Line）」词条；CONTEXT-MAP 核心交易条目主题追加。
- 实施拆票（sub-issue 挂 #1859）：① 后端核心（契约 + 子表迁移 + 写入协议三路径 + 读回 + refund + 读闭包纪律 + 同步载荷 + AI 教学 + 域单测 / API 集成测试）；② 前端出资项读侧（列表标记 + 详情出资项 + 契约接线 + i18n + Vitest）；①② 已随 #1876 / #1877 落地。③ 订单可读性全链（来源订单号列迁移与契约字段 + 购买项子表迁移与契约字段 + 读回与读闭包纪律 + 搜索命中面与性能证据 + 导入教学 + 域单测 / API 集成测试）；④ 前端订单可读性呈现（列表逐购买项行 + 订单级合并格 + 移动档卡片 + 详情购买项清单 + 长名全文 + i18n + Vitest）。退款 / 部分退款的购买项呈现随③另立票。
