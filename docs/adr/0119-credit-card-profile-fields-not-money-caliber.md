# ADR 0119: 信用卡账户档案——额度与账单日只作档案与展示，不进任何金额口径

- 状态：已接受
- 日期：2026-09-14
- 作者：Ledger 项目
- 关联：spec #1327（同号实施）；词汇表：参考数据与设置域「信用卡档案」；修订 ADR-0090 决策 6（紧凑契约方言 22KB → 24KB、OpenAPI 文档 48KB → 50KB）；类型边界见 ADR-0053（`credit` 仅信用卡、`debt` 承载一切欠款）；口径相邻见 ADR-0067（余额缓存）与 ADR-0096（出资账户准入闭集）

## 背景

`credit`（信用卡）自 V001 起就是账户类型闭集的一员，DDL 注释也写明「余额可为负表示欠款」，但全仓库没有任何额度、账单日、还款日字段——它今天只是一个带固定列的账户类型标签。`debt`（房贷 / 车贷）同样零专有属性（ADR-0053 决策 3：不建计息机制）。

用户的两件事因此答不出来：

1. **这张卡还剩多少额度？** 账本里有实时余额，却给不出「可用额度 / 使用率」这个一眼可见的信号，用户只能切到银行 App 查，两边对不上时无从判断。
2. **账单日是哪天、下次还款日是哪天？** 这是持卡人真正的行动节点（什么时候出账、最晚什么时候还），账本对此一无所知，也就无从留档与查看。

## 决策

### 1. 范围 = 档案 + 展示（A 档）

只做「三个档案字段 + 两个展示面」。**明确不做**按账单周期切分流水（已出 / 未出账单金额）、还款提醒、与定时计划域联动自动还款——账单明细银行 App 已有，而账单周期派生要先定「入账日 vs 交易日期」「退款 / 分期 / 溢缴款怎么进账单」一整套口径，成本远大于收益，留作独立票。

### 2. 三个扁平可空列，约束落域层

`accounts` 加三列（信用额度整数分、账单日、还款日），新增只增迁移，无数据迁移、无默认值；三字段彼此独立可空，旧库里既有信用卡账户不填也能照常编辑。**只被 `credit` 账户携带**、各字段范围校验（额度 > 0、日子 1–31）由域层守卫单点承担，不写进 schema：`ALTER TABLE ADD COLUMN` 无法追加多列 CHECK，「仅信用卡可携带」本就表达不了；范围校验也不落列 CHECK，使校验保持单源，不出现第二套口径。

### 3. 额度是档案，不进任何金额口径

额度、账单日、还款日不参与余额、余额缓存、净资产、折算与报表任何路径——「我还欠多少」仍由余额唯一回答，信用卡欠款就是账户负余额。派生量（已用 / 可用 / 使用率 / 下次账单日 / 下次还款日）**不落库**，与余额同源现算：落库会引入第二个需要一致性维护的派生值，与 ADR-0067「缓存行缺失报码化错误、不静默回退」的纪律冲突。

### 4. 可用额度 = 额度 + 余额（银行 App 口径）

- 已用额度 = `max(0, −余额)`（余额为正即溢缴款，此时已用为 0）；
- 可用额度 = 信用额度 − 已用额度 + 溢缴款，化简即 **信用额度 + 余额**；
- 使用率 = 已用 ÷ 信用额度（超额使用时报 > 100%，可用额度同时为负——如实呈现，不钳到 0）。

**实现期修正留痕**：spec 初稿写作「可用额度 = 额度 + `max(0, 余额)`」，该式漏掉欠款项（有欠款时会显示满额度），由前端派生纯函数的矩阵测试抓出并改为上式；spec 正文与词汇表均已同步。

### 5. 日字段存声明值，月末钳制只发生在派生

存 1–31 的「每月第 N 日」**声明值**，不强制账单日与还款日的先后（银行实际存在「账单日 25 日 / 还款日 14 日」的跨月形态，强制同月先后会把这批卡判为非法输入）；当月没有该日时取当月最后一天，「下次 X 日」取距今天最近的该日（今天就是该日则取今天），按**本地日历日**语义。钳制与「下次」都只作用于展示派生，不进存储。用「账单日 + 免息期天数」表达还款日被否决：用户是从银行 App 上直接读到「账单日 5 日 / 还款日 25 日」的，让用户反推免息期是逆着用户认知建模，且各家银行对月末的处理不同，会把银行的特例变成我们的计算歧义。

### 6. 展示密度：不新增列、不新增弹层

账户列表**只在既有的余额单元格内**为信用卡行加一行 12px 小字（已用百分比；仅已用 > 0 时显示；≥90% 用警示色），账单日与还款日只以编辑弹窗内的三个输入 + 只读摘要（额度用量、下次账单节点）出现。桌面五列与移动档三列结构一字不动：移动档账户页（issue #847）的设计目标是「328px 内容宽内无横向滚动、逐行可读」，把额度用量 + 账单日 + 下次还款日全塞进行内小字会把它压成三行。**选择账户的下拉不显示额度**：额度与余额含义不同，并排出现易被读成两套余额。日期用 ISO 短格式（界面语言不影响绝对日期格式，沿用既有约定），不给「下次账单日」造第二套本地化日期渲染。

### 7. 契约面：只增字段

三个字段进账户同步命令载荷（创建与更新两形态）与 HTTP 账户端点，**只增不改**：旧日志缺三键时按「未设置」承接（与 V023 出资字段的旧载荷纪律同款）；更新路径用三态语义（键缺席 = 不改、`null` = 清空、给值 = 落定），需要显式反序列化区分「缺席」与「null」（serde 对 `Option<Option<T>>` 默认把两者折叠）。AI 可读也可写，知识节写明「只是档案、不参与余额与折算口径」。账户类型**仍不可改**（既有约束不动），因此档案字段挂不到非信用卡账户上，域层直接拒绝。

### 8. 契约体积预算提高（修订 ADR-0090 决策 6）

三个字段跨 `Account` / `AccountInput` / `AccountUpdateInput` 三个 schema，字段描述先收敛到单行（已削 374 字节、无冗余可再削）后，紧凑契约方言实测 23192 字节仍越 22KB、OpenAPI 文档 49312 字节越 48KB，本票提至 **24KB / 50KB**。不选「删描述换预算」：额度是档案字段，「不参与余额与净资产」的语义必须写在契约里让 AI 读到，删掉描述会让 AI 把额度误读成余额口径。

## 考虑过的替代方案

- **B 档：账单周期派生**（已出 / 未出账单金额、按账单期筛选）——否决（本轮）：要先定一整套账单归属口径，成本远大于收益，账单明细银行 App 已有。
- **C 档：提醒 / 自动还款**——否决（本轮）：要牵动定时计划域的形态与调度语义，属独立票。
- **侧表 `credit_card_details`（按类型开扩展表）**——否决：账户域无扩展表先例（仓内先例在定时计划域），三个字段同属一个类型、无多形态歧义，加列让 AI 字典、同步载荷与前端字典继续共用单一读取模型、零 join；代价是「非信用卡三列为空」只能落域层守卫，这是明示接受的。
- **额度计入净资产 / 用额度算「可用资金」**——否决：额度是银行授予的临时可用性、不是资产；计入会让净资产因一次提额而虚增，破坏 ADR-0020 的忠实求和口径。
- **已用额度由用户手填**——否决：立刻产生与余额不一致的第二事实源。
- **共享额度（一额度多卡，额度组实体）**——否决：要把档案字段升级成实体；共享额度的用户自行只填其中一张卡。
- **一卡多额度（双币卡两币种额度）**——否决：账户是单币种实体，双币卡按币种拆成两个账户。
- **额度只存数字、不绑币种**——否决：「额度 50000」不知币种，跨币种折算立刻产生歧义。
- **列表行内小字放全量信息 / 新增列 / 账户详情页 / 独立只读弹层**——否决：分别撞上移动档密度、其他类型空列、无详情页的信息架构、多一个弹层与菜单项；折中为「列表一行百分比 + 编辑弹窗摘要」。
- **「账单日 + 免息期天数」表达还款日**——否决（见决策 5）。
- **削契约描述以保住原预算**——否决（见决策 8）。

## 后果

- **净资产、余额缓存与 `account_flow` 符号矩阵零改动**：额度不进任何金额路径，信用卡欠款照旧拉低净资产。
- **发布边界**：新增迁移只增列、不改已发布迁移与字段含义，不产生 BREAKING 条目（最新已发布 tag 覆盖到 V019，本次为 V026）。
- **契约体积**：紧凑方言与 OpenAPI 文档预算各提 2KB（ADR-0090 决策 6 的修订注记同步记录）。
- **已知边界**：额度使用率阈值（90%）是常量、不做设置项；百分比不随金额隐私模式掩码（掩码对象是金额，比例不泄露账户规模）；账户类型不可改的既有约束意味着「普通账户改成信用卡」仍须新建账户。
- **验收含额度口径负向条目**：改 / 清额度不得改变账户余额（域单测断言，删除该守卫即红）。
