# 备份/恢复采用文件级快照而非语义导出

用户需要手动备份/恢复界面。数据库是单一 SQLite 文件（`ledger.db`，15 张表，含投资持仓与定时交易），此前无任何用户可操作的备份设施。

**决策**：

- 备份 = 文件级整库快照，zip 包装（`ledger.db` + `backup.json` 元数据：备份时间、应用版本、schema 版本 `user_version`）；也兼容恢复裸 `.db` 文件；
- 一致性由 SQLite 在线备份（`VACUUM INTO`）保证，不停写、无需关闭应用；
- 恢复 = 替换式还原：提取到临时文件 → `PRAGMA integrity_check` + schema 版本校验 → 替换原库；恢复前自动把当前库另存为 RestoreSafetyBackup（`restore-safety-*.db`，位于应用数据目录）；
- schema 版本策略：备份旧于当前 → 恢复后自动跑迁移升级；备份新于当前 → 拒绝并提示升级应用；
- 恢复期间持有全局数据库连接锁，阻塞 IPC 与本地 HTTP API 的并发写，避免恢复过程中被写入污染；
- 恢复成功后应用自动重启（`AppHandle::restart()`），规避共享连接指向旧文件的残留状态；
- 备份文件明文，不加密；
- 备份目录为用户可配置的设备本地偏好（localStorage），不进数据库、不随备份迁移。

**备选方案与理由**：

- *语义级 JSON 导出*：可读、可选择性恢复，但实现复杂、易遗漏表间关联（持仓、定时交易期次），且与 AI 导入通道职责重叠；"备份"的语义是快照还原，"导出"是另一个功能。→ 选文件级。
- *热重载不重启*：需要把全局共享连接 `Arc<Mutex<Connection>>` 重构为可替换的连接管理器，横跨 IPC 命令层与 axum State；个人记账应用重启成本 <1 秒。→ 选重启。
- *严格版本相等才允许恢复*：用户升级应用后自己的旧备份即作废，不合理；迁移框架本就支持升级。→ 选"旧→新允许、新→旧拒绝"。
- *zip 口令加密*：需要口令存储/找回的完整产品设计，MVP 不引入。→ 明文 + 界面提示妥善保管。
