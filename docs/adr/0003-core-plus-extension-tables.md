# ADR 0003: 从完全独立模型调整为核心表 + 扩展表

- 状态：已接受
- 日期：2026-07-07
- 作者：Oz / Ledger 项目

## 背景

在 ADR 0002 中，我们曾决定采用完全独立模型：每类计划各自有独立的计划表和期次表（共 6 张表）。但在产出具体文档后，发现通用字段（如 `status`、`account_id`、`amount_cents`、`currency_code`、同步字段等）在三张计划表和三期次表中大量重复。

这促使我们重新审视方案：

- 方案 A：维持完全独立模型（6 张表）。
- 方案 B：核心表 + 扩展表（5 张表：1 核心计划表 + 1 统一期次表 + 3 扩展表）。

## 决策

采用方案 B：核心表 + 扩展表。

- 核心表 `scheduled_transactions`：存放通用字段、`kind` 区分类型、`status` 生命周期。
- 统一期次表 `scheduled_transaction_occurrences`：所有类型共享。
- 扩展表 `installment_plans` / `subscription_plans` / `scheduled_transfer_plans`：存放类型特有字段。

## 理由

1. **减少字段重复**
   - 通用字段（如账户、金额、币种、周期、同步字段）只写一次，避免三份重复。
   - 迁移、索引、同步逻辑也相应减少。

2. **期次表统一**
   - 期次本质是“某计划的一次执行实例”，其状态、日期、交易 ID 与类型无关。
   - 统一期次表避免了三张结构相同的表，跨类型查询也不需要 UNION 三对表。

3. **保留类型边界**
   - 扩展表仍然让分期、订阅、定时转账的特有字段和约束相互隔离。
   - 例如 `installment_plans.total_amount_cents` 必填，而 `subscription_plans` 没有该字段。

4. **UI 仍可独立**
   - 应用层根据 `scheduled_transactions.kind` 分发到不同的 UI 和命令，数据模型与表现层解耦。
   - 这回应了最初选择独立模型的核心动机：UI 按类型单独设计。

5. **查询更简洁**
   - 查“所有待执行”只需 JOIN 核心表 + 期次表。
   - 只有需要类型特有字段时才 JOIN 扩展表。

## 代价

1. **核心表仍有 `kind` 字段**
   - 没有完全摆脱“类型判别”，但 `kind` 只用于路由和扩展表选择，字段本身很小。

2. **扩展表与核心表必须同步创建/删除**
   - 创建分期计划时，必须同时创建 `scheduled_transactions` 和 `installment_plans`。
   - 删除时也需要同时处理（软删除）。

3. **扩展表字段为空时仍需存在一行**
   - 例如 `subscription_plans` 目前只有 `counterparty`，但每创建一条订阅都要有一行扩展记录。

## 替代方案

- 方案 A（完全独立）：类型边界最彻底，但通用字段重复三份，维护成本高。
- 方案 C（单张大表 + `kind`）：字段最集中，但可空字段多、CHECK 约束复杂，后续扩展容易让表变臃肿。

## 影响

- `docs/model/scheduled-transactions/index.md` 更新为核心 + 扩展表结构。
- `installment.md` / `subscription.md` / `scheduled-transfer.md` 更新为只描述类型特有字段和行为。
- `CONTEXT.md` 恢复 `ScheduledTransaction` 作为核心术语，三种类型作为其业务形态。
- 后续数据库迁移需要新增 5 张表（1 核心 + 1 期次 + 3 扩展），而不是 6 张。
- 应用层需要保证核心表与扩展表同时创建和更新。

## 结论

核心表 + 扩展表在“类型独立”和“避免重复”之间取得了更好的平衡。它既保留了按类型独立设计的灵活性，又避免了完全独立模型带来的大量重复字段和表。对于当前三种业务差异明显但通用字段众多的场景，这是更合适的选择。
