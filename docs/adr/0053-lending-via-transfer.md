# ADR-0053: 个人间借贷复用转账与债权/债务账户——不新增交易类型

- 状态：已接受
- 日期：2026-09-01
- 作者：Ledger 项目
- 关联：ADR-0011（金额模型与 kind→度量矩阵）、ADR-0020（净资产口径）、ADR-0026（余额调整经黑洞转账）、ADR-0028（商户收口）

## 背景

账户类型闭集自建库起就含 `debt`（负债）与 `receivable`（借出款）两个变体，但系统从未为个人间借贷（朋友/家人之间的借钱、还钱）提供任何专门行为——两种类型只有枚举与文案标签，无表单、无报表、无识别。「借入/借出如何处理」因此成为悬而未决的建模问题：是补一套借贷新交易类型（kind 闭集 8 种扩容），还是以现有机制的使用约定承载？

## 决策

1. **不新增交易类型，kind 闭集保持 8 种**：借出 = `transfer` 自资金账户转入 `receivable` 账户；借入 = `transfer` 自 `debt` 账户转入资金账户；还款/收回 = 反向转账，部分还款即多笔。账户实时余额即对该对手方的未清金额。符号沿用建库约定：receivable 为正、debt 为负；建账时已存在的借贷经期初余额表达。
2. **一人一账户**：借贷对手方（人）由账户承载、账户名即人名（约定「借出·张三」/「借入·李四」）。不为对手方引入商户或独立的人员字典——transfer 不可携带商户（ADR-0028 将交易对手方收口为商户，且仅限 income/expense/refund 可携带），商户语义（花给谁/收入来自谁）与借贷对手方（谁欠我/我欠谁）不同构。
3. **利息按普通收支**：收息记 `income`、付息记 `expense`，与本金转账分笔；不建计息机制。
4. **坏账核销 = 余额调整归零**（ADR-0026 机制）：对方确定不还时把 receivable 余额校准到 0，净资产忠实下降、**不计收支**——坏账是资产减值而非消费，与「资本变动不计经营收支」（ADR-0011 度量矩阵把 buy/sell 排除在 expense_net 外）同一哲学；不以黑洞支出把核销伪装成消费。
5. **入口 MVP 零代码**：现有转账表单 + 手动建账户即可完成全部操作；专门的借入/借出/还款表单形态留待真实痛点出现（届时本质是前端装配矩阵加行，不动本决策）。
   - **更新注记（issue #374，2026-09-01）**：专用入口已兑现——「记一笔」新增「借出」「借入」入口，表单方向切换覆盖借出/收回/借入/还款四方向，列表对借贷转账显示专属文案。纯呈现层与录入便利：不新增 kind、账务仍是 transfer + receivable/debt 账户（决策 1 不变），借贷方向是账户类型的**派生视角**、识别唯一依据是两端账户类型（方向判定收口单一纯函数，录入表单/列表标签/编辑形态识别三处共用），提交产物与转账同构，schema、后端、AI 导入契约零改动；账户实时余额继续承担未清金额口径。本条其余内容（零代码起步的历史边界）保留存照。
6. **AI 导入按约定落账**：借贷落账约定补进**导入知识**（入口提示词保持入口骨架、约定细节只在知识侧——AI 导入域 AIPrompt 的既有分界）：建/复用 receivable/debt 账户（一人一户）+ transfer，防止 AI 把借出错记为 expense；openapi 契约无需改动（账户创建与转账本就可达）。

## 理由

- **为什么复用 transfer 而不是新增 kind**：借入/借出/还款在账务上与转账同构——都是两账户间的资金移动，新 kind 表达不出 transfer 之外的任何信息；而扩容闭集要付全链路成本（kind→度量符号矩阵、行为层分派、前端表单、AI 契约、搜索与过滤）。更关键的是复用即继承：涉及账户过滤、交易搜索、定时还款计划（scheduled_transfer 形态）、余额校准、净资产口径全部对借贷款自动成立。
- **为什么一人一账户而不是单账户+备注**：个人间借贷的核心诉求是「每人一本账」（张三还欠我多少）；账户是现有体系里唯一能按对手方隔离余额且不破坏 kind 闭集的载体。
- **为什么核销不计收支**：把坏账记成 expense 会让月度支出突增，污染消费分析口径；净资产已经忠实反映损失，收支口径守住「经营收支」边界。
- **为什么值得立此存照**：`debt`/`receivable` 两个类型存在却零专门功能，未来读者（与 AI 助手）必然会问「要不要补一套借贷新交易类型」——本 ADR 就是那个问题的答案。

## 代价

1. 借贷专属的界面便利（快捷入口、按人聚合视图）不存在，操作路径与普通转账无异；接受为 MVP 取舍。（2026-09-01 起快捷入口与四方向录入/文案已补，见决策 5 更新注记；按人聚合视图仍不存在，账户余额即对账口径。）
2. 「借出·张三」命名约定依赖用户自觉；对手方增多会让账户列表变长。
3. 若未来出现两账户转账表达不了的借贷形态（多人担保、抵押等），需重开本决策并扩容 kind 闭集。
