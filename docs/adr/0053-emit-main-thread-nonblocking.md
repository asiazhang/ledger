# ADR-0053: 写后失效信号改为主线程非阻塞投递——emit 不再阻塞写请求

- 状态：已接受
- 日期：2026-09-01
- 作者：Ledger 项目
- 关联：spec #364 / issue #365；ADR-0044（失效信号发射收单点）、ADR-0032（连接层统一写入口）、ADR-0012（参考失效信号）、ADR-0031（价格失效信号）、issue #129（备份信号）

## 背景

AI 批量导入（HTTP 壳写端点）期间整个应用界面永久卡死（spec #364 事故）：写库成功后的失效信号发射走「写线程同步 `app.emit`」，而 tauri 的 `app.emit`（`tracing` feature 下 `eval_script` 走 `rx.recv()` 等回执）内部**同步等待主线程**执行 JS 注入，并在等待期间**持有 `webviews_lock`**。此时主线程若恰在处理 WebKit URL scheme 回调（前端重拉参考表）也要抢同一把锁——主线程等锁、写线程等回执，互等成环，永久死锁。前端「收到 `ledger:changed` → 重拉参考表」是唯一刷新源（无 pull 兜底），一卡即永久。

死锁的三个前提：写线程就地发射、`app.emit` 持锁等回执、主线程可能持锁回调。三者断其一带入本决策。

## 决策

1. **发射改为主线程非阻塞投递**：信号发射的机制收口点（`events.rs` 的 `emit_*` 三入口与深路径镜像句柄 `emit_backups_changed_current`，全部汇聚到唯一的 `post_emit`）从「写线程同步 `app.emit`」改为 `AppHandle::run_on_main_thread` 包裹 emit——tauri `send_user_message` 只把任务投进主线程事件循环队尾、不等回执，调用即返回。emit 在主线程自己的事件循环里执行时，主线程不与自身抢 `webviews_lock`，死锁闭环从机制上消除。
2. **机制收口单点，一处改动全壳生效**：IPC 壳（命令线程经 `signals::emit_for`）、HTTP 壳（tokio worker 经 `emit_after_write`）、深路径镜像句柄（连接层写入口提交点经 `EVENT_APP`）三条发射路径共用 `post_emit`，符合 ADR-0044「机制收口单点」结构。
3. **不阻塞 + 允许延迟、不允许丢失**：写请求在入队后立即返回；信号按入队顺序在主线程依次执行，毫秒级延迟可接受——前端消费本就是异步重拉（stale-while-revalidate 保留旧数据）；发射最终到达，不允许永久丢失。投递失败（应用退出中事件循环已关）与发射失败一样静默忽略，不影响写事务结果（沿用 ADR-0044「发射失败静默」语义）。
4. **知识层零改动**：`signals` 映射（WriteOp / Signal 闭集、`signals_for` 判定、WriteEvidence 归一化）、事件名常量、两壳声明表与 `signals_cross_check` 交叉核对全部不动——本次只改「怎么发」，不改「谁发什么」。
5. **不改 tauri 内部与依赖**：不 patch `app.emit` / `eval`，不换 WebKit 消息通道，不动 Cargo 依赖（tauri 2 保持 `tracing` feature）。

## 理由

- **为什么投递而不是就地发射**：死锁前提「写线程持锁等回执」被整体移除——写线程只做一次非阻塞入队，不再接触 `webviews_lock`；主线程在自己的循环里执行 emit，自身线程上 `run_on_main_thread` 语义为内联顺序执行，无自等待。这是对死锁成因的机制级消除，而非对单个调用点的规避。
- **为什么单点收口**：散在三个壳各自的发射点上改，必然漂移；ADR-0044 已把发射收拢到 `events.rs`，本决策在既有结构上只动机制一处，知识层测试（`signals` 映射逐写操作断言、`signals_cross_check` 双向核对）原样构成回归防线。
- **为什么静默失败可接受**：信号是写后通知，不参与写事务语义；应用退出中丢一条刷新信号与既有「emit 失败不影响写结果」语义一致。

## 代价

1. **信号到达时机异步化**：从「写返回时已发出（但阻塞）」变为「写返回后队列到达（不阻塞）」。前端重拉本就是异步消费，可感知差异仅毫秒级延迟；代价是后端不再对「信号已送达前端」提供同步保证。
2. **主线程事件循环承担入队任务**：每条写后的 emit 在主线程执行一次（原本也要在主线程执行 JS 注入，总量不变），仅排队开销新增，可忽略。
3. **机制层回归保护有限**：死锁是跨线程时序问题，且 tauri `AppHandle` 在无运行时的单测环境中不可构造（不引入 tauri `test` feature 以遵守「不动 Cargo 依赖」），无法在单测里稳定复现或断言投递时序；保护依赖知识层既有测试全绿 + 本 ADR 与 `post_emit` 单点注释锁死「必须经投递」的约定，代码评审据此把关。

## 替代方案

- **去掉 tauri `tracing` feature 让 `eval` 走非回执路径**：动 Cargo 依赖且瓦解同步链路可观测性，死锁前提仍在另一条回执路径上重建，否决。
- **写线程丢弃同步语义改为「发射线程池」/ 自建通知队列**：tauri 主线程队列已是现成的单一投递通道，自建队列多一份线程生命周期与退出排空负担，收益为零，否决。
- **前端为参考表加重拉兜底（pull / 定时轮询）**：只缓解症状——写线程仍会被回执挂住，HTTP 写请求依旧可能超时；机制缺陷必须在发射侧消除，否决（前端唯一刷新源结构保持）。
- **只在 HTTP 壳改异步发射**：死锁同样可由 IPC 写命令触发（用户故事 5），双壳 + 深路径必须同治，否决。

## 后果

1. AI 导入等长任务写库期间界面保持响应：按钮、视图切换、其他 IPC 全部不受写后信号影响；`--dry-run` 预览同样不卡界面。
2. 三条发射路径（IPC / HTTP / 深路径）行为一致：写请求及时返回、信号最终到达、失败静默，无壳间漂移。
3. 信号映射知识层与交叉核对测试零改动全绿，ADR-0044 的「知识 / 机制」两半分界在机制侧得到强化（机制层自此含投递语义）。
4. **已知残留（不在本决策范围）**：行情同步的进度事件（`sync-instruments:progress`）不经失效信号映射，仍在后台同步线程上就地同步 `app.emit`——与本决策消除的「非主线程持锁等回执」前提同类，同步进行中界面仍可能同样卡死。同一投递模式可复用，另立 issue 跟踪（issue #369）。
