# ADR 0015: 「已投资 = 当前持仓」口径 + 全量修字典 / 增量刷价格职责切分

- 状态：已接受
- 日期：2026-08-27
- 作者：Ledger 项目

## 背景

投资界面调整（issue #101）之前，刷新股票行情的入口只有设置页的"股票标的全量同步"：每次把沪市/深市/港股全部股票从东方财富全量拉一遍（分页拉取，数百次 API 请求），代价高，且入口与投资界面割裂。同时，投资页"盈亏"子视图只展示卖出时固化的已实现盈亏，用户看不到当前持仓的市值与未实现盈亏。

本次调整引入两个新概念，都需要在落地前锁定术语与口径，否则后续消费方（"只看持仓"过滤、增量同步、持仓概览）各说各话会再次漂移：

1. **"已投资"到底指什么**——是"买过就算"（含已清仓），还是"当前仍持有"？
2. **两类同步的职责边界**——全量同步是否还要继续承担"刷价格"，还是把价格刷新拆成独立的轻量增量同步？

## 决策

1. **“已投资” = 当前持仓（术语定为“持仓标的” InvestedInstrument）**。判定谓词为“有当前持仓”，即 `security_lots.remaining_quantity > 0`（等价于 `v_holdings` 视图有行）、且排除软删除账户的批次；**不含已清仓标的**。同一口径单点定义（投资域 `investment::predicates` 的 `INVESTED_EXISTS` 谓词，#401 域归位前住 `commands::investment`，与 `v_holdings` 视图口径一致），同时驱动四处：
   - `list_instruments` 返回的 `invested` 派生布尔列（issue #102）；
   - 标的页“只看持仓”过滤参数 `only_invested`（issue #102）；
   - 增量同步的标的集合（issue #103）；
   - 盈亏页持仓概览（issue #110）。
2. **同步职责切分为"全量修字典 / 增量刷价格"**。
   - **全量同步**（`sync_instruments`，现有行为）：修标的字典——拉取沪深港全部股票，新增/更新 `instruments` 与价格。
   - **增量同步**（`sync_holding_prices`，新增，UI 文案"同步持仓价格"）：只刷价格——从当前持仓（口径同决策 1）收集股票类标的，按 `(market, symbol)` 构造东财 secid（`1.600519` / `0.000001` / `116.00700`）批量查询（`ulist.np/get`，约 50 只/请求，API 访问量从数百次降到个位数），**仅 upsert `market_prices`**：不增删、不改 `instruments` 的名称与市场。
3. **两个同步入口收拢到投资界面**：设置页不再提供全量同步入口（issue #111 迁移收尾）；标的页提供全量同步（二次确认 + 模态进度 + 中断）与"同步持仓价格"增量同步；盈亏页"当前持仓"概览卡右上角复用同一增量同步接缝（issue #110）。两个界面的增量同步行为完全一致（共用 `useHoldingPriceSync`）。
4. **增量同步的跳过语义**：非股票持仓（基金/债券等，数据源不含行情）、市场未知无法构造 secid、停牌/无效价（f2≤0，保留旧价）均计入"跳过 M 只"统计提示，不报错；完全无持仓时返回明确提示（"无持仓标的可同步"）而非报错。重复触发幂等（每标的一条 `market_prices` 覆盖更新）。

## 理由

1. **"已投资"必须指"当前持仓"**。用户问"我投了什么"，关心的是此刻拿在手里的东西；把已清仓标的算进去会让"只看持仓"过滤、持仓概览、增量同步全部失去意义——增量同步刷一个已清仓标的的价格毫无用处，反而增加 API 成本。已清仓的得失由已实现盈亏（RealizedPnl）承载，两条线各司其职，互不重复。
2. **单一口径谓词防漂移**。`invested` 派生列、`only_invested` 过滤、增量同步收集、持仓概览四处若各自写"当前持仓"判定，将来改口径（例如软删除账户的批次是否计入）要改多处且极易漏改；收口为一处谓词，改动只碰一处（issue #102 落地时即如此组织）。
3. **全量修字典 / 增量刷价格分离，是因为两者代价与目标不同**。全量同步数百次 API 请求、动标的名字典（增删改 `instruments`），是低频重操作；"刷新当前持仓的现价"是高频轻需求（用户看盈亏时想随手刷新）。让全量同步顺带刷价格会把高频轻操作绑定在低频重操作上：要么每次刷新都付出数百请求的代价，要么用户被迫等待一次全量同步才能看到新价格。拆出增量同步后，日常刷新只需个位数请求，全量同步只在标的字典需要修补时（新增上市股票等）才跑。
4. **复用而非另起炉灶**。增量同步复用全量同步的 HTTP 层（主机池、重试、限流 pacer、价格换算）与 `upsert_market_price`，不做第二套网络栈；两处入口共用同一前端接缝，行为一致可推理。

## 代价

1. **两套同步命令并存**，用户需要理解"全量同步"（修字典）与"同步持仓价格"（只刷价格）的区别；靠 UI 文案（"全量同步" vs "同步持仓价格"）与全量同步的二次确认（说明范围与代价）降低误用。
2. **增量同步只覆盖股票**：基金/债券/ETF 等持仓无行情来源，静默跳过并计入统计提示——用户需从"跳过 M 只"得知有持仓没刷新。
3. **停牌/无效价的持仓保留旧价**：增量同步后这类标的的现价可能不是最新（数据源无有效报价），属预期行为而非故障，旧价保留保证市值/盈亏计算仍可用。

## 替代方案

- **"已投资" = 买过就算（含已清仓）**：会让"只看持仓"过滤与持仓概览混入已清仓标的，增量同步白白刷新无持仓标的的价格；已清仓的历史得失已有已实现盈亏承载，语义重复，否决。
- **不拆分，增量同步继续由全量同步承担（维持设置页单一入口）**：高频轻操作被绑定在低频重操作上，每次刷新现价都要付出数百次 API 请求的代价；且入口在设置页，与投资语境割裂（issue #101 的 Problem Statement），否决。
- **增量同步同时修字典（顺带 upsert 名称/市场）**：突破"只刷价格"的职责边界，让"手动创建的名称/市场"可能被数据源覆盖，且把字典变更隐式塞进高频操作，否决（决策 #2 明确不增删、不改字典）。
