# ADR-0133: 储蓄目标以「虚拟账户」承载——进度即余额、复用 other 类型与绑定派生身份

- 状态：已接受
- 日期：2026-09-23
- 作者：Ledger 项目
- 关联：#1750（spec，grilling 定案纪要）；词汇表：储蓄目标域（`CONTEXT-savings-goal.md`，新）；定时计划域 ScheduledTransfer；余额缓存 ADR-0067；黑洞账户先例 ADR-0026

## 背景

用户要「按期存钱、看进度」的目标功能（买车、教育金、养老）。两个前置定夺：

1. **资金落点**：把蓄水做成真实转账到真实账户（余额即进度），还是信封式归集标签（钱不动、按标记累计）。真实「存入」动作多半没有可标记的既有交易——钱没动就没有流水——标签层要么造假交易、要么发明不落核心流水的归集记录。
2. **目标账户的身份落位**：直接做法是账户类型闭集 +1（新增 `goal` 类型），但 `accounts.type` 带 DB 层 CHECK 闭集，SQLite 不能 ALTER CHECK，须按官方 12 步重建表——仓库无 CHECK 变更先例（V001 一次定满、V031 只做过 DROP COLUMN）；且新增枚举值对旧客户端是未知值：同步重放载荷不可解码、旧版应用读新库直接失败。

## 决策

1. **储蓄目标绑定真实账户行（虚拟账户 / 心理账户），进度 = 账户余额 vs 目标额**：存入 = `transfer`（可由定时转账计划 ScheduledTransfer 驱动）、取出 = `expense`，全部是真实流水；否决信封式归集标签层。transfer 零和 → 蓄水不改净资产（与借贷域「净资产守恒」同一哲学）；余额缓存（ADR-0067）、涉及账户过滤、交易搜索全部免费复用；**目标域零新写入路径**。
2. **专属账户复用 `other` 类型，目标身份由绑定派生（黑洞账户同款先例）**：否决新增 `goal` 类型值。复用后新增迁移退化为普通新表（goals），不再重建 accounts；旧客户端同步重放「创建目标账户」照常成功（就是个 other 账户，余额照算），只有目标本体挂起；降级应用开新库无恙；枚举、i18n、穷尽表等闭集接线点从约八处缩到一处。代价是账户类型不再「一眼说真话」——分组、标签、禁删判定全部从绑定派生（账户页分组是目标域的新增 UI 工作）。
3. **推算双向、单币种、达成不自动化**：截止日可选——无截止按节奏正推预计达成时间，有截止反推所需月存并给落后 / 超前差值；目标额币种 = 专属账户币种，目标域不折算；达成是纯展示态，可归档，不自动暂停关联计划（目标域不改定时计划域状态，只提示）。
4. **两个守卫按依赖方向落位**：在用目标的专属账户禁删守卫走壳层编排（accounts 域不可反向依赖目标域）；出资准入 v1 后端不拦（other 本在现金类白名单，目标户当结算户 = 钱出池、进度如实回落，语义自洽），前端出资候选下拉按绑定过滤防呆，后端硬守卫立票观察。
5. **养老分两期**：v1 养老就是普通目标（目标额手填）；养老测算器二期独立交付（仅城镇职工基本养老、输入分层——参保可查项默认问、假设项折叠带默认值、输出明示估算），唯一接触面是「目标金额的来源」升级为可选的缺口回填。

## 理由

- **进度忠实性压倒记账省事**：余额即进度意味着取出、花掉、利息流入全部自然反映，不需要「扣回进度」的第二套账；信封模型省下的录入功夫，换来的是进度与真实可花金额脱节。
- **类型系统少一个「说真话」的值，换回三样更贵的**：迁移成本归零、同步降级优雅、旧版可读性保住。「误清理 other 账户伤及目标池」的风险由绑定派生的分组与标签承接；若未来出现第三个需要身份的账户角色，再评估类型闭集扩充与一次性重建的总账（顺带评估「去 CHECK、枚举单点收口」的一劳永逸方案）。
- **守卫落位是依赖方向的推论不是偏好**：目标域消费核心交易与定时计划，反向引用即成环；壳层编排与前端过滤都是既有接线形态的最轻应用，不为此引入注册点反转。
