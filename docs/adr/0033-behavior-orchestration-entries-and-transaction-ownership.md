# ADR 0033: 行为层编排协议内化——create/update/delete 三入口 + 事务所有权转移

- 状态：已接受
- 日期：2026-09-16
- 作者：Ledger 项目
- 关系：延伸 ADR-0013（出口面收窄 → 协议面收窄），不翻案；其决策 #2（薄 match 不做 trait 注册表）与 #3（investment 出口 prepare/apply/revert 三件套）维持不变

## 背景

ADR-0013 把 8 种 kind 的行为收敛到行为层单点分派，但**编排协议面没收窄**：`revert → plan → 落库 → apply` 的顺序契约由三个调用方各自重演，且知识不一致（issue #169）：

1. **创建路径**（`insert_transaction`）无事务：`plan → insert_row → apply`，apply 中途失败（如 buy 建仓半途）会留下已落库的交易行与半套副作用，无回滚；
2. **修改路径**（`update_transaction_internal`）显式 BEGIN/COMMIT，但旧 kind/商户读取在事务外；
3. **删除路径**（`delete_transaction_internal`）无事务包裹：行为层 revert（buy 清理持仓批次）成功后、软删 UPDATE 失败时，持仓已删而交易仍在，无回滚——真实的数据一致性缺口。

此外：

- buy 守卫文案（「该买入交易已有部分卖出，无法修改/删除」）由每个调用方作为参数传入——调用方知道了投资域内部守卫的措辞；
- `auto_backup::on_write`（写后置脏，issue #126）的调用散在调用方：batch（COMMIT 后）、修改、删除均有，**单笔 IPC 创建缺失**——前端手动记一笔不置脏；
- 定时引擎（`scheduled_transactions::engine`）绕过行为层直调 Writer 接缝，且 CAS 置 processing → `insert_row` → 期次回填 → 计划完成检查之间**同样无事务**（期次可能滞留 processing 而交易未落库）。

## 决策

1. **行为层对外接口 = `create / update / delete` 三个编排入口**（连接 + 输入进，返回终态或错误）。`plan / apply / revert` 收为模块私有实现细节；编排代码整体迁入 `behavior.rs`（`write.rs` 删除，删除编排迁出 `read.rs`），IPC 命令与 `api_server` 直接调行为层——「行为层」与 `behavior.rs` 重合，顺序契约只有一处可达。
2. **事务所有权转移，规则是「保证处于事务中」（嵌套感知）**：入口检测连接事务状态——autocommit 则自持 BEGIN/COMMIT/ROLLBACK（中途失败整体回滚，无中间态泄漏）；已在事务中（批量导入的外层批次事务）则加入外层、失败直接返回错误、回滚由外层持有者负责。批量导入改调 `behavior::create`（嵌套模式），批次编排（去重、回写 dedup_hash、批末 COMMIT、汇总日志）与既有语义（Invalid 行跳过、非 Invalid 整批回滚）零变化。
3. **两个中间态缺口随事务化修复**（对外可观测的行为修复）：删除路径 revert 与软删 UPDATE 同处一个事务；创建路径 `insert_row → apply` 中途失败整体回滚。原「行为函数不内嵌事务、事务边界由调用方持有」的安排（ADR-0013 决策 #3 的附带约定）由此翻转。
4. **守卫文案按入口内化**：buy 已有部分卖出的拒绝文案是行为层各编排入口的实现细节——修改/删除各持自己的措辞（信息量不降），单点定义消除调用方传入导致的漂移；`revert` 的 `partial_sold_msg` 参数随之消失。
5. **提交点副作用归事务持有者**：自持事务的入口在 COMMIT 后统一调 `auto_backup::on_write`；嵌套模式跳过（batch 在自己 COMMIT 后调）。顺带修复单笔 IPC 创建不置脏的缺口（可观测变化：手动记账后开始参与备份到期判定）。`update` 入口把旧 kind/商户读取移入事务内（消除读取与 BEGIN 之间的窗口）。
6. **定时引擎是事务自持的唯一合法例外**：继续直调 Writer 接缝、不经行为层入口——期次状态机编排（CAS 锁定、期次回填、计划完成检查）不可由 create/update/delete 三入口承载。本批为其补事务包裹：`normalize` 保持事务外（只读校验，业务错误期次停留 pending 可重试，现状不变）；事务从 CAS 置 processing 起包到 `check_and_complete_plan`，任何失败 ROLLBACK、期次回原状态可重试。例外在此显式登记，防止被无意复制（batch、AI 导入扩展都是潜在误仿者）。**存量残留不救援（breaking change，不兼容历史）**：本决策只保证此后不再产生 processing 残留；旧版本失败遗留的 processing 期次不做数据迁移救援——升级后维持原状（应用内无重试入口、所在计划永久无法完成），遇个案手动改库（#220 grilling 定案，随实施切片 #230 记录）。

## 理由

1. **「何时需要事务」「操作顺序」是协议知识，不是调用方知识**。散在调用方正是「bug 藏在调用方式里」的形状——三个调用方两种事务状态、一处缺失即为证。收窄协议面后，新写路径（dividend/split 落地、AI 导入扩展）直接调编排入口，不复制协议。
2. **嵌套感知优于 SAVEPOINT 与双轨**。SAVEPOINT 每行包裹会改变 batch 失败语义（apply 失败可只回滚该行，不再整批回滚）——超出「不改行为」的边界；batch 保留直调 plan/insert_row/apply 的例外则留一个协议知识泄漏的口子。「保证处于事务中」让单条协议与批次原子性各归其位：事务知识归行为层，批次原子性是批量编排的独立关注点。
3. **守卫文案随入口走而非随调用方走**。文案漂移的根源是文案作为参数穿越了层边界；内化为入口实现细节后，同一入口同一文案由构造保证。
4. **例外登记在 ADR 而非代码注释**。不加约束的例外会被无意复制；「定时引擎是唯一合法例外」写在决策记录里才有约束力。

## 代价

1. 嵌套模式下入口的行为依赖调用方事务状态（两个分支）——由「保证处于事务中」这条单一规则约束，且 batch 是嵌套模式的唯一合法使用者。
2. 对外可观测行为变化三处：创建/删除中途失败从「残留中间态」变为「整体回滚 + 报错」；单笔 IPC 创建开始触发备份置脏；均属缺陷修复性质，BDD/HTTP seam 测试锁定。
3. `update` 读取移入事务内，事务持锁窗口略有加长（多一次主键读）——可忽略。

## 替代方案

- **SAVEPOINT 包裹**（入口统一用 SAVEPOINT）：可让 batch 失败行不再拖垮整批，但改变既有批次回滚语义，且嵌套语义更绕，放弃——语义改善值得想要另立 spec。
- **batch 保留直调 plan/insert_row/apply**：协议知识在一处泄漏，与「调用方式里不藏 bug」的目标相悖，放弃。
- **定时引擎切到编排入口**：需为期次状态机扩入口形状（回调/前置钩子），为单场景扩接口不划算，放弃——登记为例外并补事务。
- **on_write 留在全部调用方**：「何时置脏」的知识继续散在调用方，单笔创建缺口不修，与本决策方向相悖，放弃。
