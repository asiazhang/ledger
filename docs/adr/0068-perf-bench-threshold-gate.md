# ADR-0068: 性能阈值与门禁——perf-bench 全部基准 p95 ≤ 200ms 判定

- 状态：已接受
- 日期：2026-09-04
- 作者：Ledger 项目
- 关联：ADR-0062（本 ADR 兑现其「观察期后另立决策」承诺）、ADR-0009（100ms 慢查询告警线保留不动）、ADR-0008（列表分页契约不动）、ADR-0066（余额/净资产缓存，消灭两个 88s 项）；#489（性能达标 spec）、#490/#491/#492（B1–B3 三层修复）、#493（本 ADR 与门禁落地票）；词汇表无新增词条（开发侧基础设施与 CI 行为，不产生领域术语）

## 背景

ADR-0062 落地确定性基准数据集与 bench 工具（50 万笔 seed 42 库、10 项查询基准）时，明确 CI「只记录不判定」：当时尚无一份达标基线，阈值从何谈起没有依据，故承诺「阈值机制等基线分布稳定后另立决策」。彼时的 perf-bench #1 基线（run 33826098405）显示：10 项基准 9 项超过 100ms 慢查询告警线，全账户实时余额与净资产总览各约 88 秒，备注搜索 2.9 秒——先修复、后立阈值的顺序是唯一可行的。

#489 据此拆出 B1–B3 三层修复：V016 结构索引与统计（消灭 6 项慢查询）、V017 余额与净资产持久化缓存（消灭两个 88s 项，ADR-0066）、V018 搜索取行两段式（2932ms → 约 155ms @ CI）。三层已全部合入 main，全部基准项回落到 200ms 判据线以内且分布稳定——观察期结束，兑现承诺的条件成熟。若继续「只记录」，性能回归将在合入后无人拦截，B1–B3 的成果随时可能被无声侵蚀。

## 决策

### 1. 阈值判据：全部基准项逐项 p95 ≤ 200ms @ perf-bench CI

perf-bench CI（ubuntu-latest runner，现场生成 50 万笔 seed 42 确定性库）上，bench 报告的全部基准项（当前 10 项）逐项判定 p95 ≤ 200ms；任何一项超标，perf-bench job 失败。判定对报告全部项生效，不设逐项白名单——新增第 11 项基准即自动纳入门禁，但增删基准项须同步修订本 ADR 的项数表述。

### 2. 统计口径：预热 3 次 + 计时 20 次，p95 最近秩法

- 预热 3 次不计入统计（热 SQLite 页缓存与语句缓存）；
- 计时迭代 20 次，p95 取升序样本第 ⌈0.95·n⌉ 位（最近秩法）。n=10 时 rank=⌈9.5⌉=10，p95 恒等于 max、无任何分位数分辨力——迭代数由 10 提到 20（rank=19，第 19 位样本）是判据成立的前提，不是可选项；
- 判据一律以 CI 运行为准；本地 NVMe 计时与 CI 盘差异可达数倍，只作开发参考（#489 实测决策原文照录）。

### 3. 判定下沉工具内，workflow 只传参

门禁判定实现在 `ledger-perf bench --max-p95-ms 200`：工具对全部基准项逐项判定，超标即打印超标清单（报告尾部，随 tee 进 Job Summary）并以非零退出码失败。workflow（`.github/workflows/perf-bench.yml`）只负责以固定参数调用——本地与 CI 跑同一条命令，门禁行为可精确复现，不存在「CI 里另一套 awk 判定」的第二事实来源。

执行面维持每周 cron + 手动 dispatch，**不进 PR 流水线**：一次 perf-bench 含 release 冷编译 + 现场生成 + 基准，约 47 分钟/次，逐 PR 跑成本不可接受。性能回归的拦截路径是：性能相关批次合入后手动触发 perf-bench 留基线（#489 验收流程），加上每周 cron 常规运行——超标即红，超标清单直接给出回归项名字。

### 4. 豁免原则：判据只覆盖基准集内的读查询

判据只覆盖 bench 的 10 项读查询（用户高频读路径的性能形似画像）。启动迁移、备份/恢复、搜索拼音列惰性回填等合法慢路径**不在判据内**——它们本来就不在基准集里；未来若考虑入集，须先修订本 ADR 论证「合法慢」与「性能回归」在该项上如何区分。

ADR-0009 的 100ms 单条 SQL 慢查询告警线（连接级 trace_v2 观测机制）**保留不动**。两层互不替代：观测线回答「哪条 SQL 慢」（语句级、warn、含启动迁移等全部执行上下文），门禁线回答「这批用户可感查询是否达标」（基准项级、p95、仅 CI 判定）。门禁生效后启动/回填仍可能成群出现 100ms warn，按 ADR-0009 原样解读，不是门禁问题。

### 5. 阈值出处：交互可感的工程上限

200ms 取交互可感阈值的工程上限，与 ADR-0009 的 100ms 观测线保持 2× 关系。B1–B3 合入后其余各项 CI p95 均在数十毫秒以内，余量充足；最慢项为备注搜索（V018 后约 155ms @ CI），余量约 1.3×。该余量是 #489 spec 明确验收的数值（50 万笔下全部 10 项 p95 ≤ 200ms），不是本 ADR 新定。

## 备选否决

- **阈值定 100ms（与告警线一致）**：否决。CI 盘慢、runner 抖动大，对 ~155ms 的搜索项必然假红；且 100ms 是 SQL 语句级观测线，与用户可感的基准项级阈值不是一个口径。
- **p50/avg 判据**：否决。均值对尾延迟不敏感，而用户感知的正是「最慢的那一次」；p95（20 次迭代）才是与体感对齐的口径。
- **PR 触发 perf-bench（逐 PR 拦截）**：否决。约 47 分钟/次的 release 冷编译 + 生成 + 基准，乘以 PR 频率成本不可接受；拦截由「性能批合入后手动触发 + 每周 cron」承担。
- **workflow 侧脚本解析报告做判定**（awk 阈值比较 bench-report.txt）：否决。判定逻辑与数据源分离后，本地无法用同一条命令复现门禁，CI 与本地行为必然漂移；判定下沉工具内则天然同源。

## 后果

- 性能回归在 perf-bench 运行时被拦截：job 红、Summary 列出超标项名字与实测值，不再「只记录」。
- CI runner 抖动可能造成间歇假红：余量最小的搜索项约 1.3×。处置纪律：复核单次运行的完整数据（报告含 min/avg/p95 全列），持续贴线或常态超标则修订本 ADR 显式调整阈值——不悄悄改参数重跑，不以单次绿掩持续红。
- 迭代 10→20 使 bench 计时阶段时长约翻倍（10 项 × 20 次 + 预热，秒级到分钟级），相对 47 分钟的 release 冷编译可忽略。
- bench 缺省仍不判定（`--max-p95-ms` 缺省 None）：本地观察、开发调试不受门禁影响；门禁是 CI 调用参数，不是工具缺省行为。
- 每项基准的 ▲ 报告标记仍按 ADR-0009 的 100ms 阈值点亮（观测视角），与 200ms 门禁行并存于报告，两个阈值各表其义。
