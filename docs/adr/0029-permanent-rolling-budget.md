# ADR-0029: 预算简化为永久滚动（Permanent Rolling Budget）

- 状态：已接受
- 日期：2026-08-29
- 作者：Ledger 项目
- 关联：issue #181（spec）、issue #182（滚动窗口）、issue #183（写入校验与查重）、issue #184（编辑金额与表单简化）、issue #185（文档沉淀）

## 背景

预算初版（issue #91）的表模型带 `start_date` 列，暗示「从开始日期起算」的窗口语义，实现也随之漂移：年度预算实际只统计开始日期所在当月的支出（口径 bug），用户设置的预算既不按月滚动、也不按年累计。而用户的真实心智是「设一次、长期有效」——月预算每月自动归零重来，年预算全年累计，不需要也不期待逐期设置起止日期。spec #181 决定把预算简化为永久滚动模型，本 ADR 沉淀该决策及其对已发布 schema 的处理方式。

## 决策

1. **预算为永久滚动（Permanent Rolling）**：预算一经设置长期有效，不设起止日期、不逐期排程。进度窗口永远是「当前自然周期」——`monthly` = 今天所在自然月，`yearly` = 今天所在自然年——由计算时刻的「今天」驱动、随时间自动滚动，不持久化任何窗口状态。历史遗留的预算行（带旧 `start_date`）零迁移、零操作即按新规则滚动生效。
2. **`start_date` 为冻结残留，不参与计算**：`budgets.start_date` 列自初始 schema 起已发布（v0.1.0 即包含该列），按仓库发布约定（已发布 schema 只增不改，变更一律新增向前迁移）不可删除或改语义；保留该列仅为兼容已发布 schema，创建时照常记录用途，但**不参与任何计算**，UI 已移除日期选择器与「开始日期」列。不写「置空/回填」类迁移——列保留原值即为最忠实的残留记录。
3. **被放弃的替代方案：逐月/逐期设置模型**（每月一条预算记录，或「开始日期 + 结束日期」窗口式预算）。放弃理由见下「理由」；若未来出现真正的按期排程需求（如某月专项预算），应作为新概念另立，而不是复活 `start_date` 语义。
4. **写入行为随简化收敛**（issue #183 / #184 落地，非本 ADR 核心，记录边界）：金额必须为正数、只能挂支出分类；同「分类 + 周期」仅允许一条未删除预算，重复创建明确拒绝并引导编辑既有预算，不静默覆盖；编辑仅允许改金额，分类/周期不可改（改法为删旧建新）。

## 理由

- **为什么滚动而不是逐期设置**：用户的约束是持续性的「每月这类支出不超过 X」，不是一次性的按期排程；逐月设置模型要求用户每月录入或复制预算，记录负担与遗忘风险都高，而滚动模型零操作达成同一约束。逐期模型的历史期记录还会随查重、编辑语义纠缠（历史期能不能改？），复杂度不成比例。
- **为什么窗口取「当前自然周期」而不是「最近 N 天」或「自 start_date 起算」**：自然月/自然年与账本报表、订阅花费等其他周期口径对齐，用户对「这个月」的预期天然就是自然月；「自 start_date 起算」正是本次修掉的口径 bug 的来源。窗口由「今天」临时推导而非持久化，意味着没有需要随时间维护的状态，也不存在窗口状态与流水不同步的问题。
- **为什么 `start_date` 留而不删**：单机应用但已发布（该列自 v0.1.0 起存在），仓库约定已发布 schema 冻结；删除列需要新迁移且对旧库是破坏性变更，收益却只是去掉一个不参与计算的列。保留列 + 文档标注语义的成本更低，且未来若需要「预算生效起始」语义，该列尚可复用（届时再立 ADR）。

## 代价

1. `start_date` 成为 schema 噪音：新读者可能误以为它参与计算。此风险由文档收口（分域词汇表 Budget 条目、`docs/model/basic/budgets.md`），不改代码。
2. 前端类型 `start_date` 保留但标注仅记录用途，新建/编辑表单不再提供该输入——旧数据里的日期在界面上不可见。
3. 永久滚动意味着无法表达「只限某一个月」的临时预算；该需求出现时需另立概念（见决策 3）。
