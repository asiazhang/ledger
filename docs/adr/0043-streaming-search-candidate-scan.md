# ADR-0043: 交易搜索候选处理流式化（内存 O(1)）

- 状态：已接受
- 日期：2026-08-31
- 作者：Ledger 项目
- 关联：ADR-0027（统一模糊搜索语义与全量扫描实现，本文为其实现细节的延续修订）

## 背景

ADR-0027 确立了交易搜索的「SQL 取候选 → Rust 内存逐条过滤 → 分页」结构，实现为
`query_all` 一次性物化全部候选与命中行。这一形态在「子序列语义逼着全遍历」的前提下
正确，但存在 O(n) 内存驻留：候选与命中各物化一份全量 `Vec`，内存随数据量线性增长。

实测（10 万笔、release、忠实复刻生产语义）结论：

- **物化 vs 流式耗时无差异**（约 110–130ms，差值在噪声内）：瓶颈在拼音计算与 SQLite
  取行，二者都要做，「装进 Vec」不是瓶颈。
- **内存有质的差异**：最大驻留峰值 10 万笔 64.8MB → 15.9MB，50 万笔 309.5MB → 63.5MB；
  流式内存基本不随数据量增长（O(1) 单行游标），物化则线性放大。

## 决策

交易搜索候选处理改为**流式**：`query_map` 游标逐行读取、逐行按统一语义契约过滤、命中即
累加 `total` 计数、只保留当前页条目物化。语义、对外 API、排序（日期降序）、分页、
`total` 的精确性全部不变；`text` 纯函数与前端拼音契约一行不动。改动封闭在查询执行内部。

## 理由

**为什么物化不省时间**：子序列命中的键集合不可枚举、无字典序区间（ADR-0027 已论证），
任何实现都必须遍历全部候选；物化多做的只是「把遍历结果装进 Vec」，而这件额外事与
遍历本身相比成本可忽略。流式是严格更优：时间无回归、内存 O(1)、语义零变化。

**为什么仍是全量遍历而非索引加速**：本决策不改变 ADR-0027 的核心立场——子序列语义与
倒排索引不兼容，全遍历是语义的必然成本。流式只是让「全遍历」不再以「全量驻留」的形态
发生，不引入任何索引层。

**为什么不是换库或下推 SQL**：换库（DuckDB/RocksDB/Tantivy 等）对子序列语义零收益，且
数据层无抽象、20+ 命令模块直接依赖 rusqlite，代价与收益严重失衡；把匹配逻辑注册为
SQLite 自定义函数或改用 `LIKE '%...%...'` 属假下推（复杂度不减、索引仍失效、且制造
第三份语义实现）。均被否决。

## 后果

1. 内存峰值从 O(n) 降为 O(1)（候选与命中不再全量驻留），50 万+ 笔量级下不再有内存
   风险；10 万笔个人账本量级下属「严格更好但非紧急」的保险性改动。
2. 全遍历的本质不变：搜索仍是 O(全库)，若未来数据规模或匹配复杂度超出预期，仍需
   回到 ADR-0027「后果」一节的重新评估（本文不预留索引层逃生舱）。
