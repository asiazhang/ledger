# ADR-0080: 依赖重启的路径改用原位重引导 + WebView 重载——进程重启退役为用户手动行为

- 状态：已接受（已实施，issue #644）
- 日期：2026-09-06
- 作者：Ledger 项目
- 关联：ADR-0075（决策 5/6/7——解锁、转换、恢复「完成后自动重启」的时机与用户可见语义不变，重启机制由本决策更换）；ADR-0007（RestoreSafetyBackup 兜底）；ADR-0016（自动备份调度，幂等化见决策 4）；ADR-0018（DataLocation 引导，重引导复用同一解析）

## 背景

加密开启/关闭/改口令、备份恢复、解锁补做搬迁都以「操作成功 → 提示 → 应用自动重启」
收尾，`restart_app` 长期实现为 tauri 的 `app.restart()`：重新拉起当前二进制并退出老
进程。两条结构性缺陷（issue #644）：

1. **开发构建白屏**：`tauri dev` 的 CLI 拥有 dev server（vite）生命周期——应用进程
   一退出，CLI 即回收 dev server 并退出。`restart()` 先 spawn 新进程再 `exit(0)`，
   新进程拉起 WebView 时 dev server 是否存活是一场竞态：赢了有界面，输了整窗空白。
   开启加密后的首次重启正是该路径（重启 → 密文库 → 解锁屏），白屏直接击穿加密流程。
2. **macOS 重启竞态**：`AppHandle::restart` 在主线程调用时直接 `process::restart`，
   越过 `RunEvent::ExitRequested`/`RunEvent::Exit` 的常规兑现（tauri#12310 在案），
   退出兜底备份、窗口状态保存等清理的执行时序不可控；M 系机型上另有重启失效报告
   （tauri#8472）。

进程重启的根本问题：**机制上是进程边界，语义上只需要「回到新启动的状态」**——即库
文件按现状重新判定、连接与门状态与之对齐、前端按启动相位重新落屏。凡是可以不跨进程
边界就达成的状态推进，都不应承担进程重启的全部风险面。同批诊断还发现解锁屏自动
解锁无等待边界（钥匙串读取受阻时加载态永久遮蔽手输与逃生门入口，issue #644 白屏
根因一），属解锁编排，裁决在 ADR-0075 决策 5 修订，不在本篇。

## 决策

### 1. `restart_app` = 原位重引导：进程不退出，重跑启动引导序列，前端随后重载 WebView

- 命令契约不变（`restart_app`，无参，前端 `restartAppShortly` 单点延迟 800ms 调用）；
  实现从「`app.restart()` 进程重启」换为：后端重跑启动引导序列（DataLocation 解析 →
  生效库文件处置判定 → 连接原位换入/占位 → 加密锁定门与启动失败门翻转）→ 返回 →
  前端 `window.location.reload()` 重载 WebView → 重新探测启动相位，落到解锁屏/失败
  恢复屏/主界面。
- **备选与否决**：保留进程重启、仅 dev 构建改重载（两形态行为分叉，进程重启 bug 类
  不退役，且 dev 永远测不到 release 路径）；纯前端 reload 不重引导后端（语义错误：
  锁定门、连接、搬迁意图都是进程态，不重引导则 `get_boot_status` 报告旧相位，「重启
  后回到解锁屏」不成立）；修 dev 重启本身（老进程等新进程就绪再退，双进程窗口并存
  且 tauri CLI 行为不可控，时序脆弱不「明确、原子」）。

### 2. 启动引导序列单点：启动与重引导消费同一段代码

- 引导序列收口为壳层单一函数（`commands::boot::boot_sequence`）：内核是 db 层纯函数
  `plan_boot`（先 DataLocation 引导解析生效目录，再对**解析后的**生效库文件做处置
  判定），进程启动（`lib.rs` setup）与重启命令都消费它——「重启后状态 = 新进程启动
  状态」恒成立，这是进程重启退役后语义等价的根据，也由 BDD「原位重引导」场景钉住。
- DataLocation 引导结果的托管形态改为 `RwLock<Boot>`：重引导需要整体换入新引导结果
  （解锁补做搬迁后生效目录切换到目标），消费方只读克隆，登记/读取收口两个接缝。
- 门翻转次序 fail-closed：进入锁定/失败先立门再换连接，回到就绪先换入真实连接再开门
  ——换连窗口内业务 IPC 恒被门禁拦截，不会暴露给占位/旧连接。

### 3. WebView 重载由前端在命令成功后执行

- `restartAppShortly` 在 `restart_app` 返回后重载页面；命令失败不重载、保留当前界面
  （仍可操作，错误进 console）——「绝不把用户留在不可操作的空白页」。重载时点由前端
  掌握也保证了 toast 先落地再切屏的既有节奏。
- **备选与否决**：后端命令内直接 `Webview.reload()`（重载与命令应答竞态，且前端无从
  得知失败以保留界面）。

### 4. 自动备份调度幂等化：进程内至多一个调度线程 + 每轮门检

- 原位重引导后线程不重建：调度线程持共享连接 Arc，重引导换连对它透明；启动、解锁
  恢复、重引导三处入口经单次拉起守卫收敛为「至多一个线程」。
- 每轮先门检：锁定/启动失败期间跳过备份与追补（占位连接不是业务库）——重引导把门
  翻回锁定后，已存活的线程在门检处空转等待，解锁/恢复后自动继续。
- 退出兜底备份（`RunEvent::Exit` 上的 `exit_fallback`）不参与重启路径：转换/恢复
  各自有副本语义（旧库 `.bak` 副本 / RestoreSafetyBackup），不靠退出兜底；副作用是
  消除了旧进程退出前对「旧连接」补备份的竞态窗口。

### 5. 重启路径诊断可观测：区分「钥匙串阻塞」与「WebView 未加载」

- 自动解锁命令留痕钥匙串读取耗时与三态结果（耗时长 = 钥匙串阻塞，白屏根因一）；
  重启命令留痕开始/完成与重引导后相位；`get_boot_status` 每次探测即「WebView 已
  加载」信号（重引导后缺失 = WebView 未加载，白屏根因二）。日志不落主口令
  （ADR-0006/ADR-0075 隐私口径不变）。

## 后果

- 命令面零变化：`restart_app` 归口 `commands::boot`（启动域），前端调用与两张锁定/
  失败白名单不变；`commands::backup` 只余备份恢复命令。
- dev 构建下加密/恢复/搬迁全流程不再依赖 tauri CLI 的 dev server 存活；签名构建
  与开发构建机制一致，手动冒烟清单（`docs/verification/574-remember-master-passphrase-smoke.md`）
  覆盖两形态。
- 窗口不再因重启销毁重建：窗口状态、聚焦、macOS 激活行为不经历「关-开」抖动；
  `tauri-plugin-window-state` 的存取节奏不受影响（真实退出时照常保存）。
- 进程级单例（首兜底备份的每会话一次标记等）在重引导后不重置：会话语义延续，
  与「进程退出才结束会话」的既有口径一致。
- 自动化回归：Vitest 钉「重启声明与重载」（`restart.test.ts`、解锁屏自动解锁有界
  等待与搬迁重启）；BDD `encryption.feature` 钉「重引导计划与启动同序列」（搬迁
  切换生效目录仍等待解锁、关闭加密就绪建连）；调度幂等由门检逻辑与人工冒烟覆盖。
